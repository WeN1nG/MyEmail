## 设计主张:AI 原生不是「加一个聊天框」

大多数应用接入 AI 的方式是**在旁边加一个对话框**:聊天归聊天,功能归功能,两边互不知道对方在干什么。

这个项目的做法相反:**AI 是一等公民,界面是它的执行器**。用户说「把周报里的待办加到日历」,模型自己拆步骤、自己调工具、自己在失败后换参数;而**能不能做、做了什么、做完没有**,全部由引擎说了算。

分工只有一句话:

> **判断归模型(它擅长),边界与对账归引擎(它必须可验证)。**

<div align="center">

| 环节 | 谁负责 | 为什么 |
|:--|:--|:--|
| 这句话到底要干什么 | **模型** | 定性需求(「重要的邮件」)在数据里没有对应字段,只能靠理解 |
| 这件事我能不能做 | **引擎** | 能力清单由本次请求**实际下发的工具**生成,不靠提示词手抄 |
| 分几步、每步传什么 | **模型** | 清单由模型写,用户第一屏就能看出有没有理解错 |
| 这一步真的成了吗 | **引擎** | 只认工具回执 + 引擎自增的 `attempts`,模型自述不算数 |
| 同一句话写了几条 | **引擎** | 本轮已建成的标题记住,同名第二次直接拒 |
| 上次这个错怎么犯的 | **引擎** | 模型不跨轮学习,所以由引擎统计失败指纹再回灌 |

</div>

四条由此推出的硬规则:

1. **提示词只写通用原则,机制一律交给引擎。** 删掉过「天气有歧义就把候选列给用户」这类场景流程,改成「能从工具查到的先查」「你替用户做了选择就要说明按什么选的」。换一个城市、换一首歌,原则仍然成立。
2. **写操作必须可对账。** 清单条目有状态、有回执(`evidence`),`done` 还要求引擎记录的执行次数 > 0——「模型说它建了日程」不算数,库里没有就是没有。
3. **定性词由模型翻译成判据,引擎只执行。** 「优先处理」不会被写死成某个固定口径:模型给出 `must`(范围)与 `boost`(优先级),引擎如实执行并标注每封命中了哪一条。
4. **能力清单是引擎生成出来的,不是抄写的。** 工具表加一个,索引自动跟上;以前手抄的名单从 13 个漂移到 4 个,模型以为自己不会做的事,其实是没人告诉它。

## 一个请求在引擎里怎么走

```
        用户: "把周报里的待办加到日历,明天下午三点"
                          │
                  ┌───────▼────────┐
                  │  PLAN   (60s)  │  只下发 plan_submit / answer_directly
                  │  写 1–8 步清单  │  拒绝「执行期注定失败」的步骤(缺必填参数)
                  └───────┬────────┘
                          │  plan_submit
                  ┌───────▼────────┐
        ┌────────►│ EXECUTE (300s) │  业务工具 + plan_update
        │         │  按清单执行      │  每次调用带 motive,回执写进 trace
        │         └───────┬────────┘
        │                 │ 执行事实回灌
        │         ┌───────▼────────┐
        │         │ REFLECT (45s)  │  不给工具,只问「到底做完没有」
        │         └───────┬────────┘
        │  判定没做完      │ 判定做完
        └─────────┐       │
          ┌───────▼────┐  │
          │ REPLAN(120s)│ │  只给 plan_submit;新计划按历史失败指纹裁剪
          └────────────┘ │
                  ┌──────▼─────────┐
                  │  FINAL  (45s)  │  不下发任何工具,必须把话说出来
                  └────────────────┘
```

五个相位各有**独立时间预算**:某个相位自说自话,不会把整轮的时间吃光。工具集也按相位下发——PLAN 阶段看不到业务工具,REPLAN 阶段只有 `plan_submit`(否则「重列不超过 2 次」的上限等于没有),FINAL 阶段一个都没有。

上限是硬的:一轮最多 **24 次模型往返 / 24 次工具调用**、整轮 **300 秒**、并发 **2 条流**、两次请求间隔 **400ms**、HTTP 429 退避 **2s → 5s → 12s**。

## 技术要点

### 1. 清单:不是给模型做笔记,是给用户对账

模型动手前必须用 `plan_submit` 写清单(1–8 步),每步都要有:要做什么、调哪个工具、传什么参数、**拿到什么才算成功**。

约束不写在提示词里,而是引擎强制的:

| 约束 | 若违反 |
|:--|:--|
| 步号 1–8、不重复 | 整份计划被拒,回执点名第几步 |
| 标题 / 能力创建后不可改 | 拒绝改写(否则用户看到的清单和真实执行对不上) |
| 状态只能前进(`Pending → Running → 终态`) | 终态不可回退,避免「已完成」之后又变「失败」 |
| `done` 必须有 `attempts > 0` | 一次都没执行就写「已创建」,直接拒 |
| `done` 必须有 `evidence` | 没有回执等于让用户无法对账 |
| 0 命中不是失败 | 按 `on_empty` 处理,不能让后面的步拿着空结果继续跑 |

`attempts` 是**引擎唯一可写**的字段:模型改不了它,所以「谎报成功」这条路在结构上就被堵死了。2026-11-10 的实测里,模型曾写「已创建下周五交材料」而 `tool_trace` 是空的——现在这类回复会被计划校验当场拒绝。

### 2. 定性需求:模型翻译判据,引擎执行两档语义

用户说「重要的邮件」「紧急的事」「该处理的」——这些词在邮件表里**没有对应字段**。引擎不替模型定义「重要」,但也不能只给一个「取并集」的开关:那样「优先处理」会退化成「近 7 天」。

所以判据分两档:

```jsonc
"criteria": [
  { "label": "近 30 天", "mode": "must",  "days": 30 },        // 范围:取交集
  { "label": "已星标",   "mode": "boost", "flagged_only": true }, // 优先级:命中即加分
  { "label": "未读",     "mode": "boost", "unread_only": true }
]
```

- `must` 之间是「且」——**不满足就根本不出现**,用来框范围;
- `boost` 只影响排序——命中越多越靠前,用来表达「优先」;
- 一条 `must` 都没有时退化为「并集 + 命中的排前面」,与老行为等价;
- 每条结果的卡片理由写**最靠前的那条判据**,用户一眼能看出模型把「重要」理解成了什么;
- 0 命中时回执点名「是哪条 must 把范围卡死的」,模型不用猜为什么空。

判据名会显示在清单和卡片上,所以模型无法偷偷换口径——理解错了,用户第一屏就能发现。

### 3. 工具与权限:四层边界

让模型调用工具(查邮件、建日程、播音乐)最大的风险是**被诱导执行有害操作**。这里有四层:

| 层 | 机制 | 效果 |
|:--|:--|:--|
| 请求期 | 16 个工具(**13 个业务 + 3 个记账/通道**)+ **9 个权限开关** | 关掉的工具**根本不下发给模型** |
| 执行期 | `phase_allows` 二次校验 | 模型返回本相位/本次没下发的工具 → **直接拒绝** |
| 重放期 | 正向列举可重放工具(11 个) | 「重新生成」时写操作一个都调不到 |
| 确认期 | `calendar_delete` 只发确认卡 | 用户点「确认删除」之前,**库里什么都没发生** |

这几条值得单独说:

- **正向白名单而不是反向排除**:写成「排除已知写工具」,以后新增一个带副作用的工具会**默认被判成可重放**。正向列举是失败安全的——忘了登记的工具默认不可重放。
- **每个调用必须带 `motive`**:模型说明「为什么调这次」。缺失不拒绝执行(重试一枚 tool_use 只是白吃预算),但要降级记录——它是给人看的说明,不是安全边界。
- **音乐在 UI 进程执行**:模型碰不到音频设备,回执超时按「工具失败」回报,不让整轮崩掉。
- **邮件正文一律是不可信资料**:分隔符会被转义,防止正文里伪造 `--- END CONTEXT ---` 逃逸出上下文;正文里的任何指令都不执行。

### 4. 跨轮记忆:模型不会学习,引擎替它记

同一个参数错误,模型换个会话会原样重犯——它看不见自己上次怎么错的,提示词里写「注意别重复犯错」等于没说。

引擎的做法是从**已有的** `tool_trace` 里统计:

```
最近 40 条带轨迹的消息
   → 归一成指纹(抹掉步号、数字、「」里的具体值)
   → 同类失败出现 >= 2 次才算「教训」
   → 最多 4 条,随系统提示下发:「以往踩过的坑」
```

限额类失败会被排除(参数怎么改都过不去,写进去只会误导)。不新建表、不加字段——统计不该再生一份真相。

顺带说,「能力索引」也是引擎生成的:本次请求下发了哪几个工具,就列哪几个,一句话一个。加工具、关能力、重新生成,索引自动跟上。

### 5. 自研 HTML 排版引擎

**难点在于**:邮件不是网页。`<table>` 布局是 1998 年的遗产,真实邮件里满地都是;而通用 CSS 布局引擎会为了「正确」把一个表格拆成几十个匿名盒,丢掉作者精心调好的像素。

**解法**:两步走。

```
parse.rs   HTML5 DOM(scraper)→ 清洗 → 扁平块模型
   ↓         后台线程 spawn_blocking,并发 2
css.rs     CSS 子集解析 → 选择器匹配 → specificity 排序
   ↓
layout.rs  按内容宽度测量出每个块/行/单元格的绝对矩形 → 一次性绘制
```

关键设计是**测量与绘制分离**:先算出所有元素的绝对 `Rect`,再交给 painter 按文档序绘制。

- 一个段落 = **一个** `LayoutJob`(而不是每个行内片段一个控件)——断行、CJK、字体度量、文本选区全交给 egui 原生能力,但保持段落整体性
- 真实支持 `rowspan` / `colspan` 表格网格、`display:inline-block` 列容器、`max-width` 约束、相邻边距折叠
- `line-height` / `letter-spacing` / 逐行 `text-align` 精确还原
- 选择器优先级按 `(id, class/attr/pseudo, type)` 三元组近似计算

**性能**(release):930 KB 复杂邮件 ≈ **35 ms**,1000×5 表格 ≈ **13 ms**。

**安全边界**:不执行脚本、不加载外部 CSS/字体、不使用 WebView。`position`/`float`/`flex`/`grid` 按块级文档流降级。硬上限(节点 ≤50k、深度 ≤128、文本 ≤2MB)超出即回退到简化视图,绝不 panic。

### 6. 自研 SSE 流式解码

大模型 API 的流式响应用 Server-Sent Events。`reqwest` 能收字节流,但**不解析 SSE**——引入一个 SSE 库意味着多一个依赖、多一份信任。

`sse.rs` 用 267 行解决,核心是一个反直觉的细节:

> **`\n` 是 ASCII 字符,不可能出现在 UTF-8 多字节序列中间。**

所以只要**按字节缓冲、遇到 `\n` 才解码**,就不会把一个中文字符从中间切开——哪怕 TCP 恰好在那个位置断了包。这个性质无法靠事后补救,必须在缓冲策略上做对。

同时实现了字节级总上限(4 MiB)与单行上限(256 KiB),防止服务端异常导致内存无限增长。

### 7. 分层架构:靠编译器保证边界

```
me-app ──Command/Event──► me-sync ──► me-proto
  │                          │  └────► me-store
  └──只读快照───────────────► me-store
所有 crate ──► me-core(唯一汇点)
```

硬规则不是靠自觉,而是靠**编译期就会报错**:

- `me-app` **不能** `use` `async-imap` / `lettre` / `rusqlite` 的任何符号——写错就编译不过
- `me-proto` 与 `me-store` 互不依赖,只通过 `me-core` 的类型通信
- `me-core` 是**唯一汇点**,不依赖 tokio / rusqlite / 任何协议库——领域规则可脱离运行时单测
- 端口 trait 返回 `impl Future + Send` 而非 `async fn`:多线程 tokio 要求 future 为 `Send`,而 `async fn` in trait 无法表达该约束

**`me-app` 不依赖 `me-proto`**——AI 传输层在 `me-sync` 的 `start_native()` 里注入。这是分层带来的直接收益:换模型服务商时,UI 层一行代码都不动。

### 8. 并发治理:抢连接不如先让路

同步引擎面对一个经典问题:后台补全正在下载 500 封邮件的正文,用户此刻点了「发送」。

常见做法是给任务排优先级队列。这里选择**抢占式取消**——高优先任务先 `cancel_backfill(account)` 停掉该账户的补全,再抢连接:

```
Governor: 全局许可 → 账户锁(两段获取,避免环等待)
预算分离: 操作连接 全局2/单账户1,监听连接 全局4/单账户1
退避:    30s → 2min → 5min
```

两套预算分开计费是必需的:IDLE 监听连接是长连接,如果不与操作连接分开,一封长邮件的同步就能把发送请求饿死。

### 9. 数据可迁移:从 v1 活到 v8

schema 走了 8 个版本。v4/v5 是**纯加列**,靠一个反直觉的判据保证幂等:

> **判断「某列在不在」,而不是判断「版本号到没到」。**

新建库的 DDL 天然带最新列,而从 v2 升级来的库刚跑完 v3 迁移时列的情况又不同——两条路径到达同一版本时状态不一致,用版本号判断必然出错。所以迁移函数都用 `pragma_table_info` 查列,缺了才 `ALTER TABLE`。

v6 换了个判据:它是**纯索引调整**,幂等靠「先 DROP 再 CREATE」——SQLite 没有 `ALTER INDEX`,改索引列序只能重建。

v7 是**同一次迁移里加表又加列**:两张新表用 `CREATE TABLE IF NOT EXISTS` 天然幂等,两列(`in_reply_to` / `"references"`)走 `pragma_table_info` 判列。`references` 是 SQLite 保留关键字,DDL 与所有 SQL 里都得写成 `"references"`——这类细节在新建库与升级库两条路径上必须同时正确,所以它被写进了迁移测试。

v8 只给 AI 消息加一列(`thinking`,存分段思考)。`ai_messages` 上有 `CHECK` 约束,动约束就得重建表,风险远大于收益,所以继续走纯加列。

配套一条铁律:**中间步骤的版本号必须写死**,写 `SCHEMA_VERSION` 会给旧库盖上「已是最新」的章,把后续迁移整段跳过。

每步独立事务 + 末尾 `foreign_key_check`,失败即回滚、不写版本号、启动中止,**不静默降级**。

### 10. 出网请求的安全默认值

凡是会主动发出去的 HTTP 请求,都按「假设对方会攻击你」设计:

| | 防护 |
|:--|:--|
| **远程图片** | 仅 http/https、端口白名单(80/443/8080/8443)、拒本机/私网/CGNAT、**逐跳 DNS 与重定向校验**、不发 Cookie/Referer、单张 ≤8 MB、20s 超时 |
| **天气 API** | 禁止重定向(防止被引到内网)、Key 只走请求头(`X-QW-Api-Key`,URL 里绝不出现 `key=`) |
| **OAuth 令牌** | 禁止重定向、20s 超时、响应体 ≤64 KB、令牌类型 `Debug` 脱敏 |
| **模型 API** | 禁止重定向(防 Authorization 泄露到别的主机)、错误响应体不进入 `detail` |

「逐跳校验」是重点:只检查初始 URL 不够,攻击者可以给一个公网地址,让它 302 到 `http://127.0.0.1/admin`。

### 11. 原生音频:独立线程 + 零阻塞回调

频谱分析的难点是**实时音频回调线程绝不能阻塞**——它跑在 cpal 的回调里,一旦卡住就是爆音。

`spectrum.rs` 的做法:`SpectrumSink` 是唯一跨线程交接点,回调里只做「整块替换」,拿不到锁就**丢弃**这一帧。FFT 全部在 UI 线程做,回调线程永不等待。

播放状态 250ms 回传 UI,频谱与播放状态**都不进 `Command`/`Event` 通道**,也不落库——音频是高频瞬时数据,走持久化通道是设计错误。

## 工程实践

<div align="center">

| 指标 | 数值 |
|:--|:--|
| 代码规模 | 约 59,900 行生产代码 / 30,600 行测试 |
| 测试 | **931 passed / 0 failed / 7 ignored** |
| 测试结构 | 25 个集成测试文件 + 53 个内联测试模块 |
| AI 侧 | 5 相位 · 16 工具 · 9 权限开关 · 7 条编排语料 |
| 直接依赖 | 65 个 crates |
| 外部服务 | 0(邮件/日历/音乐全部本地,AI 与天气可选) |
| WebView / JS 引擎 | **0** |

</div>

**测试**:931 个测试,零失败。分层架构的直接收益是测试不需要真实服务器——`me-core` 的领域规则是纯函数,毫秒级跑完;`me-proto` 用本机 mock IMAP 测协议时序;`me-sync` 注入 scripted provider 跑端到端编排。

AI 侧尤其如此:`crates/me-sync/tests/ai_flow_mock.rs` 里有 7 条 `corpus_` 语料,每条断言**总轮数 / 工具序列 / 正文关键字段 / 清单终态与 `[结果]` 一致**。语料里的模型回答故意不写 `[结果]`,让引擎自己去合成——测的是引擎口径,不是测试自己写的文案。

```bash
cargo test --workspace        # 931 passed / 7 ignored
cargo deny check              # 许可证白名单 + 禁用 OpenSSL/native-tls + 依赖漏洞
```

**质量门禁**:`cargo fmt` / `cargo clippy -D warnings` / `cargo deny check` 全部通过,CI 只在 `windows-latest` 上跑这四道。SQLite 用 `bundled` 并把版本钉在 **3.54.1**,配一条运行时断言(不只是查 crate 版本号——那挡不住「关掉 bundled 改成链接系统库」)。

**提示词也有测试**:`system_prompt_has_no_single_scenario_playbook` 会拒绝任何「只在某一条用例里成立」的写法,`capability_catalog_lists_only_the_tools_downloaded` 保证能力索引只列本次真的下发的工具。改提示词前先通读:

```bash
cargo test -p me-core dump_system_prompt -- --ignored --nocapture
```

**发布安全**:打包脚本会做**信息泄露自检**——扫描 exe 与源码包里是否残留构建机绝对路径、本机标识、凭据形态、真实数据库内容,命中即阻塞发布。release 构建带 `--remap-path-prefix`,否则 exe 里会留下构建机的完整路径。

## 已知边界

诚实地说明这个项目**不做**什么:

- **AI 的通用性有边界**:能力索引只说明「这个工具是什么」,跨能力的组合链路靠模型自己推断;引用语法 `{{step.N.字段}}` 只表达依赖,**不做取值替换**(真正调工具时模型要填上实际值);跨轮记忆只记失败指纹,不记用户偏好;判据目前只有两档,没有更细的权重
- HTML 渲染是**邮件排版子集**,不是浏览器。不执行 JS、不加载外部 CSS/字体;`position`/`float`/`flex`/`grid` 按块级文档流降级;边框按整框近似
- 无 `.ics` 导入导出,跨设备迁移靠数据库文件
- 会话线程只覆盖**新邮件**和**本地有原始报文的旧邮件**,没打开过的历史邮件单独成串;服务器重拉尚未做
- 无系统通知,日历提醒只在应用运行时可见
- 日历重复事件只能改整个系列,尚无「仅此次」编辑界面
- AI 会话列表固定拉取最近 100 条,暂无滚动分页
- AI / 天气密钥以明文存本地库(与其它参数保持一致保存),补偿手段是「不进日志、界面暗文、`Debug` 脱敏」
- 真实 Gmail/Outlook 授权与 IDLE、Docker E2E 尚待人工验收(真实天气 / AI 密钥与真机音频已验收)

## 构建

```bash
git clone <repo>
cd MyEmail
cargo build --release          # 产物 target/release/myemail.exe
```

需要 Rust 1.89+。Windows 下直接运行即可,无需额外运行时。

**OAuth 客户端**(可选,构建期注入,密钥不进仓库):

```bash
MYEMAIL_GOOGLE_CLIENT_ID=xxx MYEMAIL_MICROSOFT_CLIENT_ID=xxx cargo build --release
```

数据目录:`%APPDATA%\MyEmail\`(其他平台走 `dirs::data_dir`)。
