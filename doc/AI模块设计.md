## 0. 摘要

AI 的能力不再按「四个工具」描述，而是按**四个能力模块**组织。每个模块有明确的权限边界、
自己的工具集、固定的任务清单模板，以及一种「给用户看的结果形态」。

| 模块 | 权限 | 执行层 | 结果形态 | 现状 |
| --- | --- | --- | --- | --- |
| 邮件 | **只读**（摘要 + 已缓存正文；不读附件、不写、不发） | `me-sync` | **邮件卡片 = 详情弹窗** | 检索 已实现 / 卡片 部分 / 正文 待建 |
| 天气 | **只读** | `me-sync` | 天气摘要（可选卡片） | 已实现 |
| 日历 | **读 / 增 / 改 / 删** | `me-sync` | 日程卡片 + 撤销/确认 | 增 已实现 / 读改删 待建 |
| 音乐 | **播放控制**（播放、暂停、切歌、进度、顺序；不碰文件） | `me-app` | 播放器状态条 | 待建 |

三条新增的**跨模块契约**（对所有模块一视同仁）：

1. **任务清单**：一次需求先被拆成有序步骤，再逐步执行；每步有状态、有回执。
2. **动机 + 结果**：每次工具调用必须带固定参数 `motive`（动机）；一次能力型回复结束必须带
   固定段落 `[结果]`，且模型必须先理解上一步的工具结果再决定下一步。
3. **卡片同构**：邮件卡片点开的形态与「阅读邮件」弹窗**是同一份实现**，不是简化版。

## 1. 设计目标与不变量

### 1.1 目标

| 目标 | 反例（要避免的） |
| --- | --- |
| 能力边界一眼可见 | 「AI 好像什么都能干」，用户不知道它有没有权限删日程 |
| 多步需求可追踪 | 一句「把上周张三的报价单发我邮箱」换来一段含糊的散文 |
| 每次调工具都说得出为什么 | 活动条只显示「检索邮件」，用户不知道它在找什么 |
| 结果可核对 | 回复里混着「已完成」和「可能失败」，用户分不清 |

### 1.2 不变量（无论怎么实现都不能破）

1. **权限只减不增**：模块开关关掉后，该模块的工具既不出现在请求里，也不能被执行
   （请求期过滤 + 执行期校验，已实现）。
2. **不存在外发路径**：没有发邮件、删邮件、改草稿、移动邮件的工具，永远不新增。
3. **删除要确认**：任何「删」的动作（日历事件）都不能由模型一次调用直接完成，必须经过
   用户确认（待建）。
4. **卡片不复制正文**：卡片只持有 `message_id` 与一句命中理由，正文仍按需打开。
5. **工具结果只回摘要**：不把完整正文、附件、原始 JSON 交给模型；`tool_trace` 不存参数原文。
6. **动机不进日志正文**：`motive` 是给用户看的说明，可以入 `tool_trace`，但不得写入
   `tracing` 的文件日志（避免把用户问题原文带进日志）。

> **两处例外，必须显式记账，不能默认成立：**
>
> - 音乐模块的工具执行器在 `me-app`（见 §2.2），所以第 1 条（执行期校验）与第 5 条（结果只回摘要）
>   由 app 侧代为完成，具体补偿写在 §8.3。`music_play` 属**不可重放**工具（会真的出声），
>   与 `calendar_create` 同级。
> - 升级迁移是一个反向风险：档案 JSON 解析失败如果被静默兜底成默认值，会把用户**关掉的**工具
>   重新打开（见 §7.1）。因此「解析失败必须报错、不得回落默认」是本节的隐含前提。

### 1.3 术语（本文固定用法，避免混读）

| 词 | 指什么 | 不要与什么混用 |
| --- | --- | --- |
| 模块（module） | 能力模块：mail / weather / calendar / music | 不要指「模型档案」 |
| 档案（profile） | `AiModel`，一份模型配置（端点 / key / 预算 / 工具开关） | 不要叫「模块」 |
| 能力（capability） | 模块在清单里的标识，取值就是四个 module 名 | — |
| 工具（tool） | 模型可调用的函数（`email_search` / `calendar_create` …） | 不要与「能力」互换 |
| 清单（plan） | 一次需求的步骤序列，由 `plan_update` 维护（§4） | 不要叫「任务列表」 |
| 卡片（card） | 结果在对话里的展示单元 | 不要与「弹窗」互换 |

### 1.4 非目标（本轮明确不做）

| 不做 | 原因 |
| --- | --- |
| 发信 / 存草稿 / 移动 / 删除邮件 | 外发不可撤回；邮件的「删」在 IMAP 侧语义复杂，本地删了服务器还在 |
| 读附件内容、全文索引附件 | 体积与隐私风险都不划算 |
| 联系人模块、RSS、笔记 | 不属于本轮四个模块，接口先不预留 |
| 多账户/多日历的「帮我挑一个」 | 选择账户是用户配置行为，AI 只在用户点名后使用 |
| 后台替用户下载正文/附件 | 会产生用户不可见的网络请求；只读已缓存内容 |
| 长期天气（>7 天）、在线音乐流 | 数据源本身不提供 |

## 2. 模块化总览

### 2.1 能力模块五要素

任何模块要接进来，必须同时提供这五样，缺一不算「模块」：

| 要素 | 含义 | 落点 |
| --- | --- | --- |
| 权限 | 模块级开关 + 动作级白名单（读/写/删/播） | `AiToolPermissions` 按动作扩列（扁平布尔 + `serde(default)`）；模块级开关由动作开关推导（待建） |
| 工具集 | 一组名字固定的工具，每个都带 `motive` | `TOOL_SPECS` 按模块分组（待建） |
| 任务模板 | 这类需求通常怎么拆步骤（给系统提示与模型参考，不是硬编码流程） | `SYSTEM_PROMPT` 分段（待建） |
| 卡片 | 结果给用户看的形态 | 事件 + UI 组件 |
| 落点 | 副作用写到哪里、能否撤销 | 各模块用例函数 |

### 2.2 分层落位

```text
            ┌──────────────── me-app（UI 线程）────────────────┐
            │  AI 页：对话 / 任务清单 / 卡片 / 结果区块          │
            │  音乐能力执行器（待建，直接操作 AudioPlayer）        │
            └───────────────┬─────────────────────────────────┘
                            │ Command / Event
            ┌───────────────▼─────────────────────────────────┐
            │  me-sync：工具循环、权限校验、任务清单状态机       │
            │  ai_tools.rs：邮件 / 天气 / 日历 三个模块的执行壳  │
            └───────────────┬─────────────────────────────────┘
                            │ 用例函数（search_mail / refresh_weather /
                            │ create_event / update_event / delete_event）
            ┌───────────────▼─────────────────────────────────┐
            │  me-store：摘要 / FTS / 日历 / 实体             │
            └─────────────────────────────────────────────────┘
```

**一处必须解释的例外：音乐在 `me-app` 执行。**

播放器是 `me-app/src/audio/` 里的**本地线程**（`AudioPlayer::send(AudioCommand)`），状态靠
`AudioState` 每 250ms 回传，**不走 `Command`/`Event`**。于是有两条路线：

| 路线 | 做法 | 代价 | 结论 |
| --- | --- | --- | --- |
| A. 把播放器命令化 | 给 `Command` 加音频分支，播放器由 `me-sync` 间接驱动 | 要改命令分发、事件回传、状态轮询三处；等于为了 AI 重构播放器 | 不选 |
| B. 工具层跨界回填 | `me-sync` 发 `Event::AiMusicCommand { call_id, op }`，app 执行后用 `Command::AiMusicResult` 回填，`me-sync` 用 `pending: HashMap<call_id, oneshot::Sender>` 等结果 | 工具循环被切成两段；取消/超时/截断都要自己补 | **选 B** |

选 B 不等于「没有代价」，必须补齐三条（细则见 §8.3）：

1. **取消**：app 侧收到命令后仍要检查 `CancelFlag`（通过事件带上 `conversation` 判定），
   并保证 `stop` 类命令在取消后不会再被回填成「成功」。
2. **截断与摘要**：app **只回结构化状态**（曲目 id / 位置 / 播放中），摘要文本由 `me-sync`
   侧统一按 `MAX_TOOL_RESULT_CHARS` 生成——这样「结果只回摘要」的出口仍然只有一个。
3. **不可重放**：`music_play` / `music_control` 都会改变真实播放状态，`is_replay_safe()`
   必须返回 `false`，重新生成时不下发（同 `calendar_create`）。

### 2.3 一次需求的完整链路

```text
用户：帮我把这周张三发的报价单找出来，顺便看下周五成都天气，再提醒我周五下午三点开会
  │
  ▼  ① 理解
模型读系统提示 + 四个模块的能力说明（只有开着的模块）
  │
  ▼  ② 出清单（待建）
plan = [
  1. 邮件：检索「张三 + 报价单 + 本周」        pending
  2. 邮件：打开命中的邮件，确认是不是报价单     pending
  3. 天气：查成都 11-06 预报                   pending
  4. 日历：建「开会」11-06 15:00，冲突检查     pending
]
  │  UI 显示为可折叠的任务清单，逐步打勾
  ▼  ③ 逐步执行（每步一次或多次工具调用，每次必带 motive）
  │    工具结果 → 模型先复述「这一步拿到什么」→ 更新步骤状态 → 下一步
  ▼  ④ 回执与结果
卡片：邮件 x2（同详情弹窗）· 天气摘要 · 日程卡（可撤销）
[结果]
状态：已完成
做了什么：找到 2 封报价单并展示，查到成都周五小雨 12–17℃，已建日程「开会」
关键信息：报价单来自 zhang@example.com，附件 1 个（未读取）
未完成：无
```

## 3. 能力模块

### 3.1 邮件模块（只读）

**定位**：把「本地已缓存的邮件」变成可检索、可引用、可核对的资料。AI 在这里**只读**。

#### 权限

| 动作 | 是否允许 | 说明 | 现状 |
| --- | --- | --- | --- |
| 检索摘要（FTS / 头部字段） | 允许 | 只查本地库，不联网 | 已实现 |
| 读正文 | 允许（限已缓存） | 未缓存时只能回「请先打开这封邮件」，**不得假装读到、不后台下载** | 待建 `mail_read` |
| 读附件 | 禁止 | 附件内容一律不进上下文 | 不适用（没有该工具） |
| 标已读 / 移动 / 删除 / 发信 | 禁止 | 永远不提供 | 不适用（没有该工具） |

> **一个必须保持的细节**：卡片在对话里出现时**不触发已读**（现状已如此，卡片只读仓储取摘要）；
> 只有用户点开详情才走 `Command::OpenMessage`（会标已读）。两者不能合并——否则「AI 帮你找邮件」
> 会顺手把一屏邮件全标成已读。

#### 工具集

| 工具 | 参数（除公共 `motive` 外） | 作用 | 执行层 | 状态 |
| --- | --- | --- | --- | --- |
| `email_search` | `query?` / `from?` / `to?` / `subject?` / `after?` / `before?` / `folder?` / `unread_only?` / `limit?` | 检索摘要，命中即产卡片 | `me-sync` | 已实现 |
| `mail_read` | `message_id` | 读一封邮件的正文（截断到预算）与元数据 | `me-sync` | 待建 |

`email_search` 的细节（多条件取交集、`from` 走实体别名换邮箱、结果带文件夹/附件标记、
2s 超时）见附录 C，这里不重复。

**`mail_read` 的三条硬规则（否则会重复计费或让模型卡死）：**

| 规则 | 内容 | 为什么 |
| --- | --- | --- |
| 去重 | 若该邮件已在本次请求的 `AiContextRef` 里（用户手动引用），直接返回「该邮件已在上下文中」，不再附正文 | 引用走 `MAX_CONTEXT_TOTAL_CHARS`（20 000），工具结果走 `MAX_TOOL_RESULT_CHARS`（24 000），两套预算；同一封进两份会直接把输入预算吃掉 |
| 预算 | 单封正文截断到 `MAX_BODY_CHARS`（12 000）；一次调用只读一封；每条消息最多 3 次 | 与手动引用同一套截断常量，避免「AI 读的比用户引用的还多」 |
| 未缓存 | 返回 `is_error=false` 的结果文本「正文尚未缓存，请用户先在邮件页打开这封邮件」+ 主题/发件人/日期，让模型能把话说明白 | 模型没有「请求用户下载」的工具，错误结果只会让它反复重试同一个调用 |

#### 任务清单模板

| 需求类型 | 步骤模板 |
| --- | --- |
| 找邮件 | 解析条件 → 检索 → 按条件复核前 3 条 → 呈卡片 → 归纳 |
| 总结某封 | 定位邮件（未指定则先检索）→ `mail_read` → 归纳要点 |
| 对比多封 | 逐封 `mail_read`（≤3 封）→ 列表对比 → 结论 |
| 找 + 引用 | 检索 → 呈卡片 → 提示可「引用到 AI 对话」 |

「找一封邮件」这种单步需求**不建清单**（见 §4.2）。

#### 输出：邮件卡片

卡片**就是**详情弹窗的入口，不是另一套 UI（详见 §6）。

#### 明确不做

- 不总结整箱邮件（没有「全库摘要」工具，代价不可控）；
- 不猜发件人邮箱（实体查不到就按原文匹配，并在结果里说明）；
- 不把附件内容读进上下文。

### 3.2 天气模块（只读）

**定位**：回答「现在/明天/这周怎么样」，数据只来自和风天气的本地快照。

#### 权限

| 动作 | 是否允许 | 说明 | 现状 |
| --- | --- | --- | --- |
| 读天气（当前 / 24h / 7d） | 允许 | 走缓存 + TTL，不额外造网络路径 | 已实现 |
| 列已保存地点 | 允许 | 让模型知道「用户都关注哪些城市」 | 待建 `weather_locations` |
| 新增/删除地点 | 受限 | 只在「唯一命中候选」时自动保存，且在结果里明说；删除只能用户做 | 部分（提示已加） |

#### 工具集

| 工具 | 参数 | 作用 | 状态 |
| --- | --- | --- | --- |
| `weather_get` | `location?` / `location_id?` / `days?` / `hours?` | 取一份天气摘要 | 已实现 |
| `weather_locations` | 无 | 列出已保存地点（名称 + id + 是否默认） | 待建 |

#### 任务清单模板

| 需求类型 | 步骤模板 |
| --- | --- |
| 单地点天气 | 解析地点 → （多候选则让用户选）→ 取数 → 归纳 |
| 多地点对比 | 逐个取数（≤3 个）→ 并列对比 → 结论 |
| 出行建议 | 取天气 → 结合日程（跨模块）→ 建议 |

地点歧义**不建清单**：这是单步阻塞，直接回问用户。

#### 明确不做

- 不做长期预报（接口只到 7 天）；
- 不因为「看起来要下雨」自动建日程或发提醒（没有该路径）。

### 3.3 日历模块（读 / 增 / 改 / 删）

**定位**：唯一有写权限的模块。也正因为它能改东西，**每一步都要能被用户看见和逆转**。

#### 权限

| 动作 | 是否允许 | 约束 | 现状 |
| --- | --- | --- | --- |
| 读（列表/单条） | 允许 | 只读本地库，按时间窗限定 | 待建 `calendar_list` |
| 增 | 允许 | 同标题 ±5 分钟去重；每条消息 ≤5 条；可撤销 | 已实现 |
| 改 | 允许 | 只能改**已存在**的事件；必须回执「改了哪些字段」 | 待建 `calendar_update` |
| 删 | 需确认 | 模型发起 → 工具返回「待确认」→ 用户点确认才删；**软删，可撤销** | 待建 `calendar_delete`（`delete_event` 用例已存在，写 `deleted_at`） |
| 建/删日历本身 | 禁止 | 日历容器属于用户配置，AI 不碰 | 不适用（无工具） |

> **为什么删要两道手**：真正的原因不是「删了找不回来」——`delete_event` 走的是
> `soft_delete_event`（`calendar_events.deleted_at`），日历也只在本地库，恢复只是把
> `deleted_at` 置空。两道手的价值在于**防误选对象**：AI 最容易犯的错不是「删得不可逆」，
> 而是「删错了那一条」——同一天两条同名会议时尤其明显。
>
> 因此删除确认之后**还应该给一步撤销**（与「增」对称，保留 10 秒「已删除 · 撤销」）。
> 这两件事不冲突：确认防误选，撤销防误判。

#### 工具集

| 工具 | 参数 | 作用 | 备注 |
| --- | --- | --- | --- |
| `calendar_list` | `from?` / `to?` / `query?` / `calendar_id?` | 按时间窗/关键词列事件 | 单次上限 20 条，结果只给摘要 |
| `calendar_create` | `title` / `start` / `end` / `all_day?` / `location?` / `description?` / `reminders?` / `calendar_id?` | 建一条 | 已实现 |
| `calendar_update` | `event_id` + 要改的字段 | 改一条 | 只允许改标题/时间/地点/描述/提醒 |
| `calendar_delete` | `event_id` / `reason` | 发起删除 | 返回 `pending_confirmation`，不直接删 |

> **落地成本比看起来小**：`me-sync/src/calendar.rs` 里 `update_event`（:131）与
> `delete_event`（:149）**已经存在**，手动编辑日程走的就是它们。三个新工具实际只差
> 「参数解析 → 调用用例 → 写 trace」这层壳，加上删除的确认流程；不需要新的仓储方法。
>
> **删除的确认流程（与清单联动）**：`calendar_delete` 立刻返回 `pending_confirmation` 并结束本轮
> → UI 展示待删卡片（标题 / 时间 / 日历）→ 用户点「确认删除」后**由 UI 直接发
> `Command::DeleteCalendarEvent`**，不再跑一轮模型 → 删完以系统消息回灌「已删除 X」。
> 不让模型在确认后再发一次调用，是为了避免它顺手改别的东西。

#### 任务清单模板

| 需求类型 | 步骤模板 |
| --- | --- |
| 建日程 | 解析时间/时区 → 冲突检查（`calendar_list`）→ 建 → 回执 + 撤销入口 |
| 改日程 | 定位事件（`calendar_list`）→ 确认改哪几项 → 改 → 回执 |
| 删日程 | 定位事件 → 展示待删卡片 → **等用户确认** → 删 → 回执 |
| 日程 + 天气 | 定位/建日程 → 查当天天气 → 结论（跨模块，必须建清单） |

#### 明确不做

- 不支持重复日程（不传 `rrule`）；
- 不改其他应用/账户的日历（只有本地库）；
- 不在用户没提时间的情况下自行选一个时间（必须回问）。

### 3.4 音乐模块（播放）

**定位**：把「播放器」变成可被语言驱动的能力，但**只到播放控制为止**——不碰文件。

#### 权限

| 动作 | 是否允许 | 说明 | 现状 |
| --- | --- | --- | --- |
| 检索媒体库 | 允许 | 只在已扫描的曲目里找（标题/文件名/标签） | 待建 `music_search` |
| 播放 / 暂停 / 继续 | 允许 | 改变播放器状态 | 待建 |
| 上一首 / 下一首 / 指定曲目 | 允许 | 队列内跳转 | 待建 |
| 拖动进度 | 允许 | 0 ~ 时长（毫秒） | 待建 |
| 切换顺序（顺序/随机） | 允许 | 对应 `MusicOrder` | 待建 |
| 扫描/更换音乐目录 | 禁止 | 属于用户配置，AI 不做 | 不适用（无工具） |
| 删除/移动/重命名文件 | 禁止 | 永远不提供 | 不适用（无工具） |

#### 工具集

| 工具 | 参数 | 作用 |
| --- | --- | --- |
| `music_search` | `query?` / `limit?`（默认 5，上限 20） | 在媒体库里按**标题 / 文件名**找，返回索引 + 标题 + 时长 |
| `music_play` | `query?` 或 `index?` / `mode?`（now / queue） | 播放指定曲目；`query` 多命中时不猜，返回候选 |
| `music_control` | `action`（pause / resume / next / prev / seek / stop）/ `position_ms?` | 控制当前播放 |
| `music_state` | 无 | 当前曲目、进度、时长、顺序、是否在播 |

> **艺术家/专辑不在搜索范围**：`playlist::Track` 只有 `path` / `title` / `duration_ms`，
> 标签是 `tags::read_now_playing()` 在**换曲时**才读的，没进媒体库索引。要按艺术家搜，
> 得先给所有曲目建标签索引（2000 首全读一遍，冷启动会很慢）——不在本轮。模型问「放周杰伦」
> 时，`music_search` 只能匹配文件名，因此结果里要如实说明「按文件名匹配」。

四个工具全部为**待建**（§11 M4）；执行层在 `me-app`，见 §2.2 的例外说明。三条约束先写死：

| 约束 | 内容 |
| --- | --- |
| 不可重放 | `music_play` / `music_control` 会改变真实播放状态（出声、换歌），`is_replay_safe() = false`；「重新生成」不下发，否则会把歌再切一遍 |
| 单一出口 | app 只回 `{ ok, 曲目 id, 位置, 是否在播 }` 这类结构化字段，**摘要文本由 `me-sync` 生成**，仍走 `MAX_TOOL_RESULT_CHARS` |
| 必须有超时 | 音频线程可能没设备、目录为空、文件损坏；3 秒内 `AudioState` 未到达目标状态即返回可读错误（「音频设备不可用」「媒体库为空」），不能让整轮对话挂着 |

#### 任务清单模板

| 需求类型 | 步骤模板 |
| --- | --- |
| 「放首歌」 | 解析歌名 → `music_search` → 唯一命中则播 / 多命中则列候选 → 回报当前曲目 |
| 「随便放点」 | 读 `music_state`（有没有队列）→ 确保有队列 → `music_play`（mode=queue）→ 回报 |
| 「换下一首」 | `music_state` 确认在播 → `music_control(next)` → 回报新曲目 |
| 「静音/停下」 | `music_control(pause/stop)` → 回报 |

#### 明确不做

- 不做在线音乐/流媒体（没有网络音源）；
- 不在没有媒体库时静默失败：必须回「还没选音乐目录」。

### 3.5 记忆（横切，不是用户能力）

`memory_upsert` 继续存在，但它不属于上面四个模块：它没有卡片、不产生用户可见的动作，
只影响「下次请求带哪些实体」。模块化后它的位置是**横切能力**：
`motive` 同样必填，`memory` 开关关掉时既不写也不自动登记（已实现）。

**它在权限模型里的位置要说清**（否则会和 §7.1 的「模块级开关」打架）：

| 项 | 结论 |
| --- | --- |
| 开关归属 | 不属于 mail/weather/calendar/music 任一个，而是与四个模块**并列的第五个横切开关**；设置页按「四个模块 + 记忆」一行一个，视觉上不混 |
| 作用面 | 同时控制两件事：模型能否调 `memory_upsert`，以及工具结果能否**自动登记**实体（`register_location_entity` / `register_event_entity`，已实现） |
| 关掉之后 | 已存在的实体不删（那是用户的资料），只是不再新增/合并 |

**一个与上限相关的副作用（当前代码就是这样，需要在落地时决定）：**

`ai_entities` 的总量上限是 200，而 `event` 类型会在每次 `calendar_create` 成功后被自动登记
（`ai_tools.rs:691`）。也就是说：**AI 每建一条日程，就消耗一条「记忆」额度**，而且这些
日程实体永远留在库里（没有 TTL、没有清理入口）。用一段时间后 `memory_upsert` 会开始报
「记忆已满（200 条）」，用户看到的是「AI 记不住事了」，真实原因却是它记了太多日程。

处置建议（落地时二选一，见 [落地方案](AI模块落地方案.md) 的 T7）：

1. `event` 实体不计入用户可见的 200 条上限（给 `ai_entities` 加 `kind` 维度的配额）；或
2. `event` 实体加 30 天 TTL，读取时过滤、后台清理。

## 4. 任务清单（Plan）

### 4.0 从需求到清单：理解三问

模型在动手之前先回答三个问题，答案直接决定 `goal` 与 `steps`：

| 三问 | 输出 | 答不上来怎么办 |
| --- | --- | --- |
| 用户要的**成果**是什么（一句话，可验收） | `goal` | 复述一遍自己的理解，向用户确认 |
| 需要**哪几个模块** | `steps[].capability` | 只列已开启的模块；缺模块就直说「需要先开启日历」 |
| 现在**缺什么**才能开始 | 缺参数 / 不缺 | 缺参数（「哪一周」「哪个城市」「删哪条」）→ 先回问，**不建清单** |

两条与「理解」有关的硬规则：

1. **破坏性动作先对齐对象**：改/删的第一条步骤必须是「列出候选并确认是哪一条」，不允许
   模型凭标题相似度直接选一条删。
2. **理解偏差要显式化**：`goal` 是给用户看的，写错比做错更容易被发现；后续任何一步跑偏，
   用户都能在清单上看到是从哪一步开始偏的。

### 4.1 计划对象

**清单怎么产出、怎么更新：走工具，不走正文。** 这一条必须先定，否则整个 §4 无法实现。

现有流式只有两种增量：`text delta` 与 `tool_call delta`。如果让模型在正文里嵌一段 JSON，
流一结束就再也改不了（步骤状态永远停在初始值），也无法在服务端校验、无法阻止它把 JSON
漏进用户看到的正文。所以清单由**一个固定工具**维护：

| 工具 | 入参 | 语义 |
| --- | --- | --- |
| `plan_update` | `goal` 或 `steps[]`（`id` / `capability` / `title` / `status` / `evidence`） | **全量替换**当前清单；幂等 |

校验规则（`me-sync` 侧，违规整条拒绝并回 `is_error`，清单不变）：

- 步骤 1–6 条；`capability` ∈ {mail, weather, calendar, music}；
- `id` 与 `title` 创建后**不可变**（只能改 `status` / `evidence`），防止模型边做边改目标；
- `status` 只能前进：`pending → running → done | failed | skipped`，不允许回退；
- 首次调用必须带 `goal`；后续调用可只带被改动的步骤。

`plan_update` **不计入** `MAX_TOOL_CALLS`（否则清单本身要吃掉两三成预算），但计入轮次与 trace。

落库形态（模型的入参是它的子集：`plan_id` 与两个时间戳由引擎填）：

```json
{
  "plan_id": "p_20261105_1",
  "goal": "找出本周张三发的报价单，并确认周五开会时间",
  "steps": [
    {
      "id": 1,
      "capability": "mail",
      "title": "检索张三本周邮件，关键词「报价单」",
      "status": "done",
      "evidence": "命中 2 封，最新一封 11-04 10:12"
    },
    {
      "id": 2,
      "capability": "calendar",
      "title": "查周五 15:00 是否已有日程",
      "status": "running",
      "evidence": null
    }
  ],
  "created_at": 1762345678,
  "updated_at": 1762345701
}
```

| 字段 | 约束 |
| --- | --- |
| `goal` | 一句话复述用户目标，≤120 字；用于 UI 顶部与失败时解释 |
| `steps` | 1–6 步；超过 6 步说明需求太大，先做前 6 步并在 `[结果]` 说明 |
| `capability` | 必须是 `mail` / `weather` / `calendar` / `music` 之一 |
| `title` | 动词开头，≤40 字；禁止「处理一下」「等等」这类空步骤 |
| `status` | `pending` / `running` / `done` / `failed` / `skipped` |
| `evidence` | 该步完成时的**一句回执**（拿到了什么、命中几条、改了什么），≤120 字 |
| `plan_id` / `created_at` / `updated_at` | **引擎生成**，模型不传；`plan_id` 用于跨轮引用同一个清单 |

`evidence` 的默认来源是执行该步的工具 `trace.summary`（截断到 120 字），模型可以改写得更像人话，
但不能与 trace 矛盾——这是「回执」能被核对的底线。

### 4.2 什么时候建清单

| 情形 | 处理 |
| --- | --- |
| 单一动作（找一封邮件、查一个城市天气、放一首歌） | **不建清单**，直接执行；避免给用户「五步操作」的错觉 |
| 两步及以上，或跨模块 | 建清单 |
| 需求含糊、缺关键参数 | **不建清单**，先回问（「哪一周？」「哪个城市？」） |
| 纯闲聊 / 知识问答 | 不建清单，也不产生 `[结果]` |

判断标准写进系统提示（待建），不靠 UI 兜底。

### 4.3 状态机

```text
            ┌──────── 用户确认/补充 ────────┐
            ▼                              │
  pending ──► running ──► done             │
                │  │                       │
                │  └──► failed ──► skipped（后续依赖它的步骤）
                │
                └──► pending（重规划：拆成更小的步骤）
```

规则：

1. **一项一步**：一步可以调多个工具（例如检索后读正文），但只对应一个用户可理解的成果。
2. **不删历史**：重规划只能追加/拆分步骤，已完成的步骤保留（用户要看到「做到哪了」）。
3. **失败不静默**：某步失败 → 标注原因 → 能独立完成的后续步骤继续 → `[结果]` 里单独列出。
4. **一步一确认（仅删除）**：`calendar_delete` 立即返回 `pending_confirmation` 并结束本轮，
   该步停在 `running`（UI 显示「等待确认」）。用户点确认后由 **UI 直接发 `Command::DeleteCalendarEvent`**
   （不重跑模型），删完以系统消息回灌，该步转 `done`；用户取消则转 `skipped`。
   这一条是整个设计里唯一「模型之外的人也能推进清单」的入口，必须写死，否则清单会永远卡住。

### 4.4 UI 呈现

- 位置：AI 页消息流顶部（当前轮），可折叠；默认展开未完成部分。
- 形态：`①②③` + 状态图标（○ 待做 / ◐ 进行中 / ● 完成 / ✕ 失败）+ 一行标题 + 回执。
- 完成后折叠为「已完成 4 步 · 1 步未完成」，点击展开。
- **不显示**模型内部思考，只显示步骤与回执。

### 4.5 预算与持久化

| 项 | 值 |
| --- | --- |
| 清单步数 | ≤6 |
| 每步工具调用 | 计入总次数（目标 `MAX_TOOL_CALLS = 12`）；`plan_update` 不计 |
| 整个计划 | 受 `MAX_TOOL_ROUNDS` 限制（目标 6）；一次轮次内可以连续推进多个步骤 |
| 持久化 | **`ai_messages.plan`（JSON 列，schema v5）**——清单是「某条回复的过程快照」，读完即用，不需要跨会话查询；独立表留到有统计需求时再说 |

**先算一遍账，再定 6 / 12 够不够**（每格是工具调用次数，`plan_update` 不计）：

| 典型需求 | 调用 | 备注 |
| --- | --- | --- |
| 找一封邮件 | 1–2 | 检索；必要时 `mail_read` |
| 总结某封邮件 | 2 | 检索 + 读正文 |
| 建一条带冲突检查的日程 | 2 | `calendar_list` + `calendar_create` |
| 改日程 | 2–3 | 定位 + 改（定位可能要多查一次） |
| 删日程 | 2 + 1 | 定位 + `calendar_delete`；确认那条走 UI，不计入 |
| 邮件 + 天气 + 建日程 | 4–5 | 三模块各 1–2 |
| 放一首指定的歌 | 2 | `music_search` + `music_play` |

结论：12 次覆盖「三模块单步」有余，但**覆盖不了**「五个步骤每步都要读正文」。所以清单超过
4 步时，系统提示要求模型优先用一次检索批量拿信息，而不是逐步深挖。

> 现实提醒：4 轮 8 次是 v0.3 为「单工具问答」定的。清单化之后预算不够是**结构性**的，
> §11 把「提高轮次」放在 M2 的第一步，而不是先做清单再撞墙。

## 5. 工具调用协议：动机与结果

### 5.1 固定参数 `motive`（动机）

**所有能力工具**（含 `memory_upsert`）的 JSON Schema 增加一个**必填**字段，且排在属性第一位：

```json
{
  "type": "object",
  "properties": {
    "motive": {
      "type": "string",
      "minLength": 4,
      "maxLength": 200,
      "description": "为什么现在调用它：用户目标 + 当前步骤编号。例：用户要本周报价单，执行第 1 步检索"
    },
    "query": { "...": "..." }
  },
  "required": ["motive", "query"],
  "additionalProperties": false
}
```

> 示例只示意 `motive` 的位置与必填性；`required` 里除 `motive` 之外的项由各工具自己定。

| 规则 | 内容 |
| --- | --- |
| 缺失/空白 | **补默认动机后继续执行**，不拒绝：`motive` 置为「（模型未说明动机）」并记 `motive_source = default`，UI 照常显示但标记为推断 |
| 长度 | 4–200 字符；超出截断而不是报错（模型偶尔啰嗦） |
| 内容 | 应当回答「为了用户的哪个目标、在第几步」；禁止空话（「调用工具」） |
| 落点 | 写进 `AiToolTrace.motive`（JSON，不需要 schema 迁移）；**不进 `tracing` 日志** |
| UI | 活动条每条显示「动机：…」，用户能看懂 AI 在干什么 |

示例（好 / 坏）：

```text
好：用户要确认周五是否已有会议，先查 11-06 的日程（第 2 步）
坏：查询日历
```

> **为什么不「拒绝执行、让模型补一次」**：协议里没有「重试同一个 tool_call」这种东西。
> 模型补动机必须**发一个新的 tool_use**（新 `call_id`），于是
> ① 吃掉 1 次 `MAX_TOOL_CALLS`（8 次预算的 12.5%）；② `tool_trace` 里留下「一错一对」
> 两条记录；③ 部分模型会连续两次漏写，直接把预算打空。而 `motive` 是给人看的说明，
> 不是安全边界——安全边界是权限与白名单。所以缺失时降级执行，把「模型没说」如实标出来，
> 比拒绝更划算。

### 5.2 调用结束后：先理解，再继续

工具结果回灌后，模型**必须**先产出一句「这一步拿到了什么」，才允许：

- 继续下一步；或
- 重规划；或
- 收尾并给 `[结果]`。

系统提示里的硬规则（待建）：

```text
每次工具返回后，先用一句话说明这次调用的结果（命中/未命中、成功/失败、关键字段），
再决定下一步。不要假设调用成功；不要在没看到结果时编造内容。
失败时说明原因与是否可以重试，不要重复同样的调用超过一次。
```

可判定性：一次工具调用后如果模型直接结束且没有 `[结果]`，视为不合规。**处理方式是渲染层兜底，
不是重发请求**——重发要再付一次完整调用（token + 延迟），而用户已经看到正文了。兜底形态见 §5.3。

### 5.3 固定段落 `[结果]`

**触发条件**：本轮**调用过至少一个能力工具**，回复必须以 `[结果]` 收尾。
纯闲聊、纯知识问答不强制（否则每句话都要挂个表）。

固定格式（字段名固定，值自由）：

```text
[结果]
状态：已完成 | 部分完成 | 未完成
做了什么：<1–3 条，动词开头，与任务清单的步骤对应>
关键信息：<用户最需要的事实：谁/什么时候/多少；没有就写「无」>
未完成：<没做到的步骤 + 原因 + 建议；没有就写「无」>
```

| 规则 | 内容 |
| --- | --- |
| 位置 | 回复**最后**一段，前面是正常叙述 |
| 状态判定 | 全部步骤 done → 已完成；有 failed/skipped 但有可用产出 → 部分完成；无产出 → 未完成 |
| 事实约束 | 「做了什么」只能写真正执行过的工具对应的动作；不得写「已发送邮件」这类没有路径的事 |
| 长度 | ≤400 字 |
| 渲染 | 正文段落走现有 Markdown；只在消息渲染里加一个分支：识别首行 `[结果]`，把它画成小标题，下面四行按原样保留。是**一处**渲染分支，不是新渲染器 |
| 兜底 | 模型漏写时，UI 用本轮工具 trace 生成「已执行 N 次工具调用」的降级块（流式期间来自 `AiToolCompleted`，落库后来自 `tool_trace`）；**不重发请求**（见 §5.2） |

示例：

```text
本周张三共发来 2 封带「报价单」的邮件，最新一封是 11-04 10:12（未读），
已在上方卡片列出；周五 15:00 目前没有日程，需要我建一条吗？

[结果]
状态：部分完成
做了什么：检索了本周张三的邮件；查了 11-06 的日程
关键信息：2 封命中，报价单在最新一封里；周五 15:00 空闲
未完成：还没有创建日程 —— 等你确认时间与标题
```

### 5.4 与现有 `tool_trace` 的关系

| 字段 | 现状 | 目标 |
| --- | --- | --- |
| `call_id` / `tool` / `status` / `summary` / `duration_ms` | 已实现 | 不变 |
| `motive` | — | 待建：新增，`Option<String>` + `#[serde(default)]` |
| `motive_source` | — | 待建：`model` / `default`，用来区分「模型真说了」和「引擎补的」 |
| 参数原文 | 不存 | 不存（`motive` 是唯一例外：它是给人看的说明，不是原始参数） |

存储形态已经具备：`ai_messages.tool_trace` 是 `TEXT` 存 JSON（`me-store/src/migrations.rs:290`），
所以加字段**不需要 schema 迁移**；代价只有一个——旧行必须能反序列化成带 `None` 的新结构，
这就是 `#[serde(default)]` 的作用，漏了会让历史消息整条读不出来（和 §7.1 的档案问题是同一类）。

## 6. 卡片契约

### 6.1 邮件卡片 = 详情弹窗（同构）

**原则**：一份实现，两个入口。列表点开、AI 卡片点开，走的是**同一个** `views::reader`
（当前是 `egui::Window::new("阅读邮件")`），因此正文渲染、附件区、引用按钮、图片加载
全都一致——不存在「卡片里看到的内容和详情里不一样」。

| 项 | 设计 |
| --- | --- |
| 卡片首屏 | 主题 / 发件人 / 时间 / 文件夹 / 附件标记 / 摘要片段（≤120 字）/ **命中理由**（来自 `motive` 与检索条件） |
| 点开 | 打开同一个「阅读邮件」窗口；目标是**在 AI 页原地弹出**（待建，要改两处，见下） |
| 卡片数据 | 只带 `message_id` + 标题 + 命中理由；正文由 UI 只读仓储按需取 |
| 数量 | 一次最多展示 5 张；其余折叠为「还有 N 封，去列表看」 |
| 预览副作用 | **不标已读**（现状已如此）；只有点开详情才走 `OpenMessage` |
| 卡片动作 | 打开 / 引用到 AI 对话 / 回复（回复走现有撰写页） |

**「原地弹出」的真实障碍（不是少切一次页，别按一行改动估时）：**

1. `app.rs:1504` 的渲染条件是 `page == Page::Mail && selected_message.is_some()` —— 只要停在
   AI 页，阅读窗**根本不会被绘制**。不要直接把条件放宽成「有 `selected_message` 就画」：
   `switch_page` 并不清 `selected_message`，那样会让阅读窗跟着用户跳到每个页面。
   正确做法是加一个独立的 `reader_open` 开关，邮件列表与卡片都置它，`show_window` 只看它。
2. `reader::show_window` 第一件事是在 `state.messages` 里按 id 找摘要，找不到就
   `selected_message = None` **静默关窗**（`reader.rs:24-28`）。AI 检索命中的邮件不一定在当前
   列表页里，所以卡片必须自带一份摘要（或在打开前先 `get_message_readonly` 塞进 `state.messages`）。
3. 现状 `show_cards` 的做法是「切页 + `Command::OpenMessage`」（`views/ai.rs:687`），
   第三条动作可以保留作为兜底。

这三条决定 M3 那一项是「半天」还是「两天」。

事件形态（待建，在现有 `AiToolEmailResults` 上扩展）：

```rust
Event::AiMailCards {
    conversation,
    call_id,
    cards: Vec<MailCardRef>,   // { message: MessageId, reason: String }
    total: u32,
}
```

| --- | --- | --- |

## 7. 权限模型

### 7.1 两级

```text
模块级开关（用户可关）：mail / weather / calendar / music / memory
        │
        └── 动作级白名单（代码固定，用户不可改）：
              mail: read_search, read_body
              weather: read
              calendar: read, create, update, delete(confirm)
              music: play, control
```

| 项 | 设计 |
| --- | --- |
| 归属 | 每个模型档案一份（沿用 `AiModel.tools`，待建：按动作扩列、扁平布尔；模块级开关由动作开关推导） |
| 记忆 | 横切开关，与四个模块并列但不属于任一模块（§3.5）；同时管 `memory_upsert` 与工具结果自动登记 |
| 默认 | 全开（与现在一致：默认关掉会让用户以为 AI 什么都不会） |
| 请求期 | 未开的模块不下发工具 |
| 执行期 | 再校验一次；未下发却被调用 → 拒绝且无副作用（已实现） |
| 删除 | 永远需要用户确认，**即使模块开关是开的** |
| 审计 | 每次调用记 `motive`；删除类额外记「谁确认的」 |
| 存储形态 | `meta.ai_models` 一列 JSON（`settings_key::AI_MODELS`），无独立表 |

**扩权限结构 = 改持久化格式，必须按迁移对待。** 现在这条路径有一个静默陷阱：

```rust
// me-sync/src/ai.rs:238
let mut models: Vec<AiModel> = loaded.models.as_deref()
    .and_then(|raw| serde_json::from_str(raw).ok())   // 解析失败 → None
    .unwrap_or_default();                             // → 空数组
// 紧接着 if models.is_empty() { …回落到默认 Anthropic 档案… }
```

而 `AiToolPermissions`（`me-core/src/ai.rs:1106`）四个字段**没有任何 `serde(default)`**。
所以只要新增一个必填字段，老 JSON 就解析失败 → 整个档案数组变空 → 用户看到的是「我的模型没了」，
而且没有任何报错。落地时必须同时做三件事：

1. 新字段全部 `#[serde(default)]`，结构体本身也加 `#[serde(default)]`，并且 `Default` 保持「全开」；
2. **键名不改**（`email_search` / `weather` / `calendar_create` / `memory` 原样保留），
   新增的是 `mail_read` / `calendar_read` / `calendar_update` / `calendar_delete` / `music` ——
   不做改名映射，就不会有「旧键认不出来」的问题；
3. **改掉上面的 `ok().unwrap_or_default()`**：解析失败要报错并保留原值，绝不能静默回落默认——
   否则「用户关掉的工具」会在升级后被默认值重新打开，这是权限模型上的实质漏洞。

### 7.2 哪些权限永远不给

| 永远不给 | 理由 |
| --- | --- |
| 发邮件 / 存草稿 | 外发不可撤回，且草稿有双向同步 |
| 删除 / 移动 / 标记邮件 | 邮件是用户资产，本地删了服务器还在，状态会乱 |
| 读附件内容 | 体积与隐私风险都不划算 |
| 删改日历容器 | 会把事件一起带走 |
| 操作音乐文件 | 播放器只该播，不该写盘 |

## 8. 执行引擎

### 8.1 循环（在现有基础上加清单）

现有循环在 `me-sync/src/ai.rs:1101`（`'rounds: for _round in 0..MAX_TOOL_ROUNDS`）。
清单化只需要动三个点，不需要重写：

```text
run_ai_stream:
  plan = None
  for round in 0..MAX_ROUNDS（待建：6）:          // 现 :1101
      turn = provider.stream_chat(...)
      if turn.tool_calls.is_empty():              // 现 :1147
          若 plan 有 pending/running 步骤 → 追加一句系统提醒，继续下一轮
          否则 break
      for call in turn.tool_calls:                // 现 :1152
          校验：权限 → 参数 → 配额              // 动机缺失时补默认值（§5.1），不拒绝
          if call.name == plan_update:
              校验并落清单状态（无副作用，也不占 MAX_TOOL_CALLS）
          else:
              执行（mail/weather/calendar 在 me-sync；music 走 §8.3 的跨层回填）
              把该步 status 置 done/failed，evidence 取 trace.summary（截断 120 字）
          回灌工具结果
  收尾：落库（文本 / plan / trace / 用量）        // 现 :1203 之后
```

两个细节决定成败：

1. **步骤与调用的对应关系不能靠猜**。`plan_update` 的 `steps[].id` 与工具调用的关联必须由
   模型在参数里点明（这也是 `motive` 里要写「第 N 步」的原因）。引擎不做「按顺序对齐」的推断——
   一次调用可能服务两步，也可能两步共用一次检索。
2. **空 `tool_calls` 不等于结束**。现在 :1147 直接 `break`，清单化后要继续，否则模型会在第一步
   之后停下来等用户催。追加的提醒必须走**同一条** `request.messages`，不能另开一次请求。

### 8.2 预算

| 项 | 现值 | 目标 |
| --- | --- | --- |
| 模型轮次 | 4 | 6（待建，清单化后不够用） |
| 工具次数 | 8 | 12（待建） |
| 单工具超时 | 2s / 20s / 5s / 5s | 不变；音乐另定 3s（待建） |
| 总时长 | 240s | 300s（待建） |
| 并发 | 全局 2 / 单会话 1 | 不变 |

### 8.3 音乐执行器的接线（待建）

```text
me-sync 工具循环拿到 music_* 调用
   → 在 pending: HashMap<call_id, oneshot::Sender<MusicOutcome>> 里登记
   → 发 Event::AiMusicCommand { conversation, call_id, op }
   → me-app 收到后调用 AudioPlayer::send(AudioCommand)
   → 等 AudioState 达到目标状态（3s 超时）
   → 发 Command::AiMusicResult { call_id, outcome }（结构化字段，不含文案）
   → me-sync 从 pending 取出 sender，生成摘要文本，回灌给模型
```

| 必须处理 | 做法 |
| --- | --- |
| 超时 | `tokio::time::timeout(3s)` 包住 oneshot；超时返回「音频设备无响应」，并从 pending 里移除 |
| 取消 | 循环内 `select!` 同时等 `token.cancelled()`；取消时移除 pending，**迟到的结果丢弃**（避免取消后还回灌一条成功） |
| 泄漏 | 会话结束/消息落库时清空该 `conversation` 的所有 pending 条目 |
| 摘要来源 | app 只回 `{ ok, track_id, title, position_ms, playing, error_kind }`；文案在 me-sync 生成，仍走 `MAX_TOOL_RESULT_CHARS` |
| 不可重放 | `music_play` / `music_control` 计入 `is_replay_safe() = false`，重新生成不下发 |

要点：**超时必须有**（音频线程可能没设备、目录为空）；失败要能被模型解释
（「没有媒体库」「设备不可用」），而不是让整轮对话卡住。

### 8.4 取消与落库

- 取消：当前步标 `skipped`（不是 failed），已执行工具的 trace 照常保留；
- 落库：流式期间只写内存，终止一次性写（文本 / plan / traces / 用量）；
- 崩溃：`streaming` 占位行启动时标 `failed`，其 plan 一并标 `未完成`。

## 11. 落地路线

按「先让契约成立，再扩能力」排序，每阶段都能独立验收。

### M0 修一个已有陷阱（不动任何新功能）

1. 改掉 `me-sync/src/ai.rs:238` 的 `from_str(...).ok().unwrap_or_default()`：解析失败要报错、
   保留原值，不能静默回落默认档案。
2. 给 `AiModel` / `AiToolPermissions` 的字段补 `#[serde(default)]`。

为什么排在最前：它不是新功能，但它决定「后面所有改权限结构的操作会不会清空用户档案」。
先修，后面每一步都能安全试。

### M1 契约层（不改表结构）

1. `TOOL_SPECS` 全部工具加 `motive`（必填）+ 缺失时补默认值（**不拒绝**）+ `AiToolTrace.motive` / `motive_source`。
2. 系统提示加入三条规则：先复述工具结果、`[结果]` 格式、清单判定标准。
3. UI：活动条显示动机（`show_activity`，`views/ai.rs:645`）；回复尾部识别 `[结果]` 并加样式。
4. 验收：任何一次工具调用都能在活动条看到「为什么」；漏动机的调用**照常成功**，但标为「模型未说明动机」。

### M2 清单层（schema v5）

1. 新增 `plan_update` 工具（含 §4.1 的全部校验）；它不计入 `MAX_TOOL_CALLS`。
2. `ai_messages.plan`（JSON 列）+ 迁移 v4 → v5（`migrations.rs` 追加 `migrate_v4_to_v5`，
   并把 `me-core/src/lib.rs:71` 的 `SCHEMA_VERSION` 提到 5）。
3. 轮次/次数上限提到 6 / 12；总时长 300s。
4. UI 任务清单条（折叠/展开、状态图标、一步一回执）。
5. 验收：跨模块需求（邮件 + 日历）能跑完并逐步显示；清单中途失败时后续步骤标 `skipped` 而不是整轮失败。

### M3 能力补齐

1. 权限结构：`AiToolPermissions` 按动作扩列（扁平布尔 + `serde(default)`，键名不变），模块级开关由动作开关推导（§7.1）。
2. 邮件：`mail_read`（去重 / 预算 / 未缓存三条硬规则，§3.1）；卡片原地弹出 + 命中理由 + 条数上限。
3. 日历：`calendar_list` / `calendar_update` / `calendar_delete`（复用现成用例），
   删除确认由 UI 直发 `Command::DeleteCalendarEvent`；删除后给 10 秒撤销（需补 store 的
   `restore_event`——现在只有软删、没有恢复路径）。
4. 天气：`weather_locations`；天气卡。
5. 系统提示：删掉第 6 条里「修改/删除已有日程」的禁令，改为「改删走确认」。
6. 验收：四个模块的单模块任务全部走通；关掉某模块后模型既看不到也用不了该模块工具。

### M4 音乐模块

1. `music_search` / `music_play` / `music_control` / `music_state`。
