## 0. 这份文档解决什么问题

v0.3 结束时，v0.4 的候选散在三处：架构文档 §1.3 的「明确不做」清单、§9.2 的 15 条未决事项（O11–O25）、收尾报告 §9 的 7 条建议。三处各自成立，但**没有排序、没有成本估算、也没有说明为什么**。

本文做三件事：

1. **收拢**——把三处候选合并成一份清单（§8 总表），消除遗漏与重复；
2. **补缺**——补上代码盘点里发现、但三处都没登记的缺口（§3、§4、§5）；
3. **排序**——按「实现成本 × 用户收益」给出建议顺序（§1），并说明每条的**落点与约束**（不是只有想法）。

**核心判断**：v0.3 的问题不是功能少，是**结构偏了**——四个新页（日历 / 天气 / AI / 音乐）都是加分项，但产品名叫 MyEmail，邮件主线本身还有几处基本盘缺口没补。v0.4 建议**先回补主线、再兑现"本地全量"这个真正独有的优势**，而不是继续加第五个功能页。

## 2. 现状盘点（代码事实）

盘点时间 2026-11-06，依据 `master` 工作区。下表每一行都可在文中给出的位置复核。

> **未读标志位的口径**：`messages.flags` 的 bit 0 是 IMAP 的 `\Seen`——`(flags & 1) = 1` 表示**已读**，`= 0` 表示未读。所以「只要未读」的条件是 `(m.flags & 1) = 0`（见 `me-store/src/search.rs:166`），不是 `flags & 1` 非零。写规则条件与查询语法时别把这个位取反了。

| 能力 | 现状 | 证据 |
| --- | --- | --- |
| 跨账户统一视图 | **无**。侧栏是「账户 → 文件夹」树，切换账户即切换整棵文件夹树；全仓搜不到聚合视图 | `views/mailbox.rs`、`views/mod.rs` |
| 搜索的结构化能力 | **后端已有，UI 未暴露**。`SearchQuery` 已有 `accounts` / `folders` / `from` / `to` / `subject` / `has_attachment` / `since` / `until` / `unread_only`，注释明写「AI 的 `email_search` 用它……**UI 搜索框留空**」 | `me-core/src/model.rs:1020`、`me-core/src/port.rs:648` |
| 会话线程 | **无**。`messages` 表有 `message_id`，但没有 `in_reply_to` / `references`，列表按单封平铺 | `me-store/src/migrations.rs:56` |
| 联系人 / 收件人补全 | **无**。全仓无 `contact` / `autocomplete` 相关代码；撰写页是三个裸 `TextEdit` | `me-app/src/views/compose.rs:304-321` |
| 批量多选 | **无**。列表选择态是单值 `selected_message: Option<MessageId>` | `me-app/src/state.rs:202` |
| 规则 / 过滤器 | **无**。仓库里的 `filter` 命中全是 egui 的控件过滤与 HTML 解析器，不存在邮件规则 | 全仓检索确认 |
| 附件预览 | **无**。仅「另存为」；正文里的图片走的是阅读页渲染链路，与附件列表不是一回事 | `me-app/src/views/reader.rs` |
| 系统通知 / 托盘 | **无**。提醒只有应用内 toast；`Notifier` 端口**尚未定义**（全仓无该符号，C9 需连 trait 一起建） | `me-core/src/port.rs`（无对应 trait） |
| 本地库加密 | **无**。SQLite 明文 | `me-store/src/db.rs` |

> **盘点中最有价值的一条**：C4（查询语法）不是「新建能力」，而是**把已经写好、只对 AI 开放的能力开放给用户**。`SearchQuery` 的字段与 `SearchRepo::search` 的 SQL 都已经支持多条件取交集（`query` 走 FTS 短语，`from`/`to`/`subject` 走 `LIKE`，`unread_only` 走 `(m.flags & 1) = 0`），AI 侧已在用。UI 侧缺的只是一个语法解析器和一个输入入口。**这让 C4 从「中等成本」降级为「低成本」**——本文的排序据此调整。

## 3. 第一梯队：回补邮件主线

### C1 统一收件箱（跨账户聚合）

**为什么排第一**：README 第一句写「多账户统一收发」，但实际体验是「切账户看各自文件夹」——这是产品定位与实现之间的明摆着的缺口，不是新功能，是**兑现已有承诺**。

**落点**：

- `folders` 表的 `role` 有 CHECK 约束（`'inbox','sent','drafts','trash','junk','archive','other'`）且 `account_id NOT NULL`（`migrations.rs:42`），所以**统一收件箱不能落库成一张文件夹行**，必须是视图层的虚拟项；
- `ReadOnlyRepo::list_messages_readonly(folder, cursor, limit)` 是**按 folder** 的（`port.rs:666`），需要新增一个跨账户的键集分页方法，或把 `folder` 放宽为 `Option<FolderId>`；
- **`me-app` 不得全表扫**：`CLAUDE.md` 的硬规则是 UI 只拿 `ReadOnlyRepo`、单次 `LIMIT ≤ 200`、禁全表扫描与 FTS。跨账户聚合必须**在 store 层一次查完**，不能由 UI 拉完各账户再本地合并（那样既要多次往返，又破坏键集分页）。

**待定**：是否也做「统一已发送」「统一草稿」；虚拟项在侧栏的位置；聚合排序是纯按 `date` 还是按账户优先级。

**成本**：中低。**收益**：高——它是"多账户"这件事从功能变成体验的分界线。

---

### C2 联系人自动补全

**为什么排第二**：投入产出比最高的一项。**不需要用户做任何事**——从 `messages.from_addr` / `to_addrs` 自动累积，写信与收信时 UPSERT 计数，撰写页输入时下拉。用户第一次用就会觉得"这软件知道我在跟谁通信"。

**落点**：

- 新增 `contacts` 表（`addr` 唯一、`display_name`、`last_seen`、`seen_count`）；
- 累积时机：正文补全落库时（`me-sync` 的 indexer 路径）与发信成功归档时，**不在 UI 线程做**；
- 撰写页：现有 `TextEdit::singleline` 换成带下拉的输入（前缀匹配 + 命中排序：最近联系 > 姓名包含 > 邮箱前缀）；
- 隐私边界：地址簿是**本地派生数据**，不进 `ClearCache` 的清理范围时要说清（建议不清理，与 D30 一致——`ClearCache` 不删日历/天气/AI 数据，联系人同理）；但**导出时必须用户主动触发**。

**待定**：是否允许用户手动编辑联系人；是否只保留出现过的地址（默认是）。

**成本**：低。**收益**：中高（感知强、粘性高）。

---

### C3 批量多选操作

**为什么需要**：现在清理一个装了 500 封的收件箱，只能一封一封点。**这是邮件客户端的基本盘**，缺了会让日常使用很别扭。

**落点**：

- `UiState` 增加 `selected: HashSet<MessageId>`，与既有单选 `selected_message` **并存**（单选点击保留，`Ctrl/Shift` 点击进多选，全选用快捷键）；
- **关键约束**：批量必须是一个 `Command` 带 `Vec<MessageId>`，**一次事务、一次网络往返**。不要做成 N 次单封命令串行——`pending_flags` 本来就支持 UPSERT 合并，天然适合批量；
- 批量动作最小集：标记已读/未读、加星、移动到文件夹、删除（移入废件箱）。批量移动同样走 `pending_ops`；
- 破坏性动作（批量删除）要沿用现有的确认卡模式（AI 页已有 `pending_delete` 的先例）。

**待定**：跨文件夹选择是否支持（建议不支持）；批量上限（建议单次 ≤ 500）。

**成本**：低。**收益**：中高。

---

### C4 查询语法（把已有后端能力开放给用户）

**核心价值**：后端**已经支持**（§2），这是纯前端 + 解析层的工作。

**建议语法**（六个，覆盖绝大多数场景）：

| 写法 | 语义 | 对应 `SearchQuery` 字段 |
| --- | --- | --- |
| `from:zhang` | 发件人包含 | `from` |
| `to:li` | 收件人包含 | `to` |
| `subject:发票` | 主题包含 | `subject` |
| `has:attachment` / `has:none` | 有/无附件 | `has_attachment` |
| `before:2026-01-01` / `after:2026-01-01` | 日期区间 | `until` / `since` |
| `is:unread` | 仅未读 | `unread_only` |

**落点**：

- 解析器放 `me-core`（**纯函数，最好测**——`me-core/src/search_query.rs` 之类，输入一段查询串输出 `SearchQuery` 的可选字段）；
- UI 搜索框直接接受语法，或另开一个「高级搜索」弹窗填字段（建议**两者都要**：搜索框支持速记，弹窗提供可点选的条件构造）；
- **必须能回填**：解析出的条件要显示在搜索框上方的条件条里，用户能看见"我搜的到底是什么"（类似 Gmail 的 chips），并能单独删掉某个条件；
- **顺带收益**：AI 的 `email_search` 工具可以复用同一个解析器，让 AI 也能用 `from:` 语法；
- 与 FTS 的关系不变：≥3 字走 FTS5 trigram，1–2 字仅头部 `LIKE`——语法只影响过滤条件，不改变分词规则。

**待定**：语法解析失败时的反馈方式（建议 inline 提示 + 保留已解析部分）；是否支持 `OR`（建议 v0.4 不做）。

**成本**：低。**收益**：中高（这是把 AI 已有的能力交给用户的最短路径）。

## 4. 第二梯队：把「本地全量」变成用户能感知的能力

### C5 本地规则引擎（唯一建议主动做的新功能）

**为什么单独一节**：它不是"Gmail 有所以我也要有"，而是**你有别人没有的东西——本地全量缓存**。

**服务端过滤器的三个天生限制**：

1. 要联网才能配，配置体验割裂；
2. 受服务商能力约束（Gmail 的过滤器与 Outlook 的规则是两套不同的语义）；
3. **不能对历史邮件回溯执行**——只对到达之后的邮件生效。

**本地规则引擎的三个结构性优势**：

1. 同步落库后立即判定，**离线照样生效**；
2. 可以对已有的全部历史邮件**补跑**一遍——这是服务端架构上做不到的；
3. 语义由自己定义，不受任何服务商的限制。

**建议的最小动作集**（只做四个，先不扩张）：

| 动作 | 说明 | 为什么安全 |
| --- | --- | --- |
| 加/去标签 | 自定义标签，落在本地 `messages.flags` 或独立标签表 | 纯本地、可撤销 |
| 移动到文件夹 | 落到既有的 `folders` + `pending_ops` 机制 | 复用已验证的删除/移动路径 |
| 标记已读 | 走 `pending_flags` UPSERT | 复用既有标志位机制 |
| **不通知** | 命中规则的邮件默认不弹提醒 | 唯一的"副作用"，且是"少打扰"方向 |

**明确不做**（动作有不可逆副作用）：转发、自动回复、自动删除、外发。

**条件维度**（第一版）：发件人、收件人、主题包含、正文包含、有无附件、日期区间、大小。全部可在**不联网**的情况下判定——因为正文已在本地。

**与 AI 的结合**（这是这条功能真正的差异化点）：用户说"以后带发票的邮件自动归到财务文件夹"，AI 生成规则草稿（条件 + 动作），**用户确认后入库**。复用现有的 function calling 与「破坏性操作先确认」模式（AI 日历删除已有 `pending_delete` + 10 秒撤销的先例），不新增机制。

**落点**：

- 规则模型放 `me-core`（条件与动作是纯数据 + 纯函数判定，最好测）；
- 存储：新表 `rules`（+ 可选 `rule_runs` 审计）；
- **执行点**：`me-sync` 的正文落库路径上，**邮件写入后、发事件前**执行。新邮件判定 = 同步路径；历史邮件补跑 = 独立的批量任务（走 `Command`，不进 UI 线程）；
- 执行失败**不得影响邮件同步**——沿用 D27 的原则，新功能不参与邮件 `Governor`；
- 规则命中要能解释（"因为发件人是 x 且主题含发票"），否则用户不敢用。

**待定**：规则是否需要顺序/优先级（建议第一版就是"全部满足"的无序合取，不做优先级，避免复杂化）；标签体系是否独立成表（建议复用 `flags` 位）。

**成本**：中高。**收益**：高——**这是「本地全量」从一句技术描述变成用户能感知到的能力的唯一途径**。

## 5. 第三梯队：会话线程视图

**为什么重要**：现在打开一个来回八封的讨论，看到的是八条独立条目。线程视图是邮件客户端体验的分水岭。

**数据侧成本（主要在这里）**：

- schema v6 给 `messages` 加 `in_reply_to TEXT` 与 `references TEXT`；
- 同步的头部 `FETCH` 多取这两个头（`me-proto` 的 MIME 解析侧要提取）；
- **历史邮件没有这两个头**——这是真正的麻烦所在。三条路：
  - **(a) 只对新增生效**：老邮件不成串，零回填成本，但用户会看到"同一个话题新老邮件分开"；
  - **(b) 后台回填**：按账号逐个重拉头部（只取头不取正文），成本高、耗时长；
  - **(c) 用户手动触发"重建线程"**：对选中的文件夹或时间段重建。
  - **建议 (a) 起步 + (c) 作为补救**，把 (b) 留给真正需要时——因为 (b) 的成本随历史邮件量线性增长，而收益只对"老邮件"生效。

**UI 侧**：列表按线程折叠（显示首封主题 + 参与人数 + 最新时间 + 封数），展开是子邮件列表；阅读页提供"线程"侧栏。这部分工作量不小。

**待定**：折叠粒度（按 `References` 根还是按 `In-Reply-To` 链）；跨账户线程（同一话题来自不同账户时是否合并——建议不合并，保持账户边界）；是否显示"已回复/未回复"。

**成本**：中高（数据 + UI 双头）。**收益**：高。

## 7. 明确不做（含「什么条件下才值得重开」）

| 不做项 | 理由 | 重开条件 |
| --- | --- | --- |
| **本地向量检索 / 语义 RAG** | embedding 要么走 API（每封邮件正文出网，与「全量本地缓存」的隐私叙事直接冲突），要么本地跑 onnxruntime（binary 体积、交叉编译、模型分发都要管）。而 FTS5 trigram 已就位，**真正的缺口不是"语义相似"，是"查询表达力"**——C4 + AI 把自然语言翻成结构化查询，用现有架构就能拿到大部分效果，**零新依赖** | 用户明确反馈"关键词搜不到我想要的那封"，且 C4 + AI 结构化查询已上线 |
| **CalDAV / Google / Microsoft 日历同步** | D17 已定本地优先；引入后要设计 OAuth Scope、双向冲突模型、增量同步三套新机制 | C7（ICS）落地后仍有大量用户反馈无法与现有日历互通 |
| **插件系统 / 脚本扩展** | Rust 没有稳定 ABI，引 wasm 又与「不引 JS 引擎」的架构底线冲突；插件权限模型会让安全边界从"固定白名单"退化为"用户脚本" | 核心功能稳定后，且能设计出**不执行任意代码**的插件形态（如声明式过滤器 DSL） |
| **多窗口 / 标签页 / 多实例新标签页** | 与 egui 单窗口状态模型冲突；单实例 IPC 激活只做窗口聚焦是刻意简化 | v0.4 的 C1–C6 全部落地且用户确有并行查看需求 |
| **SQLCipher 本地库加密** | 库体积与性能影响需先评估；且 v0.3 已接受"AI/天气 Key 明文存 `meta`"的代价（用户明确要求），加密的优先级低于把功能补齐 | 用户对本地数据安全有明确要求时，先做**独立的口令加密层**（只加密少数敏感字段），而不是整库 SQLCipher |
| **AI 自动发信 / 自动回复 / 自动删除** | 不可逆、对外可见；D22 的白名单已明确排除 | 不建议重开 |

## 9. schema 影响与迁移建议

**建议合并为一次 schema v6 迁移**，理由是迁移要写 DDL、备份、回滚、`foreign_key_check` 与签名比对测试，做三次成本远高于做一次。

| 变更 | 类型 | 迁移注意事项 |
| --- | --- | --- |
| 新增 `contacts` 表 | 新表 | 无既有表变更，风险最低 |
| 新增 `rules` 表 | 新表 | 同上 |
| `messages` 加 `in_reply_to` / `references` | 加列 | **必须可空**：历史行没有这两个值，加 `NOT NULL DEFAULT ''` 会让历史行全是空串、语义上与"有但为空"混淆；用 `NULL` 表示"未知" |

**迁移纪律**（沿用 v1→v5 的既有做法）：

1. 每步单独事务，中间步骤版本号写死（v5→v6 写 `6`），**不能写 `SCHEMA_VERSION`**——否则会给 v5 库盖上"已是最新"的章；
2. 迁移前 `wal_checkpoint(TRUNCATE)` 并备份 `myemail.db.bak-v5`；
3. 末尾 `foreign_key_check`；
4. 失败**不写版本号并中止启动**；
5. 新建库的 DDL 必须与迁移后的库**签名等价**（表/索引/CHECK，含列序）——已有 `migration_v1_v2.rs` 里的 `migrated_matches_fresh_schema` 这类测试可照抄；
6. `pragma_table_info` 判列，保证迁移**幂等**（v3→v4 的 `migrate_v3_to_v4` 就是这么做的）。

**DDL 事实源**：[数据结构.md](../数据结构.md) §4 的 DDL 段是唯一事实源，`me-store/src/migrations.rs` 的 `SCHEMA_DDL` 必须与之一致——**v0.4 的 DDL 定稿后要回写该文档**，不要只改代码。

## 11. 建议的推进顺序

```text
阶段 0（前置）：清掉 v0.3 的最后一项未完成
  └─ B4：出 dist/0.3.0/（exe 与 zip 同源）+ check_leak.py 跑通
     —— 理由：现在动新功能，出问题没法回滚

阶段 1：C1 + C2 + C3 + C4        （一次 schema v6 迁移，一次回归，一次发布）
  └─ C4 先做（纯前端 + 解析层，零 schema）→ C3 → C2 → C1
     —— 理由：三者共用一次迁移与一次回归；C4 独立可先合入

阶段 2：C5（规则引擎）
  └─ 条件判定（纯函数）→ 存储 → 同步路径执行 → 历史补跑 → AI 起草规则
     —— 理由：独立可交付，不阻塞邮件主链路（D27 原则）

阶段 3：C6（会话线程）
  └─ schema 加列 → 同步取头 → 列表折叠 → （可选）手动重建
     —— 理由：UI 工作量大，放在基础能力稳定之后

并行：C7–C13 按各自登记时点插队
  └─ C8、C11 成本最低，可随时插；C7 与 C6 同期做（都动日历/邮件关联）
```

**验收门禁**（沿用 v0.3 的约定）：`cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`（测试数不低于 548）、`cargo deny check`；新增功能必须附「邮件主链路不回归」的断言。
