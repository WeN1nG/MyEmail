## 0. 评审结论（2026-11-06）

本文初稿写完后做了一轮评审（逐条核代码 + 对每个开放问题拍板），结论如下。**这些结论已回写到本文后续各节**。

| # | 结论 | 影响 |
| --- | --- | --- |
| **D41** | **产品定位 = 自用主力，顺带发布。** 取舍标准是「我每天用得顺不顺」，不做通用性打磨（首次引导、空状态、导入导出、多版本兼容） | 全文排序按此标准重排 |
| **D42** | **规则引擎降级为「保存的搜索」。** 条件复用查询解析器，**只存条件、不做自动动作**。自动规则推迟到「真的用了一阵子、发现每次都要手动点」之后再说 | 整节重写；原"第二梯队·中高成本"降为"第一梯队·低成本" |
| **D43** | **查询语法与保存的搜索合并为一个功能「保存的搜索」。** 速记语法是它的输入方式，不是独立功能 | 原 C4/C5 两项合并为 C4 |
| **D44** | **统一收件箱保留第一梯队第一**，前提是日常在用 2 个及以上账户（已确认）。聚合视图里的移动操作，**目标文件夹从该邮件所属账户的文件夹里选** | C1 维持原判 |
| **D45** | **线程视图的历史邮件走「新增 + 本地 `raw/*.eml.gz` 离线回填」**，不做服务器回填 | 线程视图成本下调，且新增离线回填路径 |
| **D46** | **正文补全队列由「旧→新」改为「最近优先」**（`ORDER BY folder_id, date DESC, id DESC`） | 新增即修项 F1，优先级最高 |
| **D47** | **「明确不做」全封死**：本地向量检索、CalDAV、插件系统、多窗口/标签页。**整库 SQLCipher 不做**，降为「只加密敏感字段」的轻量方案（因 AI / 天气 Key 明文存 `meta`） | §7 相应改写 |
| **D48** | **不等待真实验收，直接进入开发。** v0.3 的 6 项人工验收（真实 Gmail/Outlook OAuth + IDLE、真实天气 Key、真实 AI Key、真机音频、Docker E2E、界面观感）**仍未执行**，此项风险如实保留在 §10，不因为开工而消失 | 推进顺序按"边开发边找机会验收"编排 |

> **D48 的风险要点**：真实 Gmail/Outlook 的 **IDLE 行为与本项目 mock 出来的时序很可能不同**。若真实服务器上 IDLE 不工作，"实时同步"这一整块设计要重来，届时 §11 的批次划分需要重排——但**候选功能清单本身不受影响**（统一收件箱、保存的搜索、线程视图都与之无关）。这是"先开工"的代价，知情即可。

### 评审中查实的五个技术事实

这些不是推测，均已对照代码确认，且**改变了初稿的成本估算**：

| # | 事实 | 证据 | 对结论的影响 |
| --- | --- | --- | --- |

| 5 | **项目没有创建文件夹的功能，也没有标签体系。** `create_folder` 全仓零命中，`folders` 的行只来自服务器同步；`flags` 只有 5 个标准 IMAP 位（Seen / Answered / Flagged / Deleted / Draft）；`pending_ops.kind` 只有 `move_to_trash` / `delete_permanent` / `empty_folder` 三个取值 | `me-store/src/folders.rs`、`me-core/src/model.rs:545-549`、`me-store/src/migrations.rs:141` | **决定性支持 D42**：规则引擎的动作集要么要求先补 IMAP CREATE + 扩 kind + 建标签体系，要么就只能做纯只读的保存搜索——后者成本低一个数量级 |

## 1. 结论摘要

| 梯队 | 候选 | 判断 |
| --- | --- | --- |
| **即修**（先做，与候选无关） | F1 正文补全队列改最近优先 | 一行 SQL + 一条测试 + 同步文档不变量 |
| **第一梯队**（低成本高收益） | C1 统一收件箱、C2 联系人自动补全、C3 批量多选操作、C4 保存的搜索（含速记语法） | 四项**全部不需要改服务器状态**，全是只读视图 + 本地存储；可合并进**一次** schema 迁移 |
| **第二梯队**（中高成本高收益） | C5 会话线程视图 | 成本因"头部已在手 + 可离线回填"从高降到中高；UI 工作量大 |
| **第三梯队**（补欠账） | C6 ICS 导入导出、C7 单次例外界面、C8 系统通知、C9 功能开关接线、C10 AI 会话分页、C11 AI 选区引用、C12 附件预览 | 全部已在 v0.3 登记，本文只补落点与成本 |
| **明确不做** | 本地向量检索、CalDAV、插件系统、多窗口/标签页、整库 SQLCipher | 见 §7，每条附「什么条件下才值得重开」 |

**核心判断（D41 口径）**：v0.3 的问题不是功能少，是**结构偏了**——四个新页（日历 / 天气 / AI / 音乐）都是加分项，但产品名叫 MyEmail，邮件主线本身还有几处基本盘缺口没补。v0.4 应当**先回补主线、再兑现"本地全量"这个真正独有的优势**，而不是继续加第五个功能页。

**D42 带来的额外收益**：C1–C4 全部不需要改 IMAP/SMTP 写路径，**v0.4 是一个纯增量版本**——不动协议层、不动 `pending_ops`、不引入新依赖。

## 3. 即修项：F1 正文补全队列改为最近优先

**问题**：补全队列是 `ORDER BY folder_id, uid` 升序。UID 在 IMAP 里递增，**升序 = 从最老的邮件开始补**。邮箱里有几万封时，最近收到的邮件要排在队尾等很久才被全文索引。

**为什么这是"搜索价值最高的排在最后"**：搜索价值的衰减极快——用户搜的是"最近发生的事"。而"最近的邮件"恰恰是自动通知这类**用户不会主动打开、但最需要被搜到**的邮件。（打开过的邮件不受影响：打开即入队补全。）

**改动**：`me-store/src/messages.rs` 的补全队列查询由 `ORDER BY folder_id, uid` 改为 `ORDER BY folder_id, date DESC, id DESC`。

> **实施中发现的一条硬约束（本条决定了排序不能写成纯 `date DESC`）**：`me-sync/src/indexer.rs` 的消费是**游程式**的——取 `jobs[index].folder` 后只消费**连续同 `folder_id`** 的那一段，对每段做一次 `SELECT` 再批量 `FETCH`。若把 `date` 放到 `folder_id` 前面，不同文件夹的邮件会交错，同一文件夹会被反复 `SELECT`，**IMAP 往返成倍增加**。因此 `folder_id` 必须留在最前。
>
> 最终排序语义：**文件夹之间按 `folder_id` 升序**（INBOX 等主文件夹 id 小、先补），**文件夹内部按 `date DESC`**。这是「最近优先」的主要落点——绝大多数待补全邮件都在 INBOX。`date` 为 NULL（缺 Date 头）在 `DESC` 下排末位；`id DESC` 作 tiebreaker，保证同一天内次序稳定不抖动（**后插入的先补**，符合「最近优先」）。

**必须同步的文档**（本条是**行为不变量**，改了要一起改，否则后续维护者会按旧描述改回去）：

- `CLAUDE.md`「me-sync」段：「后台补全队列……按 `(folder_id, uid)` 升序」；
- `doc/数据结构.md` §6.3 正文补全队列的 SQL（**DDL 与查询的事实源**）；
- `doc/项目大纲.md` 的补全任务描述。

**验收**：

- 队列取第一条时，期望是**同一文件夹内 `date` 最大**的那封；
- 同一 `date` 时次序稳定（不抖动、不重复取同一封）；
- **同一文件夹的行必须连续**——这是 indexer 的依赖，由 `body_jobs_keep_folders_grouped_while_sorting_newest_first_inside_each` 固定，将来谁把 `folder_id` 挪走会被测试拦下；
- 缺 `Date` 头的邮件排最后；
- 现有补全相关测试全绿；`cargo test --workspace` 不低于 548。

**已知取舍**：待补全集合较大时，`ORDER BY date` 需要额外排序（`idx_messages_body_pending` 只覆盖 `(account_id, folder_id, uid)`）。待补全行数通常远小于全表，暂不单独建索引；若将来成为瓶颈，可加部分索引 `ON messages(account_id, date DESC) WHERE body_path IS NULL`（需走 schema 迁移）。

**成本**：约一行 SQL + 一条测试 + 一处文档同步。**收益**：立刻改善搜索体验，且是后面所有搜索类功能（C4）的前提。

## 4. 第一梯队：回补邮件主线

### C1 统一收件箱（跨账户聚合）

**为什么排第一（D44）**：README 第一句写「多账户统一收发」，但实际体验是「切账户看各自文件夹」。日常在用 2 个及以上账户时，这是产品定位与实现之间的明摆着的缺口——**不是新功能，是兑现已有承诺**。

**落点**：

- `folders` 表的 `role` 有 CHECK 约束（`'inbox','sent','drafts','trash','junk','archive','other'`）且 `account_id NOT NULL`（`migrations.rs:42`），所以**统一收件箱不能落库成一张文件夹行**，必须是视图层的虚拟项；
- `ReadOnlyRepo::list_messages_readonly(folder, cursor, limit)` 是**按 folder** 的（`port.rs:666`），需要新增跨账户的键集分页方法，或把 `folder` 放宽为 `Option<FolderId>`；
- **`me-app` 不得全表扫**：`CLAUDE.md` 的硬规则是 UI 只拿 `ReadOnlyRepo`、单次 `LIMIT ≤ 200`、禁全表扫描与 FTS。跨账户聚合必须**在 store 层一次查完**，不能由 UI 拉完各账户再本地合并（那样既要多次往返，又破坏键集分页）。

**D44 已定的交互**：聚合视图里发起「移动到文件夹」时，**目标文件夹从该邮件所属账户的文件夹里选**。语义上 IMAP 本来就不能跨账户移动（UID 是账户内概念），这只是在 UI 上把限制说清楚。

**待定**：是否也做「统一已发送」「统一草稿」（建议 v0.4 只做统一收件箱，草稿走既有双入口）；聚合排序纯按 `date DESC` 还是按账户优先级（建议纯 `date DESC`）。

**成本**：中低。**收益**：高——它是"多账户"从功能变成体验的分界线。

### C2 联系人自动补全

**为什么排第二**：投入产出比最高的一项。**不需要用户做任何事**——从 `messages.from_addr` / `to_addrs` 自动累积，发信与收信时 UPSERT 计数，撰写页输入时下拉。用户第一次用就会觉得"这软件知道我在跟谁通信"。

**落点**：

- 新增 `contacts` 表（`addr` 唯一、`display_name`、`last_seen`、`seen_count`）；
- 累积时机：正文补全落库时（`me-sync` 的 indexer 路径）与发信成功归档时，**不在 UI 线程做**；
- 撰写页：现有 `TextEdit::singleline` 换成带下拉的输入（前缀匹配 + 排序：最近联系 > 姓名包含 > 邮箱前缀）；
- **隐私边界**：地址簿是**本地派生数据**，与 D30 一致——`ClearCache` 不清理它；但导出必须用户主动触发。

**自用定位下的补充考虑**：通讯录的价值取决于有没有输入源。除了从邮件自动累积，**是否可以导入其他通讯录**（另一个邮件客户端的地址簿 / CSV）？这条留到验收期观察后再定，不进 v0.4 首批。

**待定**：是否允许用户手动编辑与合并联系人（建议 v0.4 只自动累积，不给编辑入口）。

**成本**：低。**收益**：中高（感知强、粘性高）。

---

### C3 批量多选操作

**为什么需要**：现在清理一个装了 500 封的收件箱，只能一封一封点。**这是邮件客户端的基本盘**。

**已有的基础设施（实施时核实）**：`Command::SetFlags { ids: Vec<MessageId>, flags: FlagOp }`（`me-core/src/command.rs:60`）与 `Command::MoveToTrash(Vec<MessageId>)`（`:65`）**本来就是批量的**，`pending_flags` 也天然支持 UPSERT 合并。**C3 因此主要是 UI 工作，不需要新后端命令。**

**落点**：

- `UiState` 增加 `selected: HashSet<MessageId>`，与既有单选 `selected_message` **并存**（单选点击保留，`Ctrl/Shift` 点击进多选，全选用快捷键）；
- **关键约束**：批量必须是一个 `Command` 带 `Vec<MessageId>`，**一次事务、一次网络往返**。不要做成 N 次单封命令串行；
- 批量动作最小集：标记已读/未读、加星（`\Flagged`）、删除（移入废件箱）——三者都有现成命令；
- 破坏性动作（批量删除）沿用现有确认卡模式（AI 页已有 `pending_delete` 的先例）。

> **范围修正（实施时核实，原文有误）**：原文把「移动到文件夹」列进动作集，但**项目根本没有「移动到任意文件夹」这个能力**——`pending_ops.kind` 只有 `move_to_trash` / `delete_permanent` / `empty_folder` 三个取值（`me-store/src/migrations.rs:141`），`me-proto` 只实现了移入废件箱的 MOVE，UI 上也只有「删除」按钮。做「移动到文件夹」等于新增协议层能力，与 D47「v0.4 不碰服务器写路径」冲突。
> **决定：C3 第一版不含「移动到文件夹」**，只做已读/未读/加星/删除三项。这样 C3 是**纯 UI 特性，零后端改动、零 schema 改动**。「移动到文件夹」单列为后续项（且需先有「新建文件夹」能力）。

**与 C1 的关系**：统一收件箱里的批量操作，行为与单账户下完全一致（按邮件自己的 `account_id` 走），不需要额外处理。

**待定**：跨文件夹选择是否支持（建议不支持）；批量上限（建议单次 ≤ 500）。

**成本**：低。**收益**：中高。

### C4 保存的搜索（含速记语法）

> **D43 合并说明**：本项由初稿的「C4 查询语法」与「C5 规则引擎」合并而来。速记语法是保存的搜索的**输入方式**，不是独立功能；分开做会让"解析器"和"存储"分属两个功能、两套 UI。

**核心价值**：**后端已经写好了，只对 AI 开放**（§0 事实 4）。`SearchQuery` 的字段与 `SearchRepo::search` 的 SQL 都已支持多条件取交集，AI 侧一直在用。UI 侧缺的只是一个语法解析器、一份存储、一个列表。

> **实施时核实（成本比原文估的更低）**：UI 侧的高级筛选**已经做了一半**——`me-app/src/views/mailbox.rs:344-380` 有「条件」面板，含**时间范围**（起止 `YYYY-MM-DD`）与**仅含附件 / 不含附件**；`submit_search`（`:383-412`）已经把 `since` / `until` / `has_attachment` 填进 `SearchQuery`。`SearchState` 还预留了 `accounts` / `folders` 两个字段（`state.rs:497-498`）。真实缺口只有：**发件人 / 收件人 / 主题 / 仅未读**四个条件 + 速记语法 + 保存管理。

**D42 的边界**：**只存条件，不做自动动作。** 不移动邮件、不改标记、不删除——搜索结果永远只是"一批符合条件的邮件"，用户自己决定怎么处理。这让整个功能零副作用、可随时删除、离线完全可用。

**建议语法**（六个，覆盖绝大多数场景）：

| 写法 | 语义 | 对应 `SearchQuery` 字段 |
| --- | --- | --- |
| `from:zhang` | 发件人包含 | `from` |
| `to:li` | 收件人包含 | `to` |
| `subject:发票` | 主题包含 | `subject` |
| `has:attachment` / `has:none` | 有/无附件 | `has_attachment` |
| `before:2026-01-01` / `after:2026-01-01` | 日期区间 | `until` / `since` |
| `is:unread` | 仅未读 | `unread_only` |

**落点**：

- 解析器放 `me-core`（**纯函数，最好测**——`me-core/src/search_query.rs` 之类，输入一段查询串输出 `SearchQuery` 的可选字段）；
- 存储：`SearchQuery` 序列化进新表 `saved_searches`（**不要塞 `meta`**——`meta` 是键值对，`SearchQuery` 有 `Vec<AccountId>` / `Vec<FolderId>` 等结构，塞 JSON 字符串会让 `meta` 变成垃圾场，且无法按账户索引）；
- UI：搜索框直接接受速记语法 + 一个「保存此搜索」按钮 + 一个已保存搜索列表（可点击执行、可命名、可删除）；
- **必须能回填**：解析出的条件显示在搜索框下方的条件条里，用户能看见"我搜的到底是什么"，并能单独删掉某个条件；
- **顺带收益**：AI 的 `email_search` 工具复用同一个解析器，AI 也能用 `from:` 语法；反过来，AI 可以**起草**查询条件给用户（"帮我找张三上周发来的邮件" → `from:张三 after:...`），**只生成条件、不执行动作，无副作用**。

**与 F1 的依赖**：保存的搜索在正文未索引的邮件上只能搜到头部字段（这本来就是 FTS 的既有行为：≥3 字走正文 trigram，1–2 字仅头部 `LIKE`）。F1 改成最近优先后，**新建的保存搜索立刻就能搜到最近的邮件**——两者叠加才有意义。

**待定**：语法解析失败时的反馈（建议 inline 提示 + 保留已解析部分）；是否支持 `OR` 与括号（建议 v0.4 不做）；已保存搜索是否按账户分组（建议不分组，列表简单为上）。

**成本**：低。**收益**：中高。

## 5. 第二梯队：会话线程视图

**为什么重要**：现在打开一个来回八封的讨论，看到的是八条独立条目。线程视图是邮件客户端体验的分水岭。

**成本为什么比初稿估的低（§0 事实 1、2、3）**：

- **不用改 IMAP 协议层、不用改 FETCH 查询**——`BODY.PEEK[HEADER]` 抓的本来就是完整头部；
- 只需 `mime::ParsedHeader` 多提取两个字段（`In-Reply-To` / `References`），`me-core` 模型加字段，`messages` 表加两列，同步落库时写入；
- **历史邮件不用连服务器**——`raw/*.eml.gz` 里存的是完整邮件，离线解析即可。

**D45 已定的历史策略**：

```text
新增邮件      → 同步落库时直接写两列
历史邮件      → 从本地 raw/*.eml.gz 离线解析回填
未打开过的    → 没有 raw 文件，需要一次回填任务（可后置）
```

**离线回填的实现要点**：

- 复用现成的 `cache::read_raw_gz` 与 `me_proto::mime::parse_headers`；
- 回填是**纯本地操作**，不碰服务器、不消耗 IMAP 配额，可随时中断续跑；
- 进度天然持久（`in_reply_to IS NULL` 即未完成），与正文补全队列同一个套路；
- **覆盖率天然受限**：raw 只在正文补全时写（§0 事实 3），所以未打开过的历史邮件没有 raw。这类邮件的回填要么走服务器重拉头，要么就接受"不成串"——**建议 v0.4 先接受**，把服务器重拉做成用户手动触发。

**UI 侧**：列表按线程折叠（首封主题 + 参与人数 + 最新时间 + 封数），展开是子邮件列表；阅读页提供线程侧栏。这部分工作量不小，是 C5 的主要成本所在。

**待定**：折叠粒度（按 `References` 根还是按 `In-Reply-To` 链）；跨账户线程（同一话题来自不同账户时是否合并——**建议不合并**，保持账户边界）；是否显示"已回复/未回复"。

**成本**：中（数据侧低，UI 侧高）。**收益**：高。

## 7. 明确不做（D47）

| 不做项 | 理由 | 重开条件 |
| --- | --- | --- |
| **本地向量检索 / 语义 RAG** | embedding 要么走 API（每封邮件正文出网，与「全量本地缓存」的隐私叙事直接冲突），要么本地跑 onnxruntime（binary 体积、交叉编译、模型分发都要管）。而 FTS5 trigram 已就位，**真正的缺口不是"语义相似"，是"查询表达力"**——C4 的速记语法 + AI 把自然语言翻成结构化查询，用现有架构就能拿到大部分效果，**零新依赖** | 用户明确反馈"关键词搜不到我想要的那封"，且 C4 已上线一段时间 |
| **CalDAV / Google / Microsoft 日历同步** | D17 已定本地优先；引入后要设计 OAuth Scope、双向冲突模型、增量同步三套新机制 | C6（ICS）落地后仍有大量用户反馈无法与现有日历互通 |
| **插件系统 / 脚本扩展** | Rust 没有稳定 ABI，引 wasm 又与「不引 JS 引擎」的架构底线冲突；插件权限模型会让安全边界从"固定白名单"退化为"用户脚本" | 核心功能稳定后，且能设计出**不执行任意代码**的插件形态（如声明式条件 DSL） |
| **多窗口 / 标签页 / 多实例新标签页** | 与 egui 单窗口状态模型冲突；单实例 IPC 激活只做窗口聚焦是刻意简化 | C1–C4 全部落地且确有并行查看需求 |
| **整库 SQLCipher** | 库体积与性能影响需先评估；且 v0.3 已接受"AI / 天气 Key 明文存 `meta`"的代价（用户明确要求），优先级低于把功能补齐 | 见下条 |
| **AI 自动发信 / 自动回复 / 自动删除** | 不可逆、对外可见；D22 的白名单已明确排除 | 不建议重开 |

**关于数据库加密（D47 的降级口径）**：整库 SQLCipher 不做，但**「只加密敏感字段」的轻量方案保留为评估项**——AI Key 与天气 Key 目前明文在 `meta` 表里（`meta.ai_models` / `meta.weather_api_key`）。可选路径是应用层加密：主密码经 PBKDF2/Argon2 派生密钥，只加密这两个字段，其余不动。代价是需要引入用户口令与一次解锁流程——**自用定位下这个代价是可接受的**，但它属于「不紧急」象限，排在 C1–C4 之后（见 O34）。

## 9. schema 影响与迁移建议

**建议合并为一次 schema v7 迁移**，理由是迁移要写 DDL、备份、回滚、`foreign_key_check` 与签名比对测试，做三次成本远高于做一次。

| 变更 | 类型 | 迁移注意事项 |
| --- | --- | --- |
| 新增 `contacts` 表 | 新表 | 无既有表变更，风险最低 |
| 新增 `saved_searches` 表 | 新表 | `SearchQuery` 的 JSON 存 `query_json` 列；建议另加 `name` / `created_at` / `last_used_at` 列便于排序与清理 |
| `messages` 加 `in_reply_to` / `references` | 加列 | **必须可空**：历史行没有这两个值，加 `NOT NULL DEFAULT ''` 会让历史行全是空串、语义上与"有但为空"混淆；用 `NULL` 表示"未知" |

**迁移纪律**（沿用 v1→v5 的既有做法）：

1. 每步单独事务，中间步骤版本号写死（v5→v6 写 `6`），**不能写 `SCHEMA_VERSION`**——否则会给 v5 库盖上"已是最新"的章；
2. 迁移前 `wal_checkpoint(TRUNCATE)` 并备份 `myemail.db.bak-v5`；
3. 末尾 `foreign_key_check`；
4. 失败**不写版本号并中止启动**；
5. 新建库的 DDL 必须与迁移后的库**签名等价**（表/索引/CHECK，含列序）——照抄 `migration_v1_v2.rs` 里的 `migrated_matches_fresh_schema`；
6. `pragma_table_info` 判列，保证迁移**幂等**（v3→v4 的 `migrate_v3_to_v4` 就是这么做的）。

**DDL 事实源**：[数据结构.md](../数据结构.md) §4 的 DDL 段是唯一事实源，`me-store/src/migrations.rs` 的 `SCHEMA_DDL` 必须与之一致——**v0.4 的 DDL 定稿后要回写该文档**，不要只改代码。

**F1 不涉及 schema**——纯查询排序，改 `me-store/src/messages.rs` 的 ORDER BY 即可，可以先于迁移独立提交。

## 11. 推进顺序

> **详细的批次划分、每个批次的文件级改动清单、schema v7 迁移模板与验收标准见 [v4开发指南.md](v4开发指南.md)。** 本节只给粗粒度顺序，避免两份文档各维护一套。

```text
阶段 0（独立，先做）—— F1 ✅ 已实施
  └─ 改 ORDER BY + 补测试 + 同步 CLAUDE.md / 数据结构.md / 项目大纲.md 三处不变量
     理由：不动 schema、不动协议；且它是 C4 的前提

阶段 1 —— C4 + C3 + C2 + C1（一次 schema v7 迁移，一次回归，一次发布）
  └─ 顺序：C4（纯前端 + 解析器，可先合入）→ C3 → C2 → C1
     理由：四项共用一次迁移与一次回归；C4 独立可先合入
  └─ 并行：C6–C12 按各自登记时点插队（C7 / C10 成本最低，可随时插）

阶段 2 —— C5（会话线程）
  └─ 解析字段 → schema 加列 → 同步落库写入 → 列表折叠 → 本地离线回填
     理由：UI 工作量大，放在基础能力稳定之后

阶段 3 —— 敏感字段加密（评估后定，见 O34）
```

**验收门禁**（沿用 v0.3 的约定）：`cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`（测试数不低于 548）、`cargo deny check`；新增功能必须附「邮件主链路不回归」的断言。

**打包纪律**：`dist/0.3.0/` 是 15:05 的产物，而 `target/release/myemail.exe` 是 16:03 的——**两者不同源**。动代码后要重跑 `scripts/build_release.sh` + `scripts/pack_dist.py --version 0.3.0` + `scripts/check_leak.py`，否则发出去的不是当前代码。
