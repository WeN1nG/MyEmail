## 1. 架构级变更总览

v0.4 的架构级变更只有四处，其余都是实现细节。**先把这四处定下来，其余按 §2 的批次推进。**

### 1.1 schema v7（唯一的 DDL 级变更）

> ⚠️ **版本号已从 v6 改为 v7（2026-11-06 修正）**。
> 原文假定基线是 `schema_version = 5`、把 v6 用作本次迁移；但工作区**已经**实现了一套
> schema v6（**纯索引调整**：`migrate_v5_to_v6` + `crates/me-store/tests/migration_v5_v6.rs`，
> 对应 `优化清单.md` 的 P0-2/P0-3/P0-4 性能修复，有实测数据支撑）。
> 沿用 v6 会与既有实现**撞号**（函数重名、目标版本都写 6、`create_schema` 的 DDL 与迁移 DDL 分叉，
> 签名等价性测试必然失败）。故本次迁移顺延为 **v7**。
> 完整替换清单见 [v4开发准备.md](v4开发准备.md) §1.3。

一次迁移，三项变更，合并做（迁移要写 DDL、备份、回滚、`foreign_key_check` 与签名比对测试，做三次成本远高于做一次）。

| 变更 | 类型 | 关键约束 |
| --- | --- | --- |
| 新增 `contacts` 表 | 新表 | 无既有表变更，风险最低 |
| 新增 `saved_searches` 表 | 新表 | `SearchQuery` 的 JSON 存 `query_json` 列；另加 `name` / `created_at` / `last_used_at` |
| `messages` 加 `in_reply_to` / `references` | 加列 | **必须可空**：`NOT NULL DEFAULT ''` 会让历史行全是空串，与「有但为空」混淆；用 `NULL` 表示「未知」 |

**改哪些文件**：

| 文件 | 改什么 |
| --- | --- |
| `crates/me-store/src/migrations.rs` | 新增 `SCHEMA_V7_DDL` 常量；新增 `fn migrate_v6_to_v7`；`ensure_schema` 的版本分派加 `Some(6) =>` 分支 |
| `crates/me-core/src/lib.rs` | `SCHEMA_VERSION: u32 = 6` → `7`（第 81 行） |
| `crates/me-store/src/db.rs` | `create_schema` 执行 `SCHEMA_V7_DDL`（与 `migrate_v6_to_v7` 共用同一份 SQL） |
| `doc/数据结构.md` | §4 增补 v7 DDL；§9 增补 v6→v7 迁移步骤 |
| `crates/me-store/tests/migration_v6_v7.rs`（新建） | 迁移正确性、幂等性、备份、回滚、签名等价 |

> **`SCHEMA_V7_DDL` 只放本次的三个新增项**（两张新表 + 两列），
> **不要重复包含 v6 的 6 条索引定义**——那些索引已在 `SCHEMA_V3_DDL`（即 `create_schema` 的 DDL）里，
> 改索引列序属于 v6 的职责。

**怎么改（照抄 v3→v4 / v4→v5 的模板）**：

```rust
// crates/me-store/src/migrations.rs
/// v6 → v7：新增 `contacts` / `saved_searches` 两张表；给 `messages` 补两列。
fn migrate_v6_to_v7(conn: &mut Connection) -> Result<(), CoreError> {
    // 目标版本写死 7：写 `SCHEMA_VERSION` 会让 v6 库被一步标成最新版本。
    const TARGET: u32 = 7;
    let tx = conn.transaction().map_err(|e| storage(format!("开始 v6→v7 迁移事务失败: {e}")))?;

    tx.execute_batch(SCHEMA_V7_DDL)
        .map_err(|e| storage(format!("执行 v6→v7 迁移失败: {e}")))?;

    // 加列按列存在性判断，保证幂等（新建库的 SCHEMA_V7_DDL 已带这两列，
    // 重复 ALTER 会报 duplicate column）。
    for (table, column) in [("messages", "in_reply_to"), ("messages", "references")] {
        let has: bool = tx.query_row(
            "SELECT EXISTS(SELECT 1 FROM pragma_table_info(?1) WHERE name = ?2)",
            params![table, column],
            |row| row.get(0),
        ).map_err(|e| storage(format!("读取 {table} 列信息失败: {e}")))?;
        if !has {
            tx.execute_batch(&format!("ALTER TABLE {table} ADD COLUMN {column} TEXT;"))
                .map_err(|e| storage(format!("执行 v6→v7 加列失败: {e}")))?;
        }
    }

    tx.execute("UPDATE meta SET value = ?1 WHERE key = 'schema_version'", params![TARGET.to_string()])
        .map_err(|e| storage(format!("写入 schema_version 失败: {e}")))?;

    check_foreign_keys(&tx)?;
    tx.commit().map_err(|e| storage(format!("提交 v6→v7 迁移事务失败: {e}")))?;
    Ok(())
}
```

**为什么这样写**（三条都是踩过的坑）：

1. **目标版本写死 `7`**，不能写 `SCHEMA_VERSION`——否则 v6 库会被一步盖上「已是最新」的章（v2→v3 的注释里踩过同一个坑）。
2. **加列按 `pragma_table_info` 判存在性**，不无条件 `ALTER`——新建库走 `create_schema`，它的 DDL 已带这两列，重复 ALTER 会报 duplicate column（v3→v4 就是这么处理的）。
3. **迁移前 `wal_checkpoint(TRUNCATE)` + 备份 `.bak-v6`**，失败**不写版本号并中止启动**。

> **版本分派必须加分支**：现有 `ensure_schema`（`migrations.rs:419`）的兜底是 `Some(version) => Err(...)`，**不加分支的话 v6 库会直接启动失败**。同时 v1→v2→v3→v4→v5→v6→v7 的链条要逐级补上。

**验收**：`migrated_v6_matches_fresh_v7_schema`（签名比对：表 / 索引 / CHECK，含列序）、迁移幂等（连跑两次不报错）、`foreign_key_check` 无悬空、失败回滚后版本号不变、新建库与迁移库结构等价。

### 1.2 端口（trait）变更

`me-core/src/port.rs`（第 866 行）新增两个 trait，扩展一个既有 trait。**全部是加法，不改既有方法签名。**

```rust
// 新增：保存的搜索
pub trait SavedSearchRepo {
    fn list_saved_searches(&self) -> Result<Vec<SavedSearch>, CoreError>;
    fn insert_saved_search(&self, search: &SavedSearch) -> Result<SavedSearchId, CoreError>;
    fn delete_saved_search(&self, id: SavedSearchId) -> Result<(), CoreError>;
    fn touch_saved_search(&self, id: SavedSearchId) -> Result<(), CoreError>;   // 更新 last_used_at
}

// 新增：联系人
pub trait ContactRepo {
    fn upsert_contact(&self, contact: &Contact) -> Result<(), CoreError>;
    fn list_contacts(&self, prefix: &str, limit: u32) -> Result<Vec<Contact>, CoreError>;
    fn remove_contact(&self, id: ContactId) -> Result<(), CoreError>;
}
```

**`ReadOnlyRepo` 扩展**（第 663 行）——**这是 `me-app` 唯一可见的存储句柄**：

```rust
fn list_unified_inbox_readonly(&self, cursor: Option<(i64, i64)>, limit: u32)
    -> Result<Vec<MessageSummary>, CoreError>;
fn unified_unread_count_readonly(&self) -> Result<u32, CoreError>;
fn list_contacts_readonly(&self, prefix: &str, limit: u32) -> Result<Vec<Contact>, CoreError>;
```

**为什么这么切**：

- **仓储方法一律同步**（`me-store` 禁依赖 tokio，见 `me-core/src/port.rs` 注释）——写操作走 `Command`，读操作由 `me-app` 通过只读句柄直取。
- **`me-app` 不得全表扫**：单次 `LIMIT ≤ 200`、禁 FTS、禁写连接（`CLAUDE.md` 硬规则）。跨账户聚合**必须在 store 层一次查完**——不能由 UI 拉完各账户再本地合并（既破坏键集分页，又要多轮往返）。
- **`ContactRepo` 放进 `me-core` 而不是 `me-app`**：联系人累积是**后台行为**（正文补全落库时、发信归档时），发生在 `me-sync`，走 `Command` 或仓储直调。

### 1.3 Command / Event 契约变更（只做加法）

`crates/me-core/src/command.rs`：`Command` 枚举在第 34 行，`Event` 枚举在第 458 行。

```rust
// Command 新增
SaveSearch { name: String, query: SearchQuery },
DeleteSearch { id: SavedSearchId },
RunSavedSearch { id: SavedSearchId },

// Event 新增
SavedSearchesChanged { searches: Vec<SavedSearch> },
```

**为什么需要 `RunSavedSearch`**：点已保存的搜索时，UI 要把 `SavedSearch.query`（存库的 JSON）**反序列化回 `SearchQuery`** 再发 `Command::Search`。这一步必须在 UI 侧做，因为 `SearchQuery` 是 `me-core` 类型、UI 持有它。

**不要把 `SearchQuery` 直接塞进 `Event`**——`Event` 是跨线程快照载荷，大结构会让事件通道撑不住（参照 `AiStreamDelta` 的偏差 1：增量事件让通道满即丢）。

**`is_progress` / `is_critical` 要一并更新**（第 823、831 行）：`SavedSearchesChanged` 是**关键事件**（不可丢，否则 UI 与存储不一致）。

### 3.4 怎么改：解析器的形状

**先定数据形状，再写解析**——解析器输出必须能直接喂给 `SearchQuery`：

```rust
// crates/me-core/src/search_syntax.rs

/// 速记语法解析结果。未识别的片段进 `text`，认识的进对应字段。
#[derive(Debug, Clone, Default, PartialEq, Eq)]
pub struct ParsedQuery {
    pub text: String,
    pub from: Option<String>,
    pub to: Option<String>,
    pub subject: Option<String>,
    pub has_attachment: Option<bool>,
    pub since: Option<i64>,
    pub until: Option<i64>,
    pub unread_only: bool,
    /// 无法识别的片段（拼错的字段名等），UI 用来提示但不阻断搜索。
    pub unknown: Vec<String>,
}

/// 解析搜索框输入。**纯函数**：不 IO、不读时钟（日期用调用方传入的 today）。
///
/// 支持：`from:` `to:` `subject:` `has:attachment` `has:none`
///       `before:YYYY-MM-DD` `after:YYYY-MM-DD` `is:unread`
/// 不支持：`OR`、括号、引号（v0.4 明确不做，见 O29）。
pub fn parse(input: &str, today: i64) -> ParsedQuery { /* ... */ }
```

**为什么要 `today` 作参数**：项目里已有 `me_core::date` 一类的日期工具，但**纯函数不读时钟**才能测。日期上界（`before:`）用 `today` 推算，调用方传进来。

**为什么要 `unknown` 字段而不是直接报错**：搜索是探索性的——用户打错 `fromm:` 应该得到「搜索照常执行 + 一条提示」，而不是弹一个错误把输入清掉。

### 3.5 怎么改：UI 的条件回填（chips）

`SearchState` 加一个展示用的结构：

```rust
// crates/me-app/src/state.rs
pub struct SearchState {
    // ... 既有字段不动 ...
    pub from: String,
    pub to: String,
    pub subject: String,
    pub unread_only: bool,
    /// 已解析条件的展示列表（chips），每项可单独删除。
    pub conditions: Vec<ConditionChip>,
    pub saved_searches: Vec<SavedSearch>,
}

pub struct ConditionChip {
    pub label: String,   // 「发件人含 zhang」
    pub kind: ChipKind,  // From / To / Subject / HasAttachment / Before / After / Unread
    pub value: String,
}
```

**为什么要有 chips**：用户必须能看见「我搜的到底是什么」，并且能单独删掉某个条件。`submit_search` 现在把条件塞进 `SearchQuery` 就完事，用户改了输入框里的 `from:` 但没回车，界面显示的还是旧条件——**这个不一致必须避免**。

### 3.6 三个必须避开的坑

**三个必须记住的决定**：

1. **不能直接序列化 `SearchQuery`**。它带 `cursor`（键集分页游标）与 `limit`（分页大小）——
   那是**一次查询的状态**、不是**条件**。整份存进去，保存的搜索下次执行会带着上次的翻页位置，
   点开只能看到第二页。`SavedSearchQuery` 是持久化子集：只留条件，`accounts` / `folders` 这类**范围**要存。
2. **名称重复要在仓储层翻译成 `CoreError::Validation`**。`Storage` 的 `user_message()` 是通用文案
   （「本地数据库操作失败」），UI 拿不到「名字重复」这个信息。判据用 SQLite extended_code

**三条硬约束**（都写在代码注释里）：

1. **必须批量 UPSERT**——累积发生在正文补全的写库路径上，一封一封写会把补全吞吐拖垮。
2. **累积放在正文落库之后**——它是一笔额外的写，放在后面不会拖慢「正文能搜到」这条主线。
3. **失败不报错**——联系人是附带行为，一封畸形邮件不该让这封邮件的正文永远补不上。

**界面侧的四个细节**：

- 前缀取**正在输入的那一段**（地址框是 `a@x.com, Name <b@x.com>` 这样的列表），
  不是整串——否则输入第二个地址时永远匹配不到。
- 前缀不足 2 个**字节**不查库：「a」能匹配所有人，候选列表没意义。判据是 `prefix.len()`（字节）而非字符数——
  单个汉字是 3 字节，所以「张」仍然会查，这是有意的（一个姓氏就有意义）。
- 前缀没变就不重查（这一步在 UI 主线程上，不能每帧查库）。
- 查库失败**静默降级为空候选**，不弹错误——补全是辅助功能。

## 6. 批次 4：C1 统一收件箱

### 6.1 设计要点（先定这个，否则会写出四不像）

**「统一收件箱」是视图层的虚拟项，不是数据库里的文件夹行。**

### 6.3 状态设计：为什么用 `unified_inbox: bool` 而不是改 `selected_folder` 类型

现有 `state.selected_folder: Option<FolderId>`（`state.rs:196`）被十几处引用。改成 `enum MailScope { Folder(FolderId), UnifiedInbox }` 更"干净"，但会波及整个 `me-app`——**收益不抵风险**。

**决定**：加 `unified_inbox: bool`，与 `selected_folder` **互斥**：

| 场景 | `unified_inbox` | `selected_folder` |
| --- | --- | --- |
| 选了统一收件箱 | `true` | `None` |
| 选了某文件夹 | `false` | `Some(id)` |
| 都没选（初始 / 切账户） | `false` | `None` |

**互斥必须集中在一处维护**——加两个 `UiState` 方法 `select_unified_inbox()` / `select_folder(id)`，所有入口只调这两个方法，禁止直接写字段。否则会出现「`unified_inbox = true` 且 `selected_folder = Some(x)`」的矛盾态，列表取数会二义。

> **注意 `mailbox.rs:37` 的空态判断**：`if state.selected_folder.is_none() && !state.search.active` → 提示「请选择文件夹」。统一收件箱选中时 `selected_folder` 也是 `None`，**会被误判成空态**。必须改成 `if state.selected_folder.is_none() && !state.search.active && !state.unified_inbox`。

### 6.4 跨账户聚合查询

```rust
// crates/me-store/src/messages.rs

/// 统一收件箱：各账户 `role='inbox'` 文件夹的并集，按时间倒序。
///
/// 键集分页与单文件夹列表一致：`(date, id)` 游标 + `LIMIT ≤ 200`。
/// 排序键必须跨账户稳定，故用 `date DESC, id DESC`（`id` 是全局主键，天然唯一）。
pub(crate) fn list_unified_inbox_conn(
    conn: &Connection,
    cursor: Option<(i64, i64)>,
    limit: u32,
) -> Result<Vec<MessageSummary>, CoreError> {
    let limit = limit.clamp(1, MAX_PAGE_SIZE);
    // WHERE 子句：只取收件箱，且排除本地已移动（uid IS NULL）的行。
    let base = "m.uid IS NOT NULL AND m.folder_id IN (\
                SELECT id FROM folders WHERE role = 'inbox')";
    // ...
}
```

**关键点**：

- 用 `folder_id IN (SELECT id FROM folders WHERE role = 'inbox')` 而不是 `account_id IN (...)`——**「收件箱」是文件夹角色，不是账户**。一个账户可以有多个被标记为 inbox 的文件夹（IMAP 的 SPECIAL-USE 启发式可能标错，`SetFolderRole` 就是为此存在的）。
- **必须排除 `uid IS NULL`**：本地已移动、服务器身份待确认的行（`CLAUDE.md` 的删除路径不变量）在服务器上还没有位置，不该出现在聚合视图里。
- 未读计数同理，但要注意 **同一个 `flags & 1` 位**（bit 0 是 `\Seen`，`(flags & 1) = 0` 才是未读）。

**三个踩到的坑**（指南未预见）：

1. **`References` 不能用逗号列表解析器**。它是**空格分隔**（`<a> <b>`），
   `mail-parser` 的 `parse_comma_separared` 只按逗号切，会把整条链当一个字符串，
   永远分不出根。改为 `header_raw` 取原文、自己按 `<...>` 扫；没有尖括号的脏数据
   才退化成按空白/逗号切。
2. **`NULL` 与 `"[]"` 必须区分**。队列判据是 `"references" IS NULL`；
   如果回填时把空链也写 `NULL`，没有回复头的邮件会**永远留在队列里**、每次启动重解析一遍。
   最终语义：入库空链写 `NULL`（未处理），回填空链写 `"[]"`（处理过）。
3. **队列不能用「取前 N 条」**。本轮读不到 `raw/` 的行会留在队列里，
   取前 N 条会让同一批被反复选中、整轮卡死。改成 `id > after` 游标推进。

历史邮件能成串；没补全的接受单独成串（O30 的服务器重拉未做）。新建库/新邮件不受影响。

## 10. 风险与回退

| 风险 | 影响 | 缓解 | 回退 |
| --- | --- | --- | --- |
| **schema v7 迁移失败** | 数据库打不开 | 迁移失败不写版本号并中止启动；迁移前 `wal_checkpoint(TRUNCATE)` + 备份 `.bak-v6` | 从 `.bak-v6` 恢复；发版前用 v6 库做迁移演练 |
| **版本分派漏了 `Some(6)` 分支** | v6 库启动即失败 | `ensure_schema`（`migrations.rs:419`）的兜底是 `Err`，必须显式加分支 | 加分支即可；发版前用真实 v6 库跑一次 |
| **统一收件箱的聚合查询慢** | 大库下列表卡顿 | 键集分页 + `LIMIT ≤ 200`；`folder_id IN (SELECT ...)` 走 `idx_folders` | 退回按账户分别查（牺牲聚合语义） |
| **联系人累积拖慢正文补全** | 补全吞吐下降 | **必须批量 UPSERT**，不能一封一封写；累积放在补全批次之后 | 关闭累积（加开关），功能降级为「只在发信时累积」 |
| **速记语法解析误判** | 搜不到用户想要的东西 | 未知片段进 `unknown` 并提示，不阻断；解析器纯函数、覆盖单测 | 退回「只用条件面板」（现有能力） |
| **线程回填与正文补全抢磁盘** | 补全变慢 | 回填只读本地文件不联网；批间检查取消标记与磁盘余量 | 暂停回填（进度天然持久，随时续跑） |
| **v0.3 的 6 项人工验收仍未做** | 真实 Gmail/Outlook 上 IDLE 行为可能与 mock 不同 | **与本批次的开发无耦合**——C1–C4 不依赖 IDLE | 若 IDLE 要重做，只影响「实时同步」这一块，候选清单不动 |

**回退策略**：v0.4 的每个批次都是**独立提交**，可单独 revert。schema v7 的三个变更在**同一批**里——**不要拆成三次迁移**，否则中间态的 schema 版本会让回退变复杂。
