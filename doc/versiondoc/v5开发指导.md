### 1.2 明确不做的（防止范围蔓延）

- **不做 OCR**。扫描件 PDF **交给 LLM 的视觉能力**处理（它本身能读扫描页），不做本地 OCR，不引入 tesseract（+50 MB）。
- **不做纯 Rust 的 `.doc` / `.ppt` 二进制解析**（决策 O-12 / O-17）。老格式交给外部转换器，按优先级探测：LibreOffice `soffice` → Windows Word COM（内嵌 PowerShell 脚本）→ 报错。不自己实现 OLE 解析。
- **不做本地生成模型**。candle 只承担 embedding 推理，不跑 LLM。
- **不做图片/音频理解**、不做多模态向量、不做向量分片/聚类/重排模型。
- **不做知识库的跨设备同步**。
- **不做通知的点击回调**。Windows 上 `notify-rust` 的 action 回调支持有限，第一版只做「发出去」，点击不跳转。

> **注意**：PDF **要**本地按页切分（决策 O-15）。`lopdf` 是为「切文件」引入的，不是为「提文本」——切完的每一批仍以 PDF 原文件形态交给模型。这与「不做本地 PDF 解析」不矛盾：解析（提取文本/版面）交给模型，本机只做无损切页。

## 2. 架构级变更总览

### 2.1 schema v9：**纯建表，不动任何既有表**

`SCHEMA_VERSION` 从 8 → 9（[crates/me-core/src/lib.rs:88](../../crates/me-core/src/lib.rs)）。

v9 只用 `CREATE TABLE IF NOT EXISTS`，**不 ALTER、不加列、不动索引**。老库升级只是多出几张空表，回滚就是删表。

```sql
-- 知识库文档（一份导入物 / 一封邮件 = 一行）
CREATE TABLE kb_documents (
    id            INTEGER PRIMARY KEY,
    -- file = 本地文件；mail = 邮件自动入库；ai = 工具写入
    origin        TEXT NOT NULL DEFAULT 'file'
                  CHECK (origin IN ('file','mail','ai')),
    -- file: 规范化绝对路径；mail: 消息 id 的**字符串形式**；ai: 工具生成的 slug
    -- （mail 也写字符串是必须的：下面 UNIQUE(origin, source_ref) 要能成立，
    --   否则所有邮件记录都是空串、第二条就撞唯一约束）
    source_ref    TEXT NOT NULL DEFAULT '',
    title         TEXT NOT NULL,
    -- md / txt / docx / pdf / pptx / mail / text
    kind          TEXT NOT NULL,
    -- **邮件来源的整数外键**：删邮件时靠它 CASCADE，不去解析 source_ref 字符串。
    -- 非邮件来源为 NULL。这也是本表唯一的外键。
    mail_id       INTEGER REFERENCES messages(id) ON DELETE CASCADE,
    size_bytes    INTEGER NOT NULL DEFAULT 0,
    -- sha256(内容指纹)。邮件正文变化后重新入库靠它判定。
    content_hash  TEXT NOT NULL DEFAULT '',
    status        TEXT NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending','extracted','chunked','embedded',
                                    'skipped','failed')),
    skip_reason   TEXT,
    chunk_count   INTEGER NOT NULL DEFAULT 0,
    char_count    INTEGER NOT NULL DEFAULT 0,
    -- rule（本地结构拆）/ llm（模型拆）/ converter（先转格式）
    splitter      TEXT,
    embed_model   TEXT,
    embed_dim     INTEGER NOT NULL DEFAULT 0,
    enabled       INTEGER NOT NULL DEFAULT 1,
    error         TEXT,
    created_at    INTEGER NOT NULL,
    updated_at    INTEGER NOT NULL,
    UNIQUE(origin, source_ref)
);
CREATE INDEX ix_kb_documents_status ON kb_documents(status, updated_at DESC);
CREATE UNIQUE INDEX ux_kb_documents_mail ON kb_documents(mail_id) WHERE mail_id IS NOT NULL;

CREATE TABLE kb_chunks (
    id         INTEGER PRIMARY KEY,
    doc_id     INTEGER NOT NULL REFERENCES kb_documents(id) ON DELETE CASCADE,
    ord        INTEGER NOT NULL,
    text       TEXT NOT NULL,
    char_count INTEGER NOT NULL,
    -- pdf 页码 / pptx 幻灯片号 / md 标题路径 / 邮件段落序号
    locator    TEXT,
    embedded   INTEGER NOT NULL DEFAULT 0,
    UNIQUE(doc_id, ord)
);
CREATE INDEX ix_kb_chunks_doc ON kb_chunks(doc_id, ord);
CREATE INDEX ix_kb_chunks_pending ON kb_chunks(doc_id) WHERE embedded = 0;

-- 语块级全文检索。**用普通 FTS5，不用外部内容表**（决策 O-09）：
-- 多存一份文本换「删除逻辑简单一个数量级」，语块总量通常只几十 MB。
-- **tokenizer 不是 trigram**（决策 O-20）。实测 trigram 对中文几乎失效：
-- 「合同」「预算」这类 2 字词全部 0 命中，连「合同审查」这种 4 字词也 0 命中
-- （trigram 只认原文连续 3 字符，跨词就废）。
-- 改用 unicode61 + 中文逐字空格化 + 短语查询，2 字词才能命中（见 §6.4）。
CREATE VIRTUAL TABLE kb_chunks_fts USING fts5(text, tokenize='unicode61');

CREATE TABLE kb_doc_entities (
    doc_id    INTEGER NOT NULL REFERENCES kb_documents(id) ON DELETE CASCADE,
    entity_id INTEGER NOT NULL REFERENCES ai_entities(id) ON DELETE CASCADE,
    -- 命中的语块数：用来排「这份文档主要讲谁」
    hits      INTEGER NOT NULL DEFAULT 1,
    PRIMARY KEY (doc_id, entity_id)
);
CREATE INDEX ix_kb_doc_entities_entity ON kb_doc_entities(entity_id);
```

**`mail_id` 这一列是本期 DDL 的关键决策**：邮件自动入库（O-08）意味着删邮件时必须能级联清掉知识库条目，否则会留下几万条孤儿文档 + 孤儿向量。用整数外键 + `ON DELETE CASCADE` 一次解决；如果只存 `source_ref = '15023'` 字符串，删文件夹时就得先 `SELECT` 出所有 id 再逐条删，既慢又容易漏。

### 2.2 磁盘布局

```text
<root>/                       ← CachePaths::root()
  myemail.db                  ← 主库（新增 4 个对象）
  kb.sqlite                   ← 向量库，独立文件，可整文件删除
  kb/
    chunks/<doc_id>.jsonl     ← 语块导出物
    staging/                  ← 写入中间态，成功后 rename
    tmp/                      ← LibreOffice 转换用的临时目录，用完即删
  models/
    bge-small-zh-v1.5/
      model.safetensors       ← 96 MB，首次确认后从 ModelScope 下载
      tokenizer.json
      config.json
```

**为什么向量单独一个库文件**（别在实现时合并回主库）：

1. 删索引 = 删一个文件，主库与备份完全不动。
2. SQLite 删表**不缩小文件**，向量若进主库，用户删光知识库后 DB 仍然那么大。
3. 主库的 `quick_check` 与迁移/备份逻辑不被 100 MB 级向量表拖累。

`CachePaths::new`（[crates/me-store/src/cache.rs](../../crates/me-store/src/cache.rs)）现在建 `bodies/ raw/ attach/ drafts/ logs/`，需加 `kb/chunks`、`kb/staging`、`kb/tmp`、`models`（`models` 可懒建）。

### 2.3 端口（trait）变更

```rust
// crates/me-core/src/knowledge.rs

/// 嵌入器。**同步阻塞**——candle 推理本来就是阻塞的，
/// 由 me-sync 在 spawn_blocking 里调用，不把 tokio 带进领域层。
///
/// **索引与查询是两个方法，不是同一个**：BGE 系列要给 query 加指令前缀、
/// document 不加。合成一个 `embed()` 迟早会有人混用，召回质量下滑且不报错（§7.7.1）。
pub trait Embedder: Send + Sync {
    fn model_id(&self) -> &str;
    fn dim(&self) -> usize;
    /// 索引路径：不加指令前缀。
    fn embed_documents(&self, texts: &[&str]) -> Result<Vec<Vec<f32>>, CoreError>;
    /// 查询路径：加 `BGE_QUERY_PREFIX`。两者不能混用。
    fn embed_query(&self, query: &str) -> Result<Vec<f32>, CoreError>;
}

/// 知识库仓储。
pub trait KnowledgeRepo: Send + Sync {
    fn upsert_document(&self, doc: &NewKnowledgeDoc) -> Result<KnowledgeDocId, CoreError>;
    fn set_status(&self, id: KnowledgeDocId, status: KbStatus, error: Option<&str>) -> Result<(), CoreError>;
    fn replace_chunks(&self, id: KnowledgeDocId, chunks: &[NewChunk]) -> Result<(), CoreError>;
    fn put_vectors(&self, items: &[(KnowledgeChunkId, Vec<f32>)]) -> Result<(), CoreError>;
    fn knn(&self, query: &[f32], limit: usize) -> Result<Vec<ChunkHit>, CoreError>;
    fn fts(&self, query: &str, limit: usize) -> Result<Vec<ChunkHit>, CoreError>;
    fn list(&self, filter: &KbFilter, limit: u32, offset: u32) -> Result<Vec<KnowledgeDoc>, CoreError>;
    fn get(&self, id: KnowledgeDocId) -> Result<Option<KnowledgeDoc>, CoreError>;
    fn chunks(&self, id: KnowledgeDocId, from: u32, count: u32) -> Result<Vec<KnowledgeChunk>, CoreError>;
    /// **语义是「深删」**：同时清 `kb_chunks` / `kb_chunks_fts` / `kbvec.vec_chunks`，
    /// 实现即 §6.2 的 `delete_doc_deep`（决策 O-26）。调用方不需要知道有四张表。
    fn delete(&self, id: KnowledgeDocId) -> Result<(), CoreError>;
    fn link_entities(&self, id: KnowledgeDocId, links: &[(i64, u32)]) -> Result<(), CoreError>;
    fn doc_entities(&self, id: KnowledgeDocId) -> Result<Vec<i64>, CoreError>;
}
```

**`Embedder::embed` 用同步签名**：不要为了和 `AiProvider::stream_chat` 对称而引入 `AiFuture`。embedding 没有流式、没有取消粒度，同步更简单。

在 `AiProvider` 上**加一个带默认实现的方法**，用于 PDF 拆分（详见 §7.4）：

```rust
pub trait AiProvider: Send + Sync {
    fn stream_chat(&self, request: AiChatRequest, sink: AiDeltaSink, cancel: CancelFlag)
        -> AiFuture<Result<AiTurnResult, CoreError>>;

    /// 把一份 PDF 原始字节交给模型，让它读完并切成语块。**非流式、一次请求**。
    /// 默认返回「不支持」，Anthropic 与 OpenAI 兼容各自实现。
    /// 与 `stream_chat` 分开是刻意的：PDF 拆分不走历史、不走工具循环、
    /// 不进 `AiWireMessage`，复用对话通道会把 `trim_history` 和字符预算全带歪。
    fn split_document(&self, _req: DocumentSplitRequest) -> AiFuture<Result<SplitOutcome, CoreError>> {
        Box::pin(async { Err(CoreError::Ai("当前模型不支持文档输入".into())) })
    }
}

/// 送进模型「拆语块」的两种输入（决策 O-25）。
/// **PDF 与 PPTX 走同一个方法**，只是载荷不同：都不走对话历史、不走工具循环、不进 `AiWireMessage`。
pub enum SplitInput {
    /// PDF 原始字节。本地已按页切好（或整份未切，见 §7.4）。
    /// `first_page` 是批偏移，用于把模型返回的「第 N 页」换算成全局页码。
    Pdf { bytes: Vec<u8>, first_page: u32 },
    /// 纯文本（PPTX 的 `<a:t>` 机械抽取结果）。分批时给 part/total，
    /// 提示词据此告诉模型「这是第 i/N 批，首尾可能不完整」（§7.3.1）。
    Text { text: String, part: u32, total: u32 },
}

pub struct DocumentSplitRequest {
    pub input: SplitInput,
    pub model: String,
    /// 单批语块条数上限：防止模型一次吐几千块把 `max_tokens` 打满、JSON 截断成废串。
    pub max_chunks: u32,
}

pub struct SplitOutcome {
    pub chunks: Vec<SplitChunk>,
    /// 模型侧是否有截断迹象（`finish_reason = length`），用来决定「不重试也别假装成功」。
    pub truncated: bool,
}

pub struct SplitChunk {
    pub text: String,
    /// PDF 是「第 N 页」，PPTX 是「第 N 张幻灯片」。由模型写，本地只做批偏移换算。
    pub locator: Option<String>,
}
```

### 2.5 依赖变更与实测体积

```toml
# [workspace.dependencies]
candle-core = "0.11.1"     # 默认 features。**不要开 cuda / metal / accelerate / mkl**
candle-nn   = "0.11.1"
tokenizers  = "0.23.2"     # 默认 features 带入 oniguruma（C 库），MSVC 实测可编
quick-xml   = "0.42.0"     # docx / pptx
zip         = "9.6.1"      # docx / pptx 容器
lopdf       = "0.47.0"     # **只用来按页切 PDF**（不是提文本），见 §7.4
sqlite-vec  = "0.1.6"      # 向量虚表，纯 C 静态链接
notify-rust = "4.19.0"     # 系统通知
```

**本机实测**（x86_64-pc-windows-msvc / rustc 1.99.1 / `lto=thin` + `codegen-units=1`，
各探针**统一调用 `rusqlite`** 保证基线一致——这一点很重要，见下方警告）：

| 组件 | exe 增量 |
|---|---|
| `sqlite-vec` | **98 KB** |
| `zip` + `quick-xml`（docx/pptx） | **151 KB** |
| `lopdf`（PDF 切页） | **1.03 MB** |
| `zip`+`quick-xml`+`lopdf` 三者合测 | **1.99 MB**（比 0.151+1.03 高，共同依赖 inflate 等，**以合测为准**） |
| `notify-rust`（含 `tauri-winrt-notification`） | **109 KB** |
| `candle-core` + `candle-nn` + `tokenizers` | **4.47 MB** |
| **合计** | **约 6.7 MB**（32 MB → 38.7 MB） |

> ⚠️ **测量警告（踩过一次）**：如果探针 A 调了 `rusqlite`、探针 B 没调，LTO 会把 SQLite 整个从 B 里裁掉，两边的差值就不是「B 的依赖成本」，而是「B 的依赖成本 − 1.4 MB SQLite」。
> 第一轮我就这么测了，得出 `candle` 只有 2.88 MB、`lopdf`+`zip`+`quick-xml` 只有 410 KB —— **都是低估**。重新统一基线后是 4.47 MB 与 1.99 MB。
> 以后再加依赖，探针里务必都写一句 `Connection::open_in_memory()`。

## 6. 批次 3：知识库数据层（schema v9）

### 6.1 迁移实现

照 `migrate_v7_to_v8`（[migrations.rs:914](../../crates/me-store/src/migrations.rs)）的形状：

```rust
/// v8 → v9：纯建表。不动任何既有表、不加列、不改索引。
fn migrate_v8_to_v9(conn: &mut Connection) -> Result<(), CoreError> {
    const TARGET: u32 = 9;
    let tx = conn
        .transaction()
        .map_err(|e| storage(format!("开始 v8→v9 迁移事务失败: {e}")))?;

    tx.execute_batch(SCHEMA_V9_DDL)
        .map_err(|e| storage(format!("执行 v8→v9 迁移失败: {e}")))?;

    // 版本号写 meta 表，不是 PRAGMA user_version —— 照 migrate_v7_to_v8 的实际写法。
    tx.execute(
        "UPDATE meta SET value = ?1 WHERE key = 'schema_version'",
        params![TARGET.to_string()],
    )
    .map_err(|e| storage(format!("写入 schema_version 失败: {e}")))?;

    check_foreign_keys(&tx)?;
    tx.commit()
        .map_err(|e| storage(format!("提交 v8→v9 迁移失败: {e}")))?;
    Ok(())
}
```

- DDL 全部用 `IF NOT EXISTS`
- `me-core/src/lib.rs:88` 的 `SCHEMA_VERSION` 改 9
- **新库走累积式 DDL**：`create_schema`（migrations.rs:589）按 `V2 → V3 → V7 → **V9**` 顺序 `execute_batch`。v8 只是加列、新库由 `SCHEMA_V3_DDL` 带上；**v9 是新建表，必须显式加进这条链**，否则新装用户没有知识库表

- 新建 `crates/me-store/tests/migration_v8_v9.rs`：v8 库 → 迁移 → 断言 4 个对象存在、既有表行数不变、`schema_version == 9`；另加「全新库一次建到 v9」用例

### 6.2 向量库挂载（本批次最容易翻车的地方）

**四条硬约束**：

**1. `sqlite3_auto_extension` 必须在任何 `Connection` 打开之前注册，且只注册一次。**

```rust
// crates/me-store/src/db.rs
use std::sync::Once;
static VEC_INIT: Once = Once::new();

pub fn register_sqlite_vec() {
    VEC_INIT.call_once(|| unsafe {
        rusqlite::ffi::sqlite3_auto_extension(Some(std::mem::transmute(
            sqlite_vec::sqlite3_vec_init as *const (),
        )));
    });
}
```

它是**进程级全局**的：忘了注册 → `no such module: vec0`；每个连接都调 → 每次开连接跑两遍 init。

**2. 写连接和 4 条只读连接都要 ATTACH。**

放在 `Store::open()` 的 PRAGMA 之后、schema 初始化之前：

```rust
conn.execute("ATTACH DATABASE ?1 AS kbvec", params![kb_db_path.to_string_lossy()])?;
conn.pragma_update(Some("kbvec"), "journal_mode", "WAL")?;
conn.pragma_update(Some("kbvec"), "busy_timeout", 5000)?;
```

**3. `vec0` 与普通 FTS5 都不吃外键级联 —— 删文档必须手动四步，且顺序不能反。**

**四步，顺序不能反**（决策 O-26）。`vec0` 没有外键，普通 FTS5 也没有——两者都靠 `chunk_id` 定位，一旦 `kb_chunks` 被 CASCADE 删掉，就**再也找不到它们**，只能留下「搜得到但点不开」的幽灵结果：

```rust
// 唯入口：delete_doc_deep(doc_id)。所有删除路径（用户删文档、超容量清理、
// 邮件级联、AI 的 kb_delete）都调它，别在别处自己拼 SQL。
fn delete_doc_deep(&mut self, doc_id: i64) -> Result<(), CoreError> {
    let tx = self.conn.transaction()?;
    // 1) 先收 chunk id —— 这一步必须最先做，后面两步都靠它
    let ids: Vec<i64> = tx.prepare("SELECT id FROM kb_chunks WHERE doc_id = ?1")?
        .query_map([doc_id], |r| r.get(0))?.collect::<Result<_, _>>()?;
    for chunk in &ids {
        // 2) 删向量（另一个库文件）
        tx.execute("DELETE FROM kbvec.vec_chunks WHERE chunk_id = ?1", [chunk])?;
        // 3) 删 FTS 行（普通 FTS5 不会跟着 CASCADE）
        tx.execute("DELETE FROM kb_chunks_fts WHERE rowid = ?1", [chunk])?;
    }
    // 4) 最后删文档：kb_chunks / kb_doc_entities 走 CASCADE
    tx.execute("DELETE FROM kb_documents WHERE id = ?1", [doc_id])?;
    tx.commit()
}
```

**`mail_id` 的 `ON DELETE CASCADE` 会绕过这个函数** —— SQLite 自己删 `kb_documents` 行时不经过我们。所以删邮件必须**先** `delete_doc_deep` 每一份关联文档，**再**删 `messages`。写一个 `purge_mail(&[MessageId])` 把这条包住，所有删邮件的路径只准调它（§8.1）。**这是 `mail_id` 外键唯一的副作用，别漏。**

**4. `quick_check` 只查主库。**
`ensure_vector_store()` 对 `kbvec` 单独 `PRAGMA kbvec.quick_check`，失败就**重命名坏文件 + 重建空库**，把 `embedded=1` 的批量改回 0 让它们重新向量化。别散在 `open` 里。

建表语句（`vec0` 维度**建表时固定**，`distance_metric` 写在列上）：

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS kbvec.vec_chunks USING vec0(
    chunk_id INTEGER PRIMARY KEY,
    embedding float[512] distance_metric=cosine
);
```

- 主键用外部 `kb_chunks.id`，**不要 `AUTOINCREMENT`**
- `distance_metric=cosine` 返回 `1 - cosine_similarity`，**越小越相似**，按 `distance` 升序
- 同表写两个 `distance_metric=` 会报错（源码有校验）

```sql
SELECT chunk_id, distance FROM kbvec.vec_chunks
WHERE embedding MATCH ?1 AND k = 40 ORDER BY distance;
```

### 6.3 仓储实现

新建 `crates/me-store/src/knowledge.rs`，照 `ai.rs` 的形状（`impl WritableStore` + `impl ReadOnlyRepo`）。

只读侧限制不变：`me-app` 只拿 `ReadOnlyStore`，所以 `ReadOnlyRepo` 只加 `list_knowledge` / `knowledge_doc` / `knowledge_chunks`，**`LIMIT ≤ 200`**（CLAUDE.md 明写），且**只读侧不做 FTS / KNN** —— 检索一律走 `Command::SearchKnowledge` → `me-sync` → `Event`。

```rust
pub fn put_vectors(&mut self, items: &[(KnowledgeChunkId, Vec<f32>)]) -> Result<(), CoreError> {
    let tx = self.conn.transaction()?;
    {
        // sqlite-vec 只收 f32 小端裸字节，不收 JSON

            "INSERT OR REPLACE INTO kbvec.vec_chunks(chunk_id, embedding) VALUES(?1, ?2)")?;

        }
    }
    tx.commit()?;
    Ok(())
}
```

### 6.4 FTS 的维护与中文处理（决策 O-20）

`kb_chunks_fts` 是**普通 FTS5**（不是外部内容表），插入与删除都要显式写。

**但真正要小心的是分词**。实测（本机 SQLite + FTS5）：

| 查询 | `tokenize='trigram'` | `unicode61` + 逐字空格 + 短语 |
|---|---|---|
| 合同（2 字） | **0** | **1** |
| 预算（2 字） | **0** | **1** |
| 审查（2 字） | **0** | **1** |
| 法务审查（原文连续 4 字） | 1 | 1 |
| 合同审查（原文不连续） | 0 | 0 |

**trigram 对中文基本失效**：2 字词全部搜不到（中文最常见的查询单位），4 字词只要不是原文连续子串也搜不到。所以 `kb_chunks_fts` 用 `unicode61`，配两个约定：

**写入时**把中文逐字空格化再进 FTS：

```rust
/// 把 CJK 字符之间插入空格，其余原样。ASCII 单词不动（`T-1000` 不能被拆开）。
fn fts_fold(text: &str) -> String {
    let mut out = String::with_capacity(text.len() * 2);
    let mut prev_cjk = false;
    for ch in text.chars() {
        let cjk = is_cjk(ch);
        if cjk && prev_cjk { out.push(' '); }
        out.push(ch);
        prev_cjk = cjk;
    }
    out
}
```

`kb_chunks.text` 存**原文**，只有 `kb_chunks_fts.text` 存折叠后的版本——检索结果要回显原文。

> **`is_cjk` 别抄第三份**：现在已经有两份了（`me-core/src/ai.rs:2321`、`me-store/src/cache.rs:143`）。开工时把它提到 `me-core/src/text.rs`（`pub fn is_cjk`）两处改为引用，`knowledge.rs` 直接用。`is_common_punct` 目前**不存在**，要新写。

**查询时**同样折叠，并用**短语语法**包起来：

```rust
// "合同" -> "\"合 同\""  ：phrase query 要求相邻，避免命中"合…同"任意共现
let phrase = format!("\"{}\"", fts_fold(query));
stmt.execute(params![phrase]);
```

- 短语语法保证「相邻」，等价于 trigram 的连续子串语义，但**没有 3 字符起步的限制**
- 查询里的 `"` 要转义（用户可能输入引号），照 `search.rs:escape_fts_query` 的做法
- 多关键词用空格分隔时，逐个折叠后仍按 phrase 处理，不要退化成 OR

**索引体积**：逐字切分会让 token 数约等于字数，索引约是文本的 1.5~2 倍。语块几千条、每条 400 字，总量 1~2 MB 级，可接受。

**只允许在 `knowledge.rs` 内的一个私有 helper 里做**，照 `search.rs` 开头的约定（「唯一负责 `messages_fts` 的 SQL」）。别让 `replace_chunks`、`delete_doc`、`purge_mail` 各写一份——漏一处就是「搜不到但列表里有」的诡异 bug。

> **附带的观察（不在本期范围）**：现有 `messages_fts` 也是 `trigram`，所以邮件搜索对中文有同样的毛病——搜「合同」搜不到正文，只能靠主题/发件人/收件人的 `LIKE` 兜底（`search.rs:299`）。这是 v0.4 留下的既有问题，本期不动，但要写进「已知缺口」清单，别让人以为是知识库引入的。

```text
   │                       │                  │
   └──► skipped ◄──────────┘                  │
   └──► failed  ◄─────────────────────────────┘
```

- `skipped`：内容无效（**正常结果**，不是错误）
- `failed`：IO / 解析 / 模型异常（带 `error`，可重试，`stage` 决定从哪步重试）

### 7.2 前置校验

**文件类**（`me-core/src/knowledge.rs` 纯函数 + `me-sync` 侧 IO 校验）：

1. 存在、可读、非目录
2. 扩展名白名单：`md / markdown / txt / docx / pdf / pptx`（+ `doc / ppt` 走转换，见 §7.5）
3. **大小上限**：PDF **≤ 512 MB**（本地切页上限，见 §7.4）、其他 **≤ 50 MB**
4. **只有「本地拆分」的类型**（md / txt / docx）跑文本有效性判定：

```rust
pub enum SkipReason { Empty, TooShort, Garbled, ScannedPdf }

/// 判定本地提取出来的纯文本是否「包含信息」。**确定性规则，不用 LLM 判断**：
/// 可测试、零成本、结果稳定。
///
/// **只服务于本地拆分路径**（md / txt / docx）。PDF 与 PPTX 不走这里——
/// 它们的内容识别全量交给模型（决策 O-18），本地判一遍等于抢模型的活，
/// 而且规则判不准扫描件与图表页。
pub fn is_meaningful(text: &str) -> Result<(), SkipReason> {
    let t = text.trim();
    if t.is_empty() { return Err(SkipReason::Empty); }
    let effective = t.chars().filter(|c| !c.is_whitespace()).count();
    if effective < 40 { return Err(SkipReason::TooShort); }          // 封面页/空模板
    let meaningful = t.chars().filter(|c| {
        c.is_alphanumeric() || c.is_whitespace() || is_cjk(*c) || is_common_punct(*c)
    }).count();
    if (meaningful as f32) / (t.chars().count() as f32) < 0.30 {
        return Err(SkipReason::Garbled);                             // 提取出占位/乱码
    }
    let ctrl = t.chars().filter(|c| c.is_control() && *c != '\n' && *c != '\t').count();
    if (ctrl as f32) / (t.chars().count() as f32) > 0.05 { return Err(SkipReason::Garbled); }
    Ok(())
}
```

阈值是**可调常量**，放同模块顶部并注释来由。**必须配单测**：正常中英文、空串、纯空白、纯乱码各一条。

**PDF 与 PPTX 都不走这个判定**（决策 O-18）：本地拿到的东西不算「识别结果」——PDF 是原始字节，PPTX 是机械抽取的 `<a:t>` 文本。两者的有效性由模型返回决定：**模型返回空数组 → `skipped`**。

> 注意 `SkipReason::ScannedPdf` 这个变体：全量交给模型后，本地不会再产生它。保留是因为模型可能返回「该文档为扫描件且无可读内容」，那时用它回填 `skip_reason`，UI 上的文案是统一的。

### 7.3 按类型的处理策略（决策 O-03 / O-12 / O-15 / O-18 / O-19）

| 类型 | 内容获取 | 语块边界由谁定 | 本地切分（仅装不下时） |
|---|---|---|---|
| `.md` `.txt` | 读文件（UTF-8，失败试 GBK） | **本地**结构拆 | 不切 |
| `.docx` | `zip` 解 `word/document.xml`，`quick-xml` 取 `<w:p>` | **本地**结构拆 | 不切 |
| `.pptx` | `zip` 解 `ppt/slides/slideN.xml`，取 `<a:t>` | **模型**（走 `split_document` 的 `Text` 变体） | 文本 > 4000 字时按段落边界切批 |
| `.pdf` | **不提取**，原始字节 | **模型** | > 100 页或 > **24 MB**（= 32 MB 请求体，见 O-28）时按页边界切批 |
| `.doc` | 转 `.docx`（§7.5） | 转完按 docx 走 | — |
| `.ppt` | 转 `.pptx`（§7.5） | 转完按 pptx 走 | — |
| 邮件正文 | 已有缓存 | **本地**结构拆 | 不切 |

#### 7.3.1 职责边界（决策 O-19）—— 这张表是本期的核心约定

**本地只做「装不下时的物理切分」，语块怎么划全归模型。**

| 环节 | 本地 | 模型 |
|---|---|---|
| 判断文档有没有实际内容 | — | ✅ |
| 理解版面 / 表格 / 图表 / 扫描件 | — | ✅ |
| 判断哪些文字是有意义的正文 | — | ✅ |
| **决定语块的边界（一句话 / 一个要点 / 一章）** | — | ✅ |
| **决定语块的长度** | — | ✅（提示词给 300~450 字区间，见 O-21） |
| 写 `locator`（第几页 / 第几段） | — | ✅ |
| 文件太大、一次请求装不下时，找个**安全位置**切开 | ✅ | — |
| 把切开的部分按顺序拼回去、重排 `ord` | ✅ | — |

**「安全位置」的定义**：

- **PDF**：按**页边界**切。页是不可分的物理单元，且模型能读到完整页面。
- **PPTX 文本**：按**段落 / 换行边界**切，不在句中切。
- 切点之后若落在句子中间，往回退到最近的段落边界——宁可少装几个字，也不要在句子中间断开。

**只在「过长」时才切**：

| 类型 | 不切的条件 | 切分阈值 |
|---|---|---|
| PDF | ≤ 100 页 **且** ≤ 24 MB | 100 页 / 24 MB（= 32 MB 请求体） |
| PPTX 文本 | ≤ 4000 字 | 4000 字 |
| md / txt / docx | 永远不切（本地拆分，不发给模型） | — |

> 4000 字这个阈值是**请求体积限制**，不是语块长度。语块长度由模型按提示词决定（**300~450 字**）。别把两个数字搞混——本地切完的那一批里，模型仍会拆出多个语块。
>
> ⚠️ 提示词里**不能写 600**：模型产出的语块会被直接送进嵌入，超过 480 字就撞上 bge 的 512 token 上限被**静默截断**（O-21）。提示词给 300~450、本地 MAX 480，留 30 字缓冲给模型偶尔超一点。

**跨批的边界问题**：分批后每批独立送模型，**批与批之间可能在语义中间被切断**。处理方式：

1. 切点尽量落在段落边界（上面说的「安全位置」）
2. 提示词里告诉模型「这是全文的第 i/N 批，开头/结尾可能不完整，按你看到的内容拆即可」
3. 合并时**不跨批合并语块**——只按批序拼接、全局重排 `ord` 与 `locator`
4. 接受少量边界处语义略断：4000 字 / 100 页的粒度下，这类损失远小于「本地自己猜语块边界」的错误率

**「识别全量交给模型」的准确含义（决策 O-18）**：

- **PDF**：本机只做**无损切页**（字节级搬运），内容理解、版面还原、扫描件识别、语块划分 **全部由模型完成**。
- **PPTX**：本机只做**机械文本抽取**（XML 里 `<a:t>` 节点的字符串拼接），不判断哪些是有意义的正文、不猜标题层级、不做页内版面重建——这些都由模型做。
- **本地代码里不存在任何「这段文字是什么」的判断**，只有「怎么把它搬出去」。
- **代价**：PDF 与 PPTX 都必须有可用模型，无模型则导入失败（不是降级），见 §7.4.1 的费用确认。

**为什么 docx 本地拆、pptx 走 LLM**：docx 的段落结构干净，本地切又快又稳；pptx 的页面语义是「一页一个要点」，文本按 XML 顺序拉出来是散的，需要模型重组。这是按需求「doc/md/txt 直接拆、pdf/ppt 用 LLM」落的。

本地结构拆的统一参数（`me-core/src/knowledge.rs` 顶部，**只用于 md/txt/docx/邮件**）：

```rust
pub const TARGET_CHUNK_CHARS: usize = 400;   // 目标语块长度（中文按字，不按 token）
pub const MAX_CHUNK_CHARS: usize    = 480;   // 硬上限，超了强制切
pub const CHUNK_OVERLAP_CHARS: usize = 60;   // 相邻块重叠，避免切断语义
```

**为什么是 480 而不是 600**（决策 O-21）：bge-small-zh 用的是中文**逐字** tokenizer，600 个汉字约等于 600 个 token，加上 `[CLS]` / `[SEP]` 已经超过 512 的位置编码上限，**尾部会被静默截断**——块尾的文字永远不会参与检索，而且没有任何报错。480 字 + 特殊 token 正好卡在 512 以内，永不截断。

代价：块数比 600 字方案多约 25%，向量库与索引耗时同比例上升。这是为了「不丢内容」付的对价，值得。

按字符不按 token 仍然成立：tokenizer 编一条 400 字约 1 ms，几千块就是几秒，拆分阶段没必要付这个钱。

### 7.4 PDF：本地按页切分，分批交给 LLM（决策 O-15 / O-18 / O-19）

**只在过长时才切，切完整批交给模型。** `lopdf` 就是为这一件事引入的——只做无损切页，不做文本提取。

**100 页以内且 ≤ 24 MB 的 PDF 根本不切**，整份发出去。切分只是「装不下」的兜底手段，不是处理流程的固定一步（§7.3.1）。

```rust
pub const PDF_MAX_BATCH_PAGES: u32 = 100;         // 单批页数（Anthropic 硬限）
/// 32 MB 是**请求体**上限，不是原文件上限（决策 O-28）。
/// base64 让体积涨 4/3，所以原文件只能到 24 MB —— 用 24 而不是 32/1.34=23.9 的精确值，
/// 是为了给 JSON 外壳留 100 KB 余量。
pub const PDF_MAX_REQUEST_BYTES: u64 = 32 << 20;
pub const PDF_MAX_RAW_BYTES: u64 = 24 << 20;      // 单批原文件上限
pub const PDF_MAX_LOCAL_BYTES: u64 = 512 << 20;   // 本地切分上限，超过才拒绝
```

流程：

1. `Document::load` 拿总页数（`get_pages().len()`）——这步解析整个文件，**必须放 `spawn_blocking`**
2. 批数 = `ceil(N / 100)`；若 `单批原文件大小 > 24 MB`（扫描件常见），按 `24MB / 平均每页字节` 反推更小的每批页数再算批数。
   **判断的是原文件字节，不是 base64 后的体积**——但 24 MB 这个数已经是「32 MB 请求体 ÷ 4/3」的结果，别在这里再乘一次 1.34
3. 逐批：
   - **重新 `Document::load`**，不要 `clone`——避免两份文档同时在内存（300 页扫描件能吃掉几百 MB）
   - `delete_pages(除本批之外的所有页号)`
   - `save` 到 `kb/tmp/<doc_id>-p{i}.pdf`
   - **切完立刻自检**：重新 `load` 这个临时文件，断言 `get_pages().len() == 本批预期页数`。
     不相等说明 `delete_pages` 破坏了结构 —— 放弃切分，按「切页失败」处理（见下）
   - 自检通过后才以 PDF 原文件形态发给模型
   - **删临时文件，失败路径也要删**
4. 合并各批语块：`locator` 换成全局页码（批内页 + 批偏移），`ord` 重新连续编号
5. 任一批失败 → 整个文档 `failed`，`error` 带上「第 i/N 批失败」——不要留下半份语块

**不要调 `prune_objects`**：它可能删掉被保留页共享的资源（字体、图片 XObject），导致子文档渲染成空白。只 `delete_pages` + `save`，临时文件偏大但内容安全。

**成本随页数线性增长**，导入前就能估算（页数本地可见，不用调模型）：

| 页数 | 批数 | input token（按 2000/页估） | 约合（Claude Sonnet $3/M） |
|---|---|---|---|
| 50 | 1 | ~100k | $0.3 |
| 300 | 3 | ~600k | **$1.8** |
| 1000 | 10 | ~2M | **$6.0** |

所以导入前要弹一句预估：「约 300 页，将分 3 批发送，预计花费 $1.8」——这是用户唯一能拦住意外账单的机会。

**性能**：`Document::load` 对 32 MB 文件约 0.5~2 s，300 页 3 批 ≈ 5~8 s（含两次重新解析）。可接受，但全在后台。

**异常**：

- **加密 / 损坏的 PDF**：`load` 失败 → `failed`，错误写「PDF 已加密或损坏，无法读取」
- **单页 5 MB 的扫描件**：100 页就是 500 MB，单批必超 24 MB → 按大小反推批页数（上面第 2 步），退化到**每批 4 页**，批数变多、成本不变（成本按页算，不按批算）
- **> 512 MB**：只有这种才拒绝，提示「文件过大，请先拆分」
- **切页自检不过（页数不符 / 重新加载失败）**：不硬着头皮发半成品。
  退路只有一条——**若原文件 ≤ 32 MB 就整份发**（放弃切分，可能超页数导致模型报错，但至少内容完整）；
  原文件本身 > 32 MB 则 `failed`，错误写「该 PDF 结构特殊，无法在本地拆分」
- **`lopdf` 对加密 PDF 会加载失败**，对线性化 / 对象流 / 增量更新的 PDF 支持有限。
  这些是已知能力边界，不要试图用 `prune_objects` 或手改对象表去兜——越兜越容易产出空白页

**请求形态**（在 `AiProvider::split_document` 里，不走 `stream_chat`）：

```jsonc
// Anthropic
{"model": "...", "max_tokens": 8192, "messages": [{
  "role": "user",
  "content": [
    {"type": "document", "source": {"type": "base64",
      "media_type": "application/pdf", "data": "<base64>"}},
    {"type": "text", "text": "<KB_PDF_SPLIT_PROMPT>"}
  ]}]}

// OpenAI 兼容（多数端点不支持，失败时如实透传错误）
{"messages": [{"role": "user", "content": [
  {"type": "file", "file": {"filename": "part-1.pdf",
    "file_data": "data:application/pdf;base64,<...>"}},
  {"type": "text", "text": "<KB_PDF_SPLIT_PROMPT>"}

```

**能力位**：`AiModel` 加 `pdf_input: bool`，`#[serde(default)]`（老档案不炸——`tools` 字段已经踩过这个坑：没有默认值时整份 `meta.ai_models` 解析失败，会静默清空用户的模型配置）。默认：Anthropic 新建档案 `true`，OpenAI 兼容 `false`，UI 可手动勾。

**提示词一次完成「读 + 切」**，省掉第二次调用：

```rust

要求：
- 每片 300~450 字，覆盖全文，不遗漏、不重复
- 不新增内容、不改写原意，忠实于原文
- 表格与图表用文字概述其结论
- 保留章节标题作为片段开头
只输出 JSON：{\"chunks\":[{\"text\":\"...\",\"locator\":\"第 N 页\"}]}，不要任何解释。";
```

**失败处理**：某批 JSON 解析失败**不重试**（PDF 单批很贵），整份文档 `failed`，把模型返回前 200 字放进 `error` 供排查。

**没配 AI = 导入不了 PDF/PPT**（决策 O-03）：不是降级成规则拆分，而是对话框里就拦住——对 pdf/pptx 显示「需要 AI 模型」并禁用。

#### 7.4.1 配置前的费用提示（决策 O-18）

用户明确要求：**在配置/首次使用阶段就要说清「会用大模型分析、会产生费用」**，不能等拆到一半才让人发现花钱了。做**两级**提示，职责不同：

**第一级 · 一次性总确认**（`meta.kb_llm_ack`，没确认过就弹）：

```text
PDF / PPT 需要大语言模型分析

这类文档无法在本地可靠地识别内容。导入后，整份文件会发送给
「{当前模型名}」进行分析并切成语块。

· 文档内容会离开本机，发送给模型服务商
· 按页计费，索引完成后不再产生费用
· 参考价：约 $0.006/页（一本 300 页文档约 $1.8）

[我已了解，继续]      [改用其它格式]
```

- 「我已了解，继续」→ 写 `meta.kb_llm_ack = 1`，**之后不再弹**
- 「改用其它格式」→ 不写标记，只关对话框（用户下次还会看到）。这不是「拒绝」，因为我们无权替他转格式
- **费用与隐私写在同一个框里**：不要拆成两个框（「内容会发给第三方」+「会产生费用」），分散的确认更可能被无脑点掉

**第二级 · 每次导入的预估**（每份 pdf/pptx 都显示，**不可永久关闭**）：

```text
将发送 300 页，分 3 批
预计消耗约 450k ~ 900k token · 约 $1.4 ~ $2.7
[开始导入]   [取消]
```

页数从 `Document::get_pages()` **本地**拿到，不用调模型就能算。这个预估是用户唯一能在出账单前拦住的机会，不能省。

**估算函数**（`me-core/src/knowledge.rs`，纯函数、要单测）：

```rust
pub const TOKENS_PER_PAGE_LOW: u32 = 1500;
pub const TOKENS_PER_PAGE_HIGH: u32 = 3000;

/// 只用来给用户一个量级，**不当计费依据**。
/// 给区间而不是一个数：不同模型、不同版面差异很大，假精确比区间更误导。
pub fn estimate_pdf_tokens(pages: u32) -> (u32, u32) {
    (pages * TOKENS_PER_PAGE_LOW, pages * TOKENS_PER_PAGE_HIGH)
}
```

**价格从哪来**：`AiModel` 不加价格字段（会让档案变复杂、且价格随时变）。用 `me-core` 里一张**内置参考价常量表**，按 `model` 字符串前缀匹配；匹配不到就**不显示美元数**，只显示 token 区间 + 「以服务商账单为准」。宁可少说，不要瞎说。

**PPTX 同理**：抽取的文本**超过 4000 字才**分批（按段落边界切），预估文案换成「共 N 字，分 M 批」。

**走同一条通道**（决策 O-25）：PPTX 用 `split_document` 的 `SplitInput::Text`，**不要走 `stream_chat`**。走对话通道的话，split 请求会进会话历史、受 `trim_history` 与字符预算裁剪，还可能触发工具循环——三条都是隐性污染，排查起来极难。
注意 4000 字是**请求体积**阈值，不是语块长度——按 300~450 字/块算，切出来的每一批里模型仍会拆出 **9~13 个**语块（§7.3.1）。

### 7.5 老格式转换（决策 O-12 / O-17）

`.doc` / `.ppt` 按**优先级**探测外部转换器，不自己解析 OLE：

| 优先级 | 后端 | 前提 | 质量 |
|---|---|---|---|
| 1 | LibreOffice `soffice --headless --convert-to` | 装了 LibreOffice | 最好，跨平台 |
| 2 | Office COM（内嵌 PowerShell 脚本） | Windows + 装了 Office | 好，用的是 Office 自己的排版引擎 |
| 3 | 都没有 | — | `failed`，提示装其中一个 |

**COM 用内嵌脚本**（字符串常量，运行期写到 `kb/tmp/convert.ps1`），Windows 一定带 PowerShell，不需要用户额外装东西：

```powershell
param($Src, $Dst)
$app = New-Object -ComObject Word.Application
$app.Visible = $false
$doc = $app.Documents.Open($Src, $false, $true)
$doc.SaveAs2($Dst, 16)   # 16 = wdFormatXMLDocument (.docx)
$doc.Close($false)
$app.Quit()
```

PowerPoint 同构：`PowerPoint.Application` → `Presentations.Open` → `SaveAs($Dst, 24)`。

实现要点：

- **一律 `Command::new(...).arg()` 逐参数传**，绝不拼命令行字符串——路径里有空格或引号会被 shell 解释，等于给自己开一个命令注入的口子
- **超时 8 分钟**，超时 kill 并报错。Word 弹出「文件已损坏，是否修复」这类对话框会永久挂住子进程
- 转换产物与脚本都放 `kb/tmp/`，**成功/失败/超时三条路径都要删**（写 guard，别靠人工记得）
- `kb/tmp/` 启动时清空一次（上次异常退出会留残留）
- 探测结果**缓存进 `meta`**（`kb_converter = soffice|office|none`），避免每次导入都跑一遍探测；设置页给「重新检测」按钮

**为什么不写纯 Rust**：OLE 复合文档 + Word 二进制（FIB / piece table）实现量以千行计且极易出错，为一个边缘格式不值得。用系统已有的转换器是正解（O-17 明确允许「其它语言实现」）。

### 7.6 语块落盘

`<root>/kb/chunks/<doc_id>.jsonl`，一行一块：

```json
{"ord":0,"locator":"第 1 章","chars":412,"text":"……"}
```

- **只有 `origin IN ('file','ai')` 落盘**（决策 O-27）。`mail` 来源**不写文件**：正文本来就在库里，重建时直接从 `messages` 取；5000 封邮件就是 5000 个几 KB 的小文件，纯属重复且拖慢目录遍历与备份。
- 先写 `kb/staging/<doc_id>.jsonl.tmp`，flush + `sync_all` 后 `fs::rename`（原子替换）
- **同时写数据库**。`kb_chunks.text` 与文件重复，是**有意的冗余**：
  - 表是检索路径（不读文件，避免检索时几十次小 IO）
  - 文件是用户可见物 + 可重建源（不重新解析原 PDF 也能重建索引）
- 重建时**先读文件**，文件不存在或与 `chunk_count` 不符才重新走原文档

### 7.7 向量化

- 批量 **16 块/批**（candle 单条 20~50 ms）
- 跳过已完成：`WHERE doc_id = ?1 AND embedded = 0`
- 全部完成：`status='embedded'`、`embed_model`、`embed_dim` 写回
- 换模型（`model_id` 不等）→ 必须重建，不能混用两种向量

#### 7.7.1 嵌入的四个细节（写错一个，召回就废，而且不报错）

**1. Pooling 必须是 CLS，不是 mean。**
BGE 系列用 `[CLS]` 位置的 hidden state 做句向量。用 mean pooling 不会报错，向量照样是 512 维，但检索质量会明显下滑——这是最隐蔽的一类错误，因为它「看起来能跑」。

```rust
// candle：取 hidden_states 的第 0 个位置
let cls = hidden.narrow(1, 0, 1)?.squeeze(1)?;   // [batch, 512]
```

**2. 必须 L2 归一化。**
`vec0` 的 `distance_metric=cosine` 自己会算 cosine，但归一化后内积 = cosine，数值更稳、也便于以后换 metric。不归一化不会报错，但相似度分布会漂。

**3. Query 与 Document 不是同一种输入。**
BGE v1.5 官方建议给 **query** 加指令前缀（document 不加）：

```rust
pub const BGE_QUERY_PREFIX: &str = "为这个句子生成表示以用于检索相关文章：";
```

所以端口要**分成两个方法**，别用一个 `embed()` 糊过去：

```rust
pub trait Embedder: Send + Sync {
    fn model_id(&self) -> &str;
    fn dim(&self) -> usize;
    /// 索引路径：不加指令前缀。
    fn embed_documents(&self, texts: &[&str]) -> Result<Vec<Vec<f32>>, CoreError>;
    /// 查询路径：加指令前缀。**两处不能混用**，混了相似度会系统性偏低。
    fn embed_query(&self, query: &str) -> Result<Vec<f32>, CoreError>;
}
```

**4. 截断静默发生。**
tokenizer 对超过 512 token 的输入**不报错、直接截**。所以 §7.3 把语块上限压到 480 字（O-21）。另外实现时要在日志里记一条 `truncated=N`，N 不为 0 就说明分块参数算错了。

#### 7.7.2 双库写入顺序（决策 O-22）

SQLite 在 WAL 模式下**跨 ATTACH 库的提交不是原子的**：崩溃时可能主库提交了、`kb.sqlite` 没提交。所以顺序固定：

```text
1. INSERT OR REPLACE INTO kbvec.vec_chunks(...)   -- 先写向量
2. UPDATE kb_chunks SET embedded = 1 WHERE ...    -- 再标完成
```

反过来（先标 embedded=1 再写向量）崩溃时会留下「标记已完成但查不到向量」的块，**且永远不会被重跑**。

配合一条**启动自检**（`ensure_vector_store()` 里做，O-22）：

```sql
-- 标记为已向量化、但向量库里没有对应向量的块 -> 重置，让它们重跑
SELECT c.id FROM kb_chunks c
WHERE c.embedded = 1
  AND NOT EXISTS (SELECT 1 FROM kbvec.vec_chunks v WHERE v.chunk_id = c.id);
```

反向（有向量但 `embedded=0`）不用管：重跑是 `INSERT OR REPLACE`，幂等，只是多算一次。

自检只在**启动时**跑一次，语块上万条时这个查询也就几十毫秒；不要放到每批向量化里。

### 7.8 队列与限流（邮件自动入库的背压）

摄入是 CPU 密集（分词、推理）+ 磁盘写入，**不并发**：

```rust
// crates/me-sync/src/knowledge.rs
/// 全局只允许一个摄入任务在跑。用 Semaphore(1) 而不是 Governor——
/// 那个是 IMAP 连接预算，语义不同，别硬塞。
static INGEST: Semaphore = Semaphore::const_new(1);
```

`kb_documents.status = 'pending'` 本身就是队列，worker 每次取 `ORDER BY created_at LIMIT 1`，断点续传天然成立。

**邮件自动入库靠「容量」而不是「限速」来约束**（决策 O-16，见 §8.1）：用户设一个上限 N，只索引最新的 N 封。这样队列长度天然有界，不需要靠「空闲才跑」来兜底：

1. **每批 16 块之间 `yield_now`**，让出线程给 UI 与同步
2. **容量为 0 = 关闭**；调小容量立即触发一次清理（旧文档连带向量一起删）
3. **只索引值得索引的**：正文 ≥ 200 字（跳过空邮件、纯通知、回执）。这条**在摄入读正文时才判**，SQL 选不出来，
   所以「窗口 N 封」与「最终 `embedded` 数」不相等；UI 的分母用窗口大小，`skipped` 单列一栏，别混成「失败」
4. **`content_hash` 去重**：正文没变就不重跑
5. 仍然建议**手动导入优先于邮件队列**，用户主动导入时把邮件任务让出去

不同容量对应的真实代价（单核 20~50 ms/块，按每封 3 块估）：

| 容量（封） | 语块数 | 首次建索引 | 向量库占用（f32 512 维） |
|---|---|---|---|
| 100 | ~300 | ~1 分钟 | ~0.6 MB |
| **200（默认）** | ~600 | **~2 分钟** | **~1.2 MB** |
| 500 | ~1500 | ~5 分钟 | ~3 MB |
| 1000 | ~3000 | ~10 分钟 | ~6 MB |
| 5000 | ~15000 | ~50 分钟 | ~30 MB |

这张表就是给设置页用的：用户把滑块从 200 拉到 5000 时，旁边要能显示「预计 50 分钟、占用 30 MB」，别让他事后才发现。

### 7.9 验收

- 导入 md：秒级完成，语块文件出现，`status=embedded`
- 导入 `.doc` 且没有任何转换器：`failed`，提示装 LibreOffice 或 Office
- 导入 `.doc` 且装了 Office：转成 docx 后正常入库，`kb/tmp/` 里**没有残留脚本或中间文件**
- 导入 50 页 PDF 且没配 AI：**对话框阶段**就拦住，不进入导入
- 导入 50 页 PDF 且配了 Anthropic：1 批发完，`splitter=llm`，`locator` 是页码
- **导入 300 页 / 30 MB 的 PDF：按页数切成 3 批（每批 100 页），语块连续、`locator` 页码跨批连续**（决策 O-15 的核心验收点）
- **导入 300 页 / 200 MB 的扫描件：按体积反推成每批约 36 页、共约 9 批**——验的是「体积先于页数成为约束」这条分支，上面那条验的是「页数是约束」
- **导入一份「本地看起来是乱码、模型却能读」的 pptx：正常入库**——这条专门验 O-18：如果本地还在跑 `is_meaningful`，它会被误判成 `skipped`
- **模型返回空数组时 → `skipped`，不是 `failed`**（PDF/PPTX 的有效性由模型判定）
- **50 页 PDF 整份发出，本地不发生任何切页**（未超阈值就不切，`kb/tmp/` 里没有中间文件）
- **1 万字的 pptx 按段落切成 3 批，每批里模型各自拆出多个语块**，合并后 `ord` 连续、不跨批合并
- 导入中途杀进程，`kb/tmp/` 有残留，重启后被清空，且不重复向量化已完成块
- 语块文件与 `kb_chunks` 行数一致，`ord` 从 0 连续

## 8. 批次 5：邮件自动入库 + 实体匹配

### 8.1 邮件自动入库（决策 O-08）

**触发点**：`me-sync` 完成一批正文补全 / 同步收尾时，按**容量窗口**挑邮件入库（决策 O-16）。

**容量窗口**：设置页给一个数字 N（默认 **200**；`0` = 关闭；可选 100 / 200 / 500 / 1000 / 5000），含义是「只索引最新的前 N 封」。这样队列长度天然有界，**不再需要靠「空闲才跑」兜底几小时的首次索引**。

**N 是全局总量，不是每账户**（决策 O-23）：多账户时按 `date` 全局排序取前 N，可能被一个活跃邮箱占满（工作邮箱一天几十封，个人邮箱几周一封）。所以：

- UI 必须显示分配：「其中 work@ 150 封、me@ 50 封」
- 某个账户**一封都没进窗口**时给一行提示，别让用户以为那个账户的邮件搜不到是 bug
- 不按账户平均分：公平分配会让不常用的账户白占名额，而用户真正要的是「我最近关心的邮件」

```sql
-- 「最新」按 date 排（收信时间），不是入库时间。
-- body_path IS NULL 表示正文未缓存，跳过（索引空正文没有意义）。
SELECT m.id FROM messages m
WHERE m.body_path IS NOT NULL
ORDER BY COALESCE(m.date, 0) DESC, m.id DESC
LIMIT ?capacity;
```

逐封 upsert：

```sql
INSERT INTO kb_documents(origin, source_ref, title, kind, mail_id, content_hash,
                         status, created_at, updated_at)
VALUES ('mail', CAST(?message_id AS TEXT), ?subject, 'mail', ?message_id, ?hash,
        'pending', ?now, ?now)
ON CONFLICT(origin, source_ref) DO UPDATE SET
  content_hash = excluded.content_hash,
  updated_at   = excluded.updated_at,
  status       = CASE WHEN kb_documents.content_hash = excluded.content_hash
                      THEN kb_documents.status ELSE 'pending' END;
```

- **`source_ref` 必须是消息 id 的字符串**，不能留空：冲突目标用的是 `UNIQUE(origin, source_ref)`，空串会让所有邮件记录互撞（见 §2.1 的 DDL 注释）。`mail_id` 只承担级联删除，不参与去重。
- `content_hash` 不变 → 保持原状态（不重跑）
- 变了（补全后正文更新）→ 重置 `pending`
- `title` 用 `subject`，空则用「(无主题) · 发件人」

**超容量清理**（每次入库后跑一次，以及容量调小时立即跑）。窗口外的旧文档要连带向量一起清掉，否则「容量」只是个空承诺：

```sql
-- 用 NOT EXISTS 而不是 NOT IN：mail_id 可空，NOT IN 遇到 NULL 会返回空集，
-- 结果是「一条都删不掉」，最难查的那种 bug。
SELECT d.id FROM kb_documents d
WHERE d.origin = 'mail'
  AND NOT EXISTS (
    SELECT 1 FROM (
      SELECT m.id FROM messages m
      WHERE m.body_path IS NOT NULL
      ORDER BY COALESCE(m.date, 0) DESC, m.id DESC
      LIMIT ?capacity
    ) w WHERE w.id = d.mail_id
  );
```

拿到 id 列表后：**逐份调 `delete_doc_deep`**（§6.2 坑 3 的四步）。不要写成「先删 `kb_documents` 让级联收尾」——向量与 FTS 都不吃级联。

清理是**惰性**的——不要每入库一封就扫一遍全表，攒到批尾或容量变更时做一次即可。

**删除级联的两条路径**（都必须处理）：

| 路径 | 行为 |
|---|---|
| 用户删单封邮件 | 查 `kb_documents WHERE mail_id = ?` → 逐份 `delete_doc_deep`（§6.2 坑 3 的四步）→ **再**删消息 |
| 用户删整个文件夹 | 同上，只是第一批查询换成 `mail_id IN (SELECT id FROM messages WHERE folder_id = ?)` |

> 不要指望 `ON DELETE CASCADE` 替你清理：它只会删掉 `kb_documents` 行，**向量与 FTS 都会留在原地**，而且删完就再也拿不到 chunk_id。级联在这里只是「兜底别留孤儿文档」，清理必须自己先做。

**目录切换/账户删除**同理。写一个 `purge_mail(&[MessageId])` helper（内部循环 `delete_doc_deep`），所有删邮件的路径都调它。

**UI**：

- 知识库列表默认**不显示** `origin='mail'`（几千条会把列表淹掉），用来源筛选器切过去
- 设置页「知识库」分组给一个**容量下拉**（关闭 / 最近 100 / 200 / 500 / 1000 / 5000 封），旁边实时显示预估：「约 600 个语块 · 首次约 2 分钟 · 占用约 1.2 MB」（数据来自 §7.8 那张表）
- 调小容量 → 立即触发一次清理，弹一句「将移除超出上限的 N 封邮件的索引」，不要静默删
- 顶部显示当前进度「已索引 180 / 200 封」

### 8.2 与记忆实体表匹配（需求 1.c）

**方向是「文档 → 已知实体」，不是「从文档发现新实体」。**

```rust
/// 在语块文本里找已知实体。返回命中的 entity_id。
/// 用简单包含匹配：实体几百个、语块几万条，release 下是百毫秒级，
/// 不值得为它引入 Aho-Corasick。
pub fn match_entities(text_lower: &str, aliases: &[(String, i64)]) -> Vec<i64> { ... }
```

- 来源：`ai_entities.canonical_name` + `ai_entity_aliases.alias`，各自 `normalize_entity_name` 后小写
- **按长度降序排序再匹配** —— 中文里「张三」会先命中「张三丰」的一部分，这个坑很常见
- 结果写 `kb_doc_entities`，`hits` 是**命中语块数**（不是出现次数，避免长文档被一个词刷屏）
- 时机：**拆分完成、向量化之前**（语块文本已就绪，不用再读文件）
- PDF 的语块来自 LLM 返回，同样适用

用途：详情页显示「涉及：张三、XX 项目」；`kb_search` 结果带实体标签；query 命中实体时对相关文档加权。

## 9. 批次 6：RAG 召回 + AI 工具

### 9.1 混合检索

```text
query
 ├─ FTS5 unicode61（kb_chunks_fts）──► top 40 （关键词命中；2 字词靠 phrase，见 §6.4）
 └─ embed(query) → vec0 KNN cosine ─► top 40   （语义相近）
            ↓
      RRF 融合（k = 60）→ top 8 → 拼进上下文
```

```rust
/// RRF：只看排名不看分数，天然规避「BM25 分数与 cosine 距离量纲不同」。
fn rrf(fts: &[ChunkHit], vec: &[ChunkHit], k: f32) -> Vec<ScoredHit> {
    let mut score: HashMap<KnowledgeChunkId, f32> = HashMap::new();
    for (rank, hit) in fts.iter().enumerate() {
        *score.entry(hit.chunk).or_default() += 1.0 / (k + rank as f32 + 1.0);
    }
    for (rank, hit) in vec.iter().enumerate() {
        *score.entry(hit.chunk).or_default() += 1.0 / (k + rank as f32 + 1.0);
    }
    ...
}
```

**降级是正常路径不是异常**：模型未就绪（`meta.kb_embed_model` 空 / 目录缺失）→ 只跑 FTS，标 `mode = fts_only`。用户拒绝下载模型时应用要照常用。

**上下文预算**：8 块 × 480 字 ≈ 3840 字 + 标题定位，控在 5000 字内，复用 `build_chat_request` 现有字符预算。

| 「去年 Q3 的预算超支原因」 | 季度复盘.md | 第 7 块 | 单文档精确 |
| …… | | | |

覆盖四类，各 5 条：

1. **单文档精确查询**——答案在一份文档的一个块里
2. **跨文档综合**——答案需要两份文档（检验 top-8 能不能同时捞回）
3. **专有名词 / 编号 / 型号**——`T-1000`、`HT-2024-07` 这类，检验 FTS 通路（O-20 换了 tokenizer 后能不能搜到）
4. **同义改写**——问法与原文用词不同（「离职流程」vs「员工退出机制」），检验向量通路

**跑法**（需要真实模型 + 固定语料，所以标 `#[ignore]`）：

```bash
# 语料：crates/me-sync/tests/fixtures/kb/ 下放 5 份文档
cargo test -p me-sync --test retrieval_eval -- --ignored --nocapture
```

**指标只有三个**，别贪多（20 条样本算 MRR / NDCG 没有统计意义）：

| 指标 | 目标 | 不达标怎么办 |
|---|---|---|
| `Hit@8`（期望块落在 top-8 的比例） | **≥ 0.85** | 先看是哪一类失败：专有名词失败 → FTS 问题；同义改写失败 → 嵌入问题 |
| 三路对比：`FTS only` / `KNN only` / `RRF` | RRF ≥ 两者 | 若 RRF 不如单路，说明融合权重或 k 值错了 |
| 块尾召回（专测 480 字截断，O-21） | 全中 | 若有失败，说明还有更长的块没被切到 |

**RRF 的 `k = 60` 是文献默认值，不是定论**。`k` 小偏重头部（top-1 很重），`k` 大偏重长尾（各名次权重接近）。用这个评测集跑 `k ∈ {10, 30, 60, 100}` 四组，选 `Hit@8` 最高的。**不要照抄 60 就完事**。

## 12. 体积与性能预算（实测基线）

| 项 | 数值 | 来源 |
|---|---|---|
| exe 增量 | **约 6.7 MB**（32 → 38.7 MB） | 本机 A/B 编译（统一基线） |
| ├ `sqlite-vec` | 98 KB | 同上 |
| ├ `zip` + `quick-xml` + `lopdf` | **1.99 MB**（三者合测） | 同上 |
| ├ `notify-rust` | 109 KB | 同上 |
| └ `candle` + `tokenizers` | **4.47 MB** | 同上 |
| 模型文件（外置） | **96 MB** | 24M 参数 × 4 字节 fp32 |
| 向量库（容量 200 封 ≈ 600 块） | **~1.2 MB** | 512 维 f32 = 2 KB/块 |
| 向量库（容量 5000 封 ≈ 1.5 万块） | **~30 MB** | 同上 |
| 首次建索引（容量 200） | **~2 分钟**（单核） | 每块 20~50 ms |

**向量库不再是个问题**：容量机制（O-16）把上限定在用户手里。默认 200 封 ≈ 1.2 MB，即使拉到 5000 封也就 30 MB。之前按「全量 5 万封」算出来的 300 MB 场景已经不存在了——这也反过来证明容量机制比「限速跑全量」更对：**约束规模比约束速度有效**。

**PDF 切分的代价不在体积，在时间**：`Document::load` 一次 0.5~2 秒（32 MB），300 页要 load 3 次。所以 §7.4 强调「重新 load 而不是 clone」是内存与时间的折中——clone 省时间但两份文档同时在内存，扫描件能吃掉几百 MB。

**candle 拿不到 int8 这件事再强调一次**：它的量化只覆盖 ggml 的 `QMatMul`（为 llama 的大线性层设计），BERT 的小矩阵要自己包。若哪天分发总量成硬指标，ONNX Runtime + int8 是「exe +20 MB / 模型 24 MB」的另一套账，总量反而更小。**本版按 candle 走，不要再翻这个案**（决策已定）。

### 15.3 后续修正的连带变化（消除了四个原先的坏消息）

| 原先的问题 | 现在 |
|---|---|
| >32 MB / >100 页的 PDF **无法导入** | 本地切分，**任意页数都能导**（上限 512 MB，只是批数变多、成本线性增长） |
| 首次开启要跑 **75 分钟**嵌入 | 容量默认 200 封 ≈ **2 分钟**，用户可自己加码 |
| 向量库会涨到 **300 MB** | 默认 **1.2 MB**，拉满 5000 封也才 30 MB |
| `.doc` 转换只认 LibreOffice（用户常没装） | 没装 LibreOffice 也能走 **Office COM**（Windows 自带 PowerShell） |

### 15.4 仍然需要知情的两个代价

1. **PDF / PPTX 全面依赖模型，并且要花钱**（决策 O-03 / O-18）。切分只解决「大文件」，不解决「没模型」；本地不做任何识别，所以没配 AI 就直接导入失败。费用侧已加两级确认（一次性总确认 + 每次导入预估），但用户仍可能低估——所以预估框**不提供「不再提示」**。
2. **PDF 成本随页数线性涨**：300 页约 $1.8、1000 页约 $6。这是预算量级，实际以服务商账单为准；匹配不到内置价表的模型**不显示美元数**，只说 token 区间。
