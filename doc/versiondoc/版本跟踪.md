# MyEmail 版本跟踪

> 用途：**按版本追踪功能的增加与删除**，让「这个能力从哪一版开始有 / 哪一版没了」有唯一答案。
> 编写日期：2026-11-18　|　覆盖版本：v0.1 → v0.4（0.4.0）+ 未定版增量 + **v0.5（批 1/2/3/4/5/6/7/8 全部完成）**　|　当前 `SCHEMA_VERSION = 9`
>
> **本表以代码为准，不以规划文档为准。** 规划里写了但代码里没有的，一律进「计划未落地」，
> 不进「新增」；代码里有但规划里没写的，照实记「实施期新增」。

## 0. 口径与证据规则

### 0.1 三条硬规则

1. **只写能在代码里验证的**。每条能力给一个**定位**（`文件` 或 `文件:符号`），
   定位对不上就不写。行号会漂移，因此**只写符号名**。
2. **「新增 / 变更 / 删除」分三栏**。删除栏即使为空也要写「无」，并给出**判定方法**
   （否则「没写」和「没查」分不清）。
3. **「计划未落地」单独成栏**，并写清**为什么能判定没有**（通常是某处 grep 为空、
   或只有枚举/常量而没有读取方）。这是本表最容易被写成谎言的地方。

### 0.2 证据强度

| 标记 | 含义 |
| --- | --- |
| **A** | 仓库里有对应提交可追溯（`git log` 能查到功能提交与定版提交） |
| **B** | 仓库历史不含该版本的提交，依据当版架构设计文档 + **相关代码仍在仓库且通过测试** |

> 本仓库最早的**功能**提交是 `27cfe95 add:v03 first commit`（2026-11-03），它之前只有两条
> 仓库初始化提交（`49c4597 ignore`、`99d2f82 gitattributes`）。因此 **v0.1 / v0.2 只能是 B**：
> 功能能验证「现在存在」，版本归属来自当版文档。
> v0.3 / v0.4 是 A。标签 `v0`（→ `27cfe95`）与 `v04`（→ `0c45ac4`）**都不是发布点**，
> 不要拿它们当版本边界。

### 0.3 状态标记

`✅ 已交付`　`⚠️ 部分交付（有明确缺口）`　`❌ 未实现（规划有、代码没有）`　`🗑 已移除`

## 2. v0.1（2026-11-02）— 可用邮件客户端

**定位**：把一个「能日常收发」的邮件客户端做完整，不做日历、不做 OAuth、不做 HTML 渲染。

### 2.1 新增能力

| 能力 | 代码定位 | 边界（代码里真实存在的限制） |
| --- | --- | --- |
| 多账户增删改 + 连接测试 | `me-core/src/command.rs:AddAccount/UpdateAccount/DeleteAccount/TestConnection`；`me-sync/src/engine.rs` | 删除仍有草稿的账户默认拒绝，需二次确认 |
| IMAP / SMTP 与 TLS 模式 | `me-proto/src/imap.rs`、`smtp.rs`；`TlsMode` | 仅密码 / 授权码（PLAIN、LOGIN），不支持 OAuth（v0.2 才加） |

### 2.2 计划但未落地

无功能缺口——v0.1 架构文档 §1.2 的能力在代码里都有对应实现。

### 3.2 相对 v0.1 的变更

| 项 | v0.1 | v0.2 |
| --- | --- | --- |
| 同步触发 | 启动 + 手动刷新 | IDLE 监听 + 降级轮询（`SetRealtimeSync` / `SetPollInterval` / `SetAccountRealtime`） |
| 读信 | 纯文本（HTML 经 `html2text`） | Rich / Plain / Markdown 三视图，Rich 走自研渲染器 |
| 草稿 | 本地是唯一事实来源，服务器只手动镜像 | 双向同步 + 冲突副本（保留两份，不静默覆盖） |
| 认证 | 密码 / 授权码 | 增加 OAuth2 + XOAUTH2，密码方式保留 |

**无。** 判定方法：`html2text` 仍在依赖与调用路径上（`me-proto/src/mime.rs` 的
`html_only_uses_html2text` 测试），密码认证分支仍在 `auth.rs` 与 `imap.rs`。
「纯文本阅读」被三视图**取代为其中一档**，不是删除。

- 无功能缺口。
- **人工验收 6 项未执行**（真实 Google/Microsoft 授权、真实 IDLE 长连接、真实草稿双端、

## 9. 维护规则

1. **每个版本收尾时必须更新本表**，且三栏齐全：新增 / 变更 / 删除。
   删除栏为空也要写「无」+ 判定方法（`git log --diff-filter=D`、枚举差异、grep 结论）。
2. **新增条目必须带定位**。只写「支持 X」而不给 `文件:符号` 的，视为未验证。
3. **计划项不进新增**。规划文档里的能力，只有代码里能跑通才移到「新增」；
   否则留在「计划未落地」，并写清缺什么。
4. **定位只用符号名，不写行号**（行号随每次改动漂移，会立刻变成假证据）。
5. **文档与代码冲突时以代码为准**，冲突本身记进 §8。

## 14. 未定版增量（v0.4 之后）— 工具调用失败恢复（2026-11-12）

> 由一次真实事故触发：11 月 12 日的每日简报会话（会话 id=5）10 个模型轮次里只成功干了一轮活，
> 最后一张正文都没写出来。复盘定位到四层缺陷，全部与「模型犯错之后能不能自己爬出来」有关。

### 14.1 行为变更

| 项 | 变化 | 代码定位 |
| --- | --- | --- |
| **入口类型归一化**（治根） | 拿到模型回复后、进入任何分支之前，按 `TOOL_SPECS` 的 `input_schema` 把参数强制成声明的类型：`"7"`→`7`、`"True"`/`"1"`→`true`、`3`→`"3"`；`plan_submit` 还穿透到 `steps[].id` 与 `steps[].args`（按该步声明的 `tool` 取 schema） | `me-core/src/ai.rs:coerce_tool_arguments` / `coerce_against_schema` / `coerce_plan_step_args`；调用点 `me-sync/src/ai.rs`（`turn` 拿到之后） |

| 兜底不覆盖原因 | `fallback_answer` 写 `error_text` 时改成拼接，保留「连续 N 轮没有拿到新的工具结果」这类真实原因 | `me-sync/src/ai.rs`（`AiMessageStatus::Complete` 兜底段） |

### 14.2 事故链（为什么值得单独记一节）

1. `plan_submit` 首次被拒：模型把 `id` 写成字符串，`as_u64()` 返回 `None`，报错只说「每一步都需要数字 id」——它看到的原文就是 `1`，于是原样重交。
2. 同一轮里模型还发了 3 个业务工具，全被「计划阶段不能执行工具」拒掉。
3. `calendar_list` 的 `from` 连着被拒三次：`T00:00`（真没时区）→ `T00:00+08:00`（**合法但缺秒**）→ `2026-11-12`（纯日期）。三次的报错文案**一字不差**，模型无法从错误里得到差分。
4. 三次用尽 → 该步终态 `failed`；第 4 次模型终于写对、也查到了「没有日程」，但 `bind_step` 不再绑定终端步，回执无处可写。
5. `plan_update` 想把该步标 done，被「已经是「失败」，不能再改成「已完成」」挡回；模型连撞两轮。
6. `no_progress` 计到 3 → `break`，此时仍在 `Execute`，**从未进入 `Final`**，因此模型从未被要求写正文；兜底直出工具原文，`error` 被覆盖成「模型未输出正文」。

## 16. 未定版增量（v0.4 之后）— 用户消息气泡溢出修复（2026-11-12）

> 用户粘一大段文字进 AI 页后，只看得见自己气泡的右半截，模型输出被推出可视区。
> 这是两个独立缺陷叠在一起：**RTL 布局不换行**（横向溢出）+ **没有长度上限**（纵向铺满几屏）。

### 16.1 缺陷与修法

| 项 | 根因 | 修法 | 代码定位 |
| --- | --- | --- | --- |
| 长输入横向溢出 | 气泡画在 `Layout::right_to_left` 里，`ui.label` 在该布局下拿不到右侧边界，换行宽度算成无限大——1280 的窗口画出 **2340 宽**的单行文本，RTL 从右边界往左铺，超宽部分直接溢出到屏幕左侧 | 在 RTL 里再套一层 `ui.vertical`（top_down）并 `set_max_width`，`available_width` 才等于给定宽度，label 正常换行 | `me-app/src/views/ai.rs:show_user_message` |
| 长输入纵向铺满 | 气泡高度随内容无限增长，一个 3000 字的消息能占满好几屏，模型输出被推到很远 | 超过 `USER_MESSAGE_PREVIEW_CHARS = 480`（约 12 行）折叠，末尾给「展开全文（共 N 字）」；展开后变「收起（全文 N 字）」 | 同上 + `AiPageState::expanded_user_messages`（`HashSet<AiMessageId>`，纯 UI 状态、不落库） |
| 窄窗口下气泡比面板还宽 | `(available * 0.82).max(200.0)` 在 available < 244 时结果仍可能超出面板 | 改成 `.max(160.0).min((available - 8.0).max(160.0))`，助手气泡同口径 | `show_user_message` / `render_turn` |
| 长 URL 排得太松 | egui 0.32 遇到无断点的超长 ASCII 串**会**强行折断（实测 215 字符的 URL 排 4 行、宽 1029 < 气泡宽，并不溢出），但断点位置保守、行尾留白多 | 检测到 ≥32 字符的连续 ASCII 串时改用 `LayoutJob` + `wrap.break_anywhere`（同一段排 **2 行**）；普通中英文仍按词/字断行，不会把单词拆开 | `me-app/src/views/ai.rs:bubble_job` / `has_overlong_ascii_run` |

| 助手气泡宽度 | 与用户气泡统一，窄窗口下不再溢出 |
| 长 URL / 无空格英文 | 命中 ≥32 字符的连续 ASCII 串时改用强制断行排版，同一段从 4 行压到 2 行；其余消息仍按词/字断 |

### 19.3 实测中修掉的六个真问题（**都不是「评测集太严」，是会真出错的**）

1. **worker 死循环**（最严重）。`pending_docs` 把 `chunked` 也算作待处理，模型未就绪时该文档状态不变，于是 worker 永远取到同一份文档原地打转——**实测 134 封邮件卡在 pending，只有 1 份被处理**。拆成两条队列后 166 份全部处理完，切出 1531 个语块。
2. **整句查询必然 0 命中**。`fts_phrase` 把整个查询包成一个短语，「采购合同的付款周期是多久」变成 13 个字的连续短语——原文里当然不连续。改成「分段 + 短段精确短语（≤4 token）+ 长段二元组 OR」。
3. **段间 AND 会误杀**。查询「合同编号 CG-2024-0371 的金额」里「的金额」在原文不存在（原文写「合同总额」），AND 之下整条查询 0 命中——**用户明明搜到了正确的那份文档**。改成段间 OR，精度交给 BM25。
4. **标题与章节标题不在索引里**。`HT-2024-07` 只出现在标题行，标题在 `locator` 与 `kb_documents.title` 里，正文里没有。搜型号必然搜不到。改成 FTS 索引内容 = 标题 + locator + 正文。
5. **融合后 top-8 被一篇文档吃满**。实测「设备故障响应的时限与服务级别如何对应」这一问，top-8 里 6 块来自《服务手册》，真正需要的《采购合同》被挤出去，**跨文档的问题就此答错**。加文档级轮转取（`diversify_by_document`）后 RRF 从 19/20 变 20/20。
6. **模型权重没有 `bert.` 前缀**（ModelScope 的 sentence-transformers 转换版）。写死 `vb.pp("bert")` 报「找不到张量 bert.embeddings.…」，错误信息完全不提示「前缀不对」。改成读 safetensors 头部探测前缀。

另有两个「只在特定条件下炸」的坑，一并记下：
- **批量推理撞 `MatMulUnexpectedStriding`**：`transpose` 出来的张量非连续，candle 的 matmul 不接受。单条查询恰好连续，**只有批量会炸**——所以评测必须真的把语料向量化，不能只测查询。
- **模型结构参数不能硬编码**：现在从 `config.json` 读（`hidden_size` / `num_hidden_layers` / …），换模型时硬编码会静默错位，出来的向量全是垃圾。

| # | 根因 | 证据 |
| --- | --- | --- |
| 1 | **计划阶段选错工具** | 计划第 3 步写的是 `weather_locations`（列地点）而不是 `weather_get`（取天气），`args: {}`。PLAN 阶段只下发 `plan_submit` / `answer_directly`，模型只看得见**参数名白名单**——`weather_locations` 没有参数、看着"简单安全"，两者的区别只在工具描述里，而描述当时没下发给模型 |
| 2 | **收尾阶段硬性丢弃业务工具** | 第 3 轮 `phase=Final tools=3 dropped_calls=3`，模型的三个调用全被丢弃。引擎不给任何"为什么不行"的信息 |
| 3 | **模型把「没调用」说成「查询失败」** | thinking 原文：*"用户明确说不要调用工具了。那我就用已有的信息回答，并说明天气信息无法获取。"* ——它接受了"不许调工具"的提示，转而编了一个受限理由 |

对照组：**同一天的自动简报（会话 15）选对了** `weather_get`，因为走 `DAILY_BRIEFING_PROMPT`，里面明写「调用 weather_get（days=3，不传 location 就用默认关注地点）」。
**结论：走内置提示词的路径没问题，手动提问的路径会退化。**

### 20.3 修复

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| **用途表** | `me-core/src/ai.rs` · `tool_purpose_reference` | PLAN 阶段下发「每个工具是干什么的」，挂在 `plan_submit` 的 **`tool` 字段**上。与 `tool_argument_reference`（参数表，挂在 `args` 上）分工：参数表说"参数叫什么"，用途表说"这个工具干什么" |
| **描述首句自足** | `me-core/src/ai.rs` · `TOOL_SPECS` | `weather_get` 首句改成「查天气数据…用这个，不传地点就按默认关注地点查」；`weather_locations` 首句改成「…**要天气数据请用 weather_get**，它不取天气」。用途表只取第一句、限 60 字，区分必须落在第一句里 |
| **收尾阶段补一次只读工具** | `me-sync/src/ai.rs` · `phase_allows` / `final_readonly_tools` | 观测到被丢弃的调用里有**只读**工具时，下一轮下发只读工具集并放行一次（`final_allows_readonly` / `final_readonly_used`）。**写工具永远不放**：收尾阶段执行 `calendar_create` / `kb_delete` 等于绕过执行期的清单与确认流程 |
| **回喂明确原因** | `me-sync/src/ai.rs` · `final_readonly_retry_hint` | 说清「可以再调一次」，并堵住「把『没调用』写成『查询失败』」这个坑。只说「不行」的话模型会自己编理由，用户就以为工具坏了 |
| **提示词跟着换** | `me-sync/src/ai.rs` · `final_readonly_suffix` | 补数据时改说「可以调只读工具」。不能与 `phase_system_suffix` 的 Final 分支（「不许调工具」）同时出现——两句话打架，模型干脆不调 |
| **去掉硬编码工具名** | `me-core/src/ai.rs` · `plan_submit.tool` | 原写死「如 email_search / mail_read / calendar_list」（只列三个、必然过期），改为指向用途表 |
| **描述首句自足** | `me-core/src/ai.rs` · `TOOL_SPECS` | 用途表只取描述**第一句**且限 60 字，所以「要天气数据请用 weather_get」这类区分必须落在第一句里。`weather_get` 首句改成「查天气数据…不传地点就按默认关注地点查」；`weather_locations` 首句改成「…**要天气数据请用 weather_get**，它不取天气」 |
| 引用语法结论修正 | 本表 §441 行 | 原写「`{{step.N.字段}}` 引擎早已支持…把机制说反了」，**有误**：实际 `ai_plan.rs` 里只有 `refs_in_args`（提取引用）与 `skip_dependents`（级联跳过），**没有取值替换代码**。schema 写「引擎不会替你替换成实际值」是准确的，README 原本的表述也对 |
