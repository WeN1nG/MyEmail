## 0. 一句话结论

指南的**架构判断与批次划分是可靠的**——逐条比对代码后，关键事实（搜索后端已完备、线程字段已在手、

## 1. 阻塞性冲突：schema v6 已被占用

### 1.1 事实

| 项 | 指南的假设 | 代码的真实状态 |
| --- | --- | --- |
| `SCHEMA_VERSION` | `5` → 改为 `6` | **已是 `6`**（`crates/me-core/src/lib.rs:81`） |
| 迁移链 | `v1→…→v5→v6` | **已是 `v1→v2→v3→v4→v5→v6`**，`Some(5) =>` 分支已存在（`migrations.rs:497`） |
| `migrate_v5_to_v6` | 待新增（加表 + 加列） | **已存在**（`migrations.rs:716`），做的是纯索引调整 |
| v6 的性质 | 新增 2 表 + `messages` 加 2 列 | **纯索引调整**：6 条索引重建/新增，不动任何列 |
| 备份文件 | `.bak-v5` | 沿用 `.bak-v1` 约定 |
| 迁移测试 | 待新增 `migration_v5_v6.rs` | **已存在**（未跟踪文件），校验索引定义逐条一致 + 幂等 + EXPLAIN 计划 |

### 1.2 为什么会撞

指南 §1.1 的 `migrate_v5_to_v6` 模板要执行 `SCHEMA_V6_DDL`（建 `contacts` / `saved_searches`）并给
`messages` 加 `in_reply_to` / `references`。若照抄：

- `migrate_v5_to_v6` **重名**，且两份函数语义完全不同（一份纯索引、一份加表）；
- 目标版本都写 `6`，v5 库走哪条都说不清；
- `create_schema` 的 DDL 会与 `migrate_v5_to_v6` 的 DDL 分叉，签名等价性测试无法通过。

### 1.3 解决方案（推荐）：**v0.4 的新表走 schema v7**

> ✅ **已于 2026-11-06 执行完毕**：下表的机械替换已全部落到
> [v4开发指南.md](versiondoc/v4开发指南.md) §1.1 / §2 / §3.3 / §5.1 / §7.2 / §9 / §10，
> [v04候选功能.md](versiondoc/v04候选功能.md) 的基线口径同步更新为 `schema_version = 6` / `561 passed`。

这是唯一自洽的选项，因为 v6 已被工作区改动**实际占用**（且那套改动是 `优化清单.md` P0-2/P0-3/P0-4
的性能修复，有实测数据支撑，不能作废重来）。

**具体改法**（对指南 §1.1 的机械替换）：

| 指南原文 | 改为 |
| --- | --- |
| `SCHEMA_V6_DDL` | `SCHEMA_V7_DDL` |
| `fn migrate_v5_to_v6(conn)` | `fn migrate_v6_to_v7(conn)` |
| `const TARGET: u32 = 6;` | `const TARGET: u32 = 7;` |
| `SCHEMA_VERSION: u32 = 5` → `6` | 保持 `6`，改为 `6` → `7` |
| `migrate_or_open` 加 `Some(5) =>` 分支 | 加 `Some(6) =>` 分支（`Some(5)` 已存在） |
| 备份 `.bak-v5` | 备份 `.bak-v6` |
| 测试 `migration_v5_v6.rs` | 新建 `migration_v6_v7.rs` |
| 文档「§9 增补 v5→v6 迁移步骤」 | 增补 **v6→v7** 迁移步骤 |
| §9 文档回写清单里的「schema v6」 | 改为「schema v7」 |
| §10 风险表的「schema v6 迁移失败」 | 改为「schema v7 迁移失败」 |

**注意**：`SCHEMA_V7_DDL` 只应包含 **v0.4 的三个新增项**（`contacts` 表、`saved_searches` 表、
`messages` 的两列），**不要**重复包含 v6 的索引定义——那 6 条索引已在 `SCHEMA_V3_DDL`（即 `create_schema`
的 DDL）里，改索引列序属于 v6 的职责。

**迁移幂等判据**（指南原文给的判据要按变更类型分开）：

- 加两列（`in_reply_to` / `references`）→ 沿用 **`pragma_table_info` 判列存在性**（指南原文正确）；
- 建两张新表 → `CREATE TABLE IF NOT EXISTS`，或用 `SCHEMA_V7_DDL` 里的 `IF NOT EXISTS`；
- 目标版本号**写死 `7`**，不能写 `SCHEMA_VERSION`。

### 1.4 备选：与 v6 索引调整合并成一次迁移

把「加表加列」并入既有 `migrate_v5_to_v6`，让 v6 同时做索引调整 + 加表加列。

**不推荐**：这会让 v6 的语义从「纯索引调整（零破坏、可与既有备份策略解耦）」变成「加表加列」，
且既有 `migration_v5_v6.rs` 测试（已断言「不改任何列类型/CHECK/NOT NULL」）会失效，
还要重做已通过的实测基准。两个语义混在一版里，回退时无法拆分。
