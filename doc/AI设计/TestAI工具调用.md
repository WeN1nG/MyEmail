# AI 工具调用 · 人工验收用例

> 用途：**照着聊天测**。每个用例给一句原话、期望答复要点、清单/日志/库里该看到什么，以及「看到什么算失败」。
> 不是自动化测试清单——自动化在 `crates/*/tests/` 与 `me-core` 单测里，本文不重复它们。
> 适用版本：v0.4.0（2026-11-09 工具调用链改造后）。改提示词、改限额、改清单校验后都该重跑。

---

## 0. 上手

### 0.1 准备

| 项 | 要求 |
|---|---|
| 程序 | `target/release/myemail.exe`（改完代码必须重编，旧二进制不带新逻辑） |
| 模型 | 真实模型，**不要**用小参数/降智模型跑——本套测的是「模型与引擎配合」 |
| 数据 | 一个已同步的邮箱 + 至少 2 个天气关注城市（其中一个设默认，便于测「点名城市」） |
| 日志 | `%APPDATA%\MyEmail\logs\myemail.YYYY-MM-DD.log` |
| 库 | `%APPDATA%\MyEmail\myemail.db`（**只读副本**，连 `-wal` 一起拷） |

### 0.2 怎么跑

1. 按 §2 顺序一条条发，**每条用新会话**（避免上下文串味），除非用例写明「接着上一句」。
2. 每条记三样：**答复原文**、**清单 / `[结果]`**、**该轮日志行**（见 §1.3）。
3. 对照「期望」与「失败」判定，结果填进 §4 记录表。
4. 一轮 40–60 分钟；只跑冒烟（§3.1）约 10 分钟。

### 0.3 严重度

| 级别 | 含义 | 处理 |
|---|---|---|
| S1 阻断 | 用户看不到数据、答案与事实相反、误删/误写 | 修完才能出包 |
| S2 明显 | 多绕 1–2 轮、清单与答复不一致、该问不问 | 记 issue，可出包但下次必修 |
| S3 体感 | 措辞啰嗦、卡片理由重复、追问过多 | 攒起来一起改提示词 |

## 1. 判定口径（每条都按三层看）

### 1.1 第一层：答复

- **有数据**：温度、封数、日程、曲名这些具体值必须出现，不能只有「帮你查到了」。
- **不甩锅**：查到了却说「无法获取」「没有拿到结果」——直接 S1。
- **该问才问**：信息不足时反问是**正确**行为（例：两个关注城市都没设默认）；信息够时反问是打扰。

### 1.2 第二层：清单与 `[结果]`

调过工具就会有 `[结果]`，四行必须与清单一致：

```
状态：已完成 / 部分完成 / 未完成
做了什么：…
关键信息：…
未完成：…
```

- 清单 `n/n 完成、0 步失败` ⟺ `状态：已完成`；
- 任何一步 `失败` ⟹ 状态不能是「已完成」，且 `未完成` 行要点名它；
- 步骤 `skipped` 必须写清原因（依赖上游失败 / 用户取消 / 主动放弃）。

**不一致即 S1**——2026-11-09 那次的原始问题就是「清单全绿、答复说没拿到」。

### 1.3 第三层：日志与库

```bash
# 每轮一行，字段固定
grep "AI 轮次" myemail.*.log | tail -5
# round=2 phase=final tools=0 dropped_calls=0 dropped_total=1 text_chars=412 final_retries=1 no_progress=0 ms=1830
```

| 字段 | 读法 |
|---|---|
| `phase` | 正常 1 步任务应走 `plan → execute → final` |
| `text_chars=0` + `dropped_calls>0` | 模型在收尾期想调工具（被丢弃），不是「不会写」 |
| `text_chars=0` + `dropped_calls=0` | 模型真的一个字没写 |
| `final_retries=2` | 已催满，下一条应是兜底直出 |
| `no_progress=3` | 无进展闸触发，提前收尾 |
| `tools` | 这一轮模型**请求**了几个工具（不是执行了几个） |

库（只读副本上查）：

```sql
select id, status, error, tool_trace, plan from ai_messages
where role='assistant' order by id desc limit 1;
```

`tool_trace[].args` 是实际传的参数（`motive` 已剔除）；清单里的 `args` 只是说明书。

## 2. 用例

编号 `M-能力-序号`。「输入」照抄，不要改写——改写会掩盖模型的行为差异。

### 2.1 天气（M-WX）

#### M-WX-01 没给地点，但有默认城市

| 项 | 内容 |
|---|---|
| 输入 | `天气怎么样` |
| 期望答复 | 直接给**默认城市**的当前天气 + 未来几天，并写明是哪个城市 |
| 期望清单 | 1 步完成；`[结果]`「状态：已完成」 |
| 日志 | `weather_get` 一次，`final_retries=0` |
| **失败** | 反问「你要查哪个城市」→ S2；回「无法获取实时天气」→ **S1** |

#### M-WX-02 没给地点，也没添加过城市

| 项 | 内容 |
|---|---|
| 前置 | 清空所有关注城市 |
| 输入 | `天气怎么样` |
| 期望答复 | 明说「你还没添加城市」，给一句怎么加，**不编数据** |
| **失败** | 编造某个城市 → **S1**；只说「查询失败」不说原因 → S2 |

#### M-WX-03 点名城市（与 01 成对）

| 项 | 内容 |
|---|---|
| 前置 | 关注「双流」（默认）+「自贡」 |
| 输入 | `自贡天气怎么样` |
| 期望答复 | 报自贡的数据，不出现「你要查哪一个」 |
| **失败** | 答成默认城市 → **S1** |

#### M-WX-04 两个城市对比（限额）

| 项 | 内容 |
|---|---|
| 输入 | `成都和北京哪个更冷` |
| 期望答复 | 两城各自温度 + 一句比较结论 |
| 日志 | `weather_get` **2 次**（限额 3） |
| **失败** | 只答一个就下结论 → S1；报「最多查询 3 次已用完」→ S2 |

#### M-WX-05 地名含糊

| 项 | 内容 |
|---|---|
| 输入 | `朝阳天气`（北京朝阳区 / 辽宁朝阳市） |
| 期望答复 | 要么问清哪一个，要么明说「按北京朝阳处理」并给数据 |
| **失败** | 默默给一个且不说明 → S2 |

#### M-WX-06 未配置天气 Key

| 项 | 内容 |
|---|---|
| 前置 | 清掉天气 Key |
| 输入 | `今天天气` |
| 期望答复 | 说清是**配置问题**（没填 Key），不是「网络错误」 |
| **失败** | 整轮 `failed`，或让用户「稍后重试」→ S2 |

### 2.2 邮件（M-MAIL）

#### M-MAIL-01 纯时间窗

| 项 | 内容 |
|---|---|
| 输入 | `最近三天有什么邮件` |
| 期望答复 | 报封数 + 列几封（主题/发件人） |
| 期望清单 | 1 步完成；evidence 写「命中 N 封」 |
| **失败** | 回「请提供检索条件」→ **S1**（时间窗就是条件）；实际有却报 0 封 → S1 |

#### M-MAIL-02 定性需求（最容易被写死的一条）

| 项 | 内容 |
|---|---|
| 输入 | `有什么需要我优先处理的邮件` |
| 期望答复 | 几封邮件 + **每封为什么被选中**（不能统一一句「匹配筛选条件」） |
| 期望卡片 | 每张卡带「命中判据」（如「已星标」「近三天未读」） |
| 日志/库 | `email_search` 的 `args` 里是 `criteria`（`important_only` 已删除） |
| **失败** | 卡片理由全同一句 → S2；报参数不存在 → **S1** |

#### M-MAIL-03 换一个定性词（通用性）

| 项 | 内容 |
|---|---|
| 输入 | `哪些邮件该我跟进` |
| 期望 | 机制同 02：模型把「该跟进」翻译成几条判据，引擎按判据查、取并集 |
| **失败** | 回「不支持该功能」/ 套固定模板 → **S1**（口径又写死了） |

#### M-MAIL-04 0 命中

| 项 | 内容 |
|---|---|
| 输入 | `找一下主题是 zzzz-not-exist 的邮件` |
| 期望答复 | 明说没找到，并说明查了什么条件（不说「查询失败」） |
| 期望清单 | 该步完成（0 命中是合法业务结果） |
| **失败** | 标成「失败」→ S2；答复与清单矛盾 → **S1** |

#### M-MAIL-05 两步：先检索再读正文

| 项 | 内容 |
|---|---|
| 输入 | `看看昨天那封周报讲了什么` |
| 期望答复 | 主题 + 3 条以内要点，能看出读的是正文 |
| 期望清单 | 2 步都完成；第 2 步 evidence 写「拿到了什么」 |
| 日志 | 序列 `plan_submit → email_search → mail_read`，总轮数 ≤ 4 |
| **失败** | 只复述标题 → S2；正文没缓存却编内容 → **S1** |

#### M-MAIL-06 条件复合 + 附件

| 项 | 内容 |
|---|---|
| 输入 | `这周带附件的邮件有哪些` |
| 期望 | 能检索（说明 `has_attachment` 在 schema 里可见） |
| **失败** | 回「参数不认得」→ **S1**（三处清单又漂移了） |

#### M-MAIL-07 跨能力：邮件 + 日历

| 项 | 内容 |
|---|---|
| 输入 | `把周报里的待办加到日历，明天下午三点` |
| 期望 | 先读邮件 → 提取待办 → 建日程 |
| 期望清单 | 3 步左右，每步 evidence 具体；**第 2 步的 args 是 `{{step.1.…}}` 引用**，不是手抄的 id |
| 日志 | 第 1 步失败时，第 2 步必须是 `skipped`（`upstream`），不能拿空 id 继续跑 |
| **失败** | 跳过读邮件直接编日程内容 → **S1**；引用写成「第 1 步的 message_id」这种自由文本 → S2（引擎认不出依赖） |

#### M-MAIL-08 定性词分「范围」与「优先」两档（新增，P7）

| 项 | 内容 |
|---|---|
| 输入 | `最近一个月里，优先看星标的邮件` |
| 期望 | 范围（近 30 天）内的邮件都出现；星标的排前面 |
| 期望卡片 | 排第一的那张理由是「已星标」；其余卡片可以只写范围判据名 |
| 工具回执 | 带「必须同时满足：近 30 天」，且各判据命中数逐条列出 |
| **失败** | 范围外的邮件被 boost 拉进来 → S1；范围内非星标的邮件被 must 滤掉 → S2（把「优先」写成必须，用户看到的是空） |

### 2.3 日历（M-CAL）

#### M-CAL-01 查询

| 项 | 内容 |
|---|---|
| 输入 | `这周有什么安排` |
| 期望 | 按天列出；没日程就说没有 |
| **失败** | 说「没有」但实际有 → S1（时间窗算错） |

#### M-CAL-02 创建

| 项 | 内容 |
|---|---|
| 输入 | `周四下午两点跟张总开会，一小时` |
| 期望 | 建好并回读时间/标题；时区按本地 |
| 验证 | 日历页看到这条，时间正确 |
| **失败** | 时间差一小时（时区）→ S1 |

#### M-CAL-03 删除（确认卡）

| 项 | 内容 |
|---|---|
| 输入 | `把周五的复盘删了` |
| 期望 | 出**确认卡**，答复说明「待确认」 |
| 验证 | 确认前到日历页看，那条日程**还在** |
| **失败** | 直接删掉 → **S1（最高优先级）** |

#### M-CAL-04 时间含糊

| 项 | 内容 |
|---|---|
| 输入 | `下周五提醒我交材料` |
| 期望 | 按明确日期建，或先确认具体哪天（有歧义时反问是正确行为） |
| **失败** | 建到错误日期且没说明 → S1 |

### 2.6 跨轮与上下文（M-CTX）

#### M-CTX-01 继续上一轮没做完的清单

| 项 | 内容 |
|---|---|
| 输入 | 先 `帮我整理这周的邮件`，中途取消，再发 `继续` |
| 期望 | 能看到「还剩哪几步」，不是从头规划 |
| 日志 | 第二轮首条 `phase=execute`（不是又 `plan`） |
| **失败** | 全部重来 → S2 |

#### M-CTX-02 指代

| 项 | 内容 |
|---|---|
| 输入 | 先 `查一下双流天气`，再 `那明天呢` |
| 期望 | 沿用「双流」，不重新问城市 |
| **失败** | 反问城市 → S2 |

#### M-CTX-03 长对话（20 轮以上）

| 项 | 内容 |
|---|---|
| 操作 | 连续问 20 轮杂事，再问一个需要工具的问题 |
| 期望 | 仍能出结果；日志出现「早期结果已压缩」不算错 |
| **失败** | 报上下文过长整轮失败 → **S1**（请求预算没生效） |

### 2.7 异常与边界（M-ERR）

#### M-ERR-01 取消

| 项 | 内容 |
|---|---|
| 操作 | 生成中点心停止 |
| 期望 | 保留已生成内容；`status=cancelled`；运行中的步 `skipped`，未开始仍 `pending` |
| **失败** | 整条消息消失 → S1 |

#### M-ERR-02 Key 错

| 项 | 内容 |
|---|---|
| 前置 | 把 Key 改错 |
| 期望 | 明确报鉴权失败、不反复重试；改回 Key 后立刻可用 |
| **失败** | 多次重试仍转圈 → S2；提示「请求过于频繁」→ S1（分类错） |

#### M-ERR-03 限流

| 项 | 内容 |
|---|---|
| 操作 | 连续快速发 5–6 条需要工具的消息 |
| 期望 | 最多偶发变慢，不出现整轮 `failed`「请求过于频繁」 |
| **失败** | 429 导致整轮失败 → S2 |

#### M-ERR-04 关闭能力后再要求

| 项 | 内容 |
|---|---|
| 前置 | 设置里关掉「日历」 |
| 输入 | `帮我建个日程` |
| 期望 | 说明能力已关闭并给开启指引，**不假装完成** |
| **失败** | 说「已创建」→ **S1** |

### 2.8 收尾专项（改提示词后必跑，M-FINAL）

这三条不是功能，是**观察**：确认模型不会把最后一轮花在「汇报完成」上，也不会交白卷。

#### M-FINAL-01 最短链路

| 项 | 内容 |
|---|---|
| 输入 | `天气怎么样` |
| 看什么 | 总轮数 ≤ 3；任何一轮都不同时出现 `text_chars=0` 与 `dropped_calls>0` |
| **失败** | 连续两轮 `dropped_calls>0 && text_chars=0` → S2（收尾期记账出口失效） |
| **失败** | 出现「模型没能整理这次的结果，以下是查询原文」→ S3（兜底生效了，但模型又交白卷，查提示词） |

#### M-FINAL-02 带清单的多步任务

| 项 | 内容 |
|---|---|
| 输入 | `整理这周的未读邮件，挑三封最重要的告诉我` |
| 看什么 | 清单逐步推进（不是最后一次性全标完成）；`[结果]` 与清单一致 |
| **失败** | 某步标 `done` 但 evidence 为空 → S2 |

#### M-FINAL-03 容易「放弃」的问法

| 项 | 内容 |
|---|---|
| 输入 | `最近有什么重要的邮件吗`（不给条件） |
| 期望 | 自己定判据并检索；真判断不了就先问范围，**而不是**答「无法确定」就结束 |
| **失败** | 直接放弃且不反问 → S2 |

## 3. 跑法建议

### 3.1 冒烟（10 分钟，每次改完代码）

`M-WX-01` → `M-MAIL-01` → `M-MAIL-05` → `M-CAL-03` → `M-FINAL-01`

覆盖：默认兜底、检索基本盘、两步链路、写操作确认、收尾不白卷。

### 3.2 全量（40–60 分钟，出包前）

§2 全部 32 条。

### 3.3 随机抽查（防「只为用例优化」）

每次挑 1 条，用**自己的话**问，不看本文：

- 让 AI 查两个城市天气再比较；
- 让它从邮件里找一件具体的事（发票、快递、会议时间）；
- 让它改某个日程的时间；
- 问它「刚才为什么没查到」（考察诚实度：应说「没匹配到」，不是编）。

原则：**用例是下限，不是上限。** 用例全过但随口一问就翻车，说明提示词被写成了模板。

### 7.3 问题清单（按优先级）

> **修复状态**：P1–P6 已修（第二轮，见 §7.8）；**P7 已修（第三轮，见 §7.9）**；P8（记账轮次上限）属设计改动，仍留待实测分布；P9 的措辞项随下次提示词调整一起改。

#### P1 [S1] 引擎没告诉模型「今天几号」，相对时间全靠猜

- **现象**：同一个「今天」，模型三次算出三个答案——`2026-07-14`（周二）、`2025-07-07`（本周一）、`7月24日`（下周五）。
- **证据**：
  - `ai_messages.plan`（id=20）：`args={"from":"2025-07-09","to":"2025-07-13"}`，trace 实际下发 `2025-07-07T00:00:00+08:00 ~ 2025-07-13T23:59:59+08:00`；
  - `plan`（id=24）第 1 步 evidence：`今天2026-07-14是周二，下周五是2026-07-24`；
  - `plan`（id=22）trace `motive`：`创建与张总下周一下午两点的会议日程`，实际建在 **11-13（周五）**；
  - M-MAIL-01 答复把「最近三天」写成「11月7日–11月9日」——漏掉今天。
- **根因**：`SYSTEM_PROMPT`（`me-core/src/ai.rs:1475`）全文没有日期；用户消息是原话直传，没有任何时间锚点；`crates/` 里除 `ai_tools.rs:2206`（`calendar_list` 的默认起点）之外没有一处把 `Local::now()` 注入上下文。模型只能从训练先验里编。
- **修法**：每轮在 system 末尾（或用户消息前）钉一行不可协商的锚点：

  ```
  当前本地时间：2026-11-10 11:05（周二，Asia/Shanghai）。
  凡涉及「今天/明天/这周/下周四/最近三天」一律以这一行为基准推算，不要猜。
  ```

  顺带把 `calendar_list` 的 `days` 补进 schema（当前只有 `from/to/keyword/limit`，模型写 `days` 被拒，白掉一轮）。

#### P2 [S1] 一个请求写两遍：缺写操作闸

- **现象**：M-CAL-02 一句话造出两条同名日程。
- **证据**：`calendar_events` id=5 `start_utc=1794549600`（2026-11-13 Fri 14:00）、id=6 `start_utc=1795068000`（2026-11-19 Thu 14:00），`created_at` 相差 13 s。
- **根因**：`plan_submit` 连续失败后，引擎退化到「按单步直接回答」的免清单通道，模型进入连续自由调用（本轮共 9 次 Execute）。`MAX_TOOL_CALLS=24`（`me-core/src/ai.rs:87`）对写操作没有任何单独限制，也没有「同名 + 同日 ±1h 的 create 先查重」。
- **修法**：
  1. 写类工具（`calendar_create/update/delete`）单轮上限 1 次，第 2 次直接拒并回一句「本轮已创建过一条，如果是重复请先确认」；
  2. `calendar_create` 落库前按 `summary + start±1h` 查重，命中就返回「已存在」而不是再插一条；
  3. `plan_submit` 连续失败 2 次后**不要**切免清单通道——那等于放开了记账约束；应把校验错误原话回给模型并只允许 1 次修正，仍失败则进 Final。

#### P3 [S1] 谎报写操作：模型自述的 evidence 没有 trace 交叉校验

- **现象**：M-CAL-04 声称「已创建下周五（7月24日）交材料」，库里没有这条，工具一次都没调。
- **证据**：`ai_messages.tool_trace = []`（空数组）；`plan.steps[1]`：`status=done, attempts=0, args` 全为空串，`evidence="成功创建日程: event_id=1..."`。
- **根因**：`plan_update` 对 `done` 的校验只覆盖「上一次执行失败不能标 done」，没有要求「本轮存在对应工具的成功 trace」。模型只要在 plan 里把 evidence 编漂亮，清单就是绿的——**这正是 2026-11-09 事故的同一条路径，换了入口**。
- **修法**：
  1. `plan_update` 把某步标 `done` 时，必须能在本轮 traces 里找到同 `tool`、`status=ok` 且 `step_id` 对得上的记录，否则拒绝并回「你没有调用 calendar_create」；
  2. 落库前做一次「答复 vs 事实」核对：正文出现「已创建/已删除/已修改」而对应工具无成功 trace 时，强制在正文前插入不一致提示。

#### P4 [S1] 天气：歧义把数据藏掉，还用 `ok` 记账

- **现象**：M-WX-04「成都和北京哪个更冷」，两城一个温度都没给，全部打回「请确认是哪个区」；清单却是 2/3 步完成、0 步失败。
- **证据**：trace 两条 `weather_get` 均 `status=ok`、`summary="地点不明确"`；plan 第 1/2 步 `status=done`、`evidence="地点不明确"`；答复只有候选清单。
- **根因**（`me-sync/src/ai_tools.rs`）：
  - `:1434` 多命中时 `return Ok((...匹配到多个已保存地点...))` —— 用 `Ok` 表达「需要用户输入」，于是 trace 记 ok、清单记 done；
  - 多命中时没有看 `is_default`：成都名下「双流（默认）/武侯」两条，本可先按默认收敛（这也违反 M-WX-01 已确立的「有默认就用默认」）；
  - `:1538` 城市名走 `weather_candidates()` 后一律 `len>1 ⟶ 反问`：查「北京」返回的是 北京·北京市 + 海淀/朝阳/顺义… 十个下级区县，**没有「城市级同名优先」规则**，于是一个完全正常的城市名永远查不出来。
- **修法**：
  1. 歧义用独立结果态（`need_input`），trace 记 `skipped`、步骤不得算 `done`；
  2. 多命中先按 `is_default` 收敛，仍有多个才问；
  3. geo 候选里若存在 `name == 输入 && level == city`（或名称完全相等）直接选中，别再问；
  4. 用户给了两个城市做比较时，把「两城各自数据都没拿到」明确写成该轮失败，而不是 `部分完成`。

#### P5 [S1] 音乐：`index` 是曲库序号，模型当成了搜索结果序号

- **现象**：M-MUS-01 两轮都把《一路向北》播成《7 Years》，两轮清单都标 `done`。
- **证据**：trace `music_play` `args={"index":1}` → `summary="播放「7_Years-Lukas_Graham-6952280」（第 1 / 305 首，顺序：随机）"`；`plan` 第 3 步 `title=播放一路向北, status=done`。
- **根因**：
  - `music_search` 只回曲名与数量，**没有回转给 `music_play` 的定位键**；`music_play` 的 `index` 是「曲库扫描序号（1..305）」，与「候选列表第 1 条」不是一回事——schema 里那句「多首命中请用 query 点名，不要报序号」没有给出可执行替代（`query=一路向北` 才是可行路径）；
  - 引擎拿到「播的是别的歌」仍判定 `ok`，没有任何「结果与请求不符」的判据，于是模型只能靠自觉，而它选择标 done。
- **修法**：
  1. `music_search` 每首带稳定 `track_id`（或路径哈希），`music_play` 接受 `track_id`；
  2. 没 `track_id` 时给 `index` 加护栏：本轮做过 `music_search` 且 `index` 不在结果集内 ⟶ 直接拒，并回「候选请用 query 点名」；
  3. 返回串里带一句「实际播放 ≠ 请求曲目」的显式标记，让模型必须说明。

#### P6 [S2] 清单与答复对不上，三种形态

| 形态 | 证据 | 根因 |
|---|---|---|
| a. 两个 `[结果]` 段 | M-MAIL-01 正文先有 `**[结果]**`（粗体），引擎又追加一段 `[结果]`，两段状态措辞不同 | `has_result_block`（`me-sync/src/ai.rs:3178`）只认整行 `== "[结果]"`，UI 切分（`me-app/src/views/ai.rs:1370`）同一规则 ⟶ 粗体/标题变体既不被识别为「已有」，也不会被渲染成段落 |
| b. 内部记账混进业务动作 | M-CAL-02 的 `[结果]`：`做了什么：…；提交计划（失败）；提交计划（失败）`、`未完成：更新清单（失败）×4` | `synthesized_result_block`（`ai.rs:3190`）把全部 trace 都当业务动作，没过滤 `plan_submit/plan_update` |
| c. 步骤 done 但 evidence 是「没拿到」 | M-WX-04 `evidence="地点不明确"`；M-MUS-01 `evidence` 写的曲目与 title 相反 | `done` 只校验「上次没失败」，不校验 evidence 是否与 expect 相符 |

**修法**：① 抽一个 `is_result_block_line()` 给引擎与 UI 共用，放宽到 `**[结果]**` / `### [结果]` / 全角括号；② 合成段过滤 bookkeeping 工具；③ `done` 要求 evidence 非空且不落入 `地点不明确/未找到/没有数据` 这类否定词表。

#### P7 [S2] 定性需求在「判据取并集」下退化成时间窗

- **现象**：M-MAIL-02「有什么需要我优先处理的邮件」拿到 10 封，卡片理由**全是「近 7 天」**——「已星标」这条判据 0 命中后被并集吞掉，等于没提。库里 `flags` 含 `Flagged` 的邮件为 0 封，所以这条判据注定空转。
- **根因**：提示词 §13③ 规定「判据之间是或的关系」，对**筛选**型需求正确；但「优先处理」是**排序**型需求，用 OR 就变成「近 7 天 或 星标 或 …」= 全部近 7 天，排序意图丢失，最后靠模型读主题手工排序（答复里的分级是模型自己排的，不是引擎排的）。
- **修法**：`criteria` 支持两档语义——`must`（与，收窄）与 `boost`（或，加分/靠前）；提示词明确「筛选用 must、排序用 boost」。短期最小改动：允许每条判据带 `weight`，卡片理由显示「命中：已星标（权重 2）」。
- **已修（2026-11-10 第三轮，见 §7.9）**：`criteria[].mode = must | boost` 落到 schema 与引擎：must 取交集框范围、boost 命中数决定排序，卡片理由取最靠前的那条判据（多命中不再拼成长串）。用例见 M-MAIL-08。

#### P8 [S2] 记账校验错误吃掉轮次，把执行挤到超时

- **现象**：M-CAL-02 单轮 10 次 AI 往返、85 s，最后没有 Final 相位，直接兜底。
- **证据**：日志 `conversation=11` round=0..9 全是 `Plan/Execute`，`no_progress` 累到 2；trace 里 `plan_submit` 被拒 4 次（`第 1 步缺少 title`、`第 2 步是工具步，但没写 tool`）、`plan_update` 被拒 4 次（`第 2 步缺少标题（title）`、`第 1 步已经是「已完成」，不能再改成「失败」`）。
- **根因**：校验文案本身清楚，但**同一轮允许无限次重提交**；`plan_update` 要求带完整 title（`ai_tools.rs:2063` 走的是 v2 全量解析）而提示词只说「把该步标成 done/failed/skipped 并写一句 evidence」——契约与说明不一致。
- **修法**：① 提示词写明 `plan_update` 的 `steps[]` 每项**至少** `{id, status, evidence}`，且 `title` 可省；② bookkeeping 工具每轮最多 2 次，超了把清单直接定成「未完成」并进 Final；③ `done ⟶ failed` 的改判放开（现实中确实需要撤回误标）。

#### P9 [S3] 措辞与格式

- 回复开头普遍带 1–9 个空行（M-WX-01/03/04、M-MAIL-01/02/03、M-CAL-01、M-MUS-01/03），UI 上是大片留白；
- M-MUS-02「等扫描完成后再让我**重试试试**」；M-CAL-04「计算了**下周五的日期（7月24日）**，并创建了日程提醒」——把没发生的事写得像流水账；
- 「清空所有关注城市」那轮同一件事答了两遍（MSG 4 前后两段语义重复）；
- M-MAIL-03 把已经过期的截止时间（11-04）当成「需立即跟进」，与事实相反——取决于 P1 的日期锚点能否修好。

### 7.4 本轮确认有效的机制（别改坏）

1. **相位推进正常**：1 步任务 `plan→execute→final` 三轮收工（M-WX-01、M-MAIL-04、M-MAIL-06），`final_retries` 全 0。
2. **收尾记账没出问题**：全天 `dropped_calls=0`、无 `text_chars=0 && dropped_calls>0`，M-FINAL-01 通过。
3. **参数校验真的拦住了脏参数**：`plan_submit` 拒绝了空判据（「判据必须写成可执行的条件」）、未知参数（`calendar_list` 不认识的 `days`）、无检索条件的 `email_search`——三次都是**正确拒绝**，问题只在「拒了之后模型能得到几次重试」。
