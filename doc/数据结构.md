## 1. 设计原则

1. **摘要入库，正文出库**：`messages` 只存可检索的头部与状态；正文写文件 + FTS，避免库无限膨胀。
2. **本地 ID 与服务器 ID 分离**：`messages.id` 是本地主键，`(folder_id, uid)` 是服务器身份，二者不可混用。
3. **单一写入者**：一个写连接，所有写操作在事务内完成。
4. **可重建**：任何派生数据（FTS、正文缓存、原始邮件）都能从数据库 + 服务器重建，唯一不可重建的是草稿原文。
5. **显式维护 FTS**：不用 contentless / external content 表，删除与更新都显式写 SQL。

## 2. 存储布局

```
%APPDATA%/MyEmail/                 Windows；其余平台经 dirs 定位
├─ myemail.db                      SQLite 主库
├─ myemail.db-wal / -shm           WAL 附属文件（勿单独备份）
├─ bodies/{messages.id}.txt        正文纯文本（HTML 已由 html2text 转换）
├─ raw/{messages.id}.eml.gz        原始邮件（下载正文时同步留存）
├─ attach/{messages.id}/{part_index}_{safe_name}  附件缓存（按需）
├─ drafts/{drafts.id}/             草稿原文 + 托管附件
└─ logs/                           tracing 按天滚动，保留 7 天
```

`attach/` 根目录可由用户在设置中重定位：生效路径存于 `meta.attachment_dir`（空串或缺失表示默认 `attach/`），必须是绝对路径。迁移步骤为「复制附件树 → 更新设置 → 重写 `attachments.local_path` → 删除旧目录」；新目录必须为空或带有 `cache::ATTACHMENT_MARKER` 归属标记。`local_path` 始终保存绝对路径。

### 2.1 文件命名规则（v0.4 已回写大纲 §5.3）

大纲 §5.2 与本文一致，均使用 **本地 `messages.id`** 作为文件名（早期版本曾写作 `<message_id>`）。理由：

- RFC 5322 的 `Message-ID` **可以为空**，而文件名不能为空；
- 同一 `Message-ID` 可能重复出现（群发、转发失败重投、恶意邮件），用它会互相覆盖；
- 头部值可能含 `/`、`\`、`:`、超长串，直接做文件名有路径穿越与长度超限风险。

**规则**

| 位置 | 命名 | 说明 |
| --- | --- | --- |
| 正文 | `bodies/{messages.id}.txt` | 固定 `.txt`，UTF-8 |
| 原始邮件 | `raw/{messages.id}.eml.gz` | gzip 压缩 |
| 附件 | `attach/{messages.id}/{part_index}_{safe_name}` | `safe_name` 见下 |
| 草稿 | `drafts/{drafts.id}/` | 目录内含 `message.eml` 与 `attachments/` |

`safe_name` 规范化：仅保留字母、数字、`.`、`-`、`_` 与 CJK；其余替换为 `_`；去除开头的 `.`；截断到 100 字符；为空则用 `attachment`。文件名冲突时追加 `-1`、`-2`。

## 3. 领域类型（Rust）

```rust
// me-core/src/model.rs
pub struct AccountId(pub i64);
pub struct FolderId(pub i64);
pub struct MessageId(pub i64);   // = messages.id，本地主键
pub struct DraftId(pub i64);

pub enum FolderRole { Inbox, Sent, Drafts, Trash, Junk, Archive, Other }

pub struct Account {
    pub id: AccountId, pub email: String, pub display_name: Option<String>,
    pub imap: Endpoint, pub smtp: Endpoint, pub auth_user: String,
}

pub struct Endpoint { pub host: String, pub port: u16, pub tls: TlsMode }
pub enum TlsMode { Implicit, StartTls, None }   // None 默认不可选，见大纲 §2.1

pub struct Folder {
    pub id: FolderId, pub account: AccountId, pub name: String,
    pub delimiter: Option<char>, pub role: FolderRole,
    pub uid_validity: u32, pub last_uid: u32,
    pub deleted_on_server: bool,        // 服务器已删除、本地待用户确认
}

pub struct MessageSummary {
    pub id: MessageId, pub account: AccountId, pub folder: FolderId,
    pub uid: Option<u32>,               // None = 本地已移动、服务器身份待确认
    pub message_id: Option<String>,
    pub subject: Option<String>, pub from: Option<Address>,
    pub to: Vec<Address>, pub cc: Vec<Address>,
    pub date: Option<i64>, pub date_source: DateSource,
    pub size: Option<u32>, pub flags: Flags,
    pub snippet: Option<String>, pub has_attachment: bool,
    pub body_cached: bool,              // 对应 body_path.is_some()
}

pub enum DateSource { Header, Internal }   // 对应 date_source 列

pub struct Flags(pub u32);                  // 位掩码，见 §7
```

`Address` 序列化为 `{ "name": "...", "addr": "..." }`；`to_addrs` / `cc_addrs` 列存 `[Address]` 的 JSON 数组，避免显示名中的逗号被误拆。

## 4. Schema

### 4.1 连接初始化（每次取连接后执行）

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;   -- WAL 下的常规选择，兼顾安全与吞吐
```

启动时额外执行一次 `PRAGMA quick_check`；WAL 超过 64 MB 执行 `PRAGMA wal_checkpoint(TRUNCATE)`；剩余磁盘 < 500 MB 时暂停后台补全并提示。

### 4.2 完整 DDL

```sql
CREATE TABLE accounts (
    id            INTEGER PRIMARY KEY,
    email         TEXT NOT NULL UNIQUE,
    display_name  TEXT,
    imap_host     TEXT NOT NULL,
    imap_port     INTEGER NOT NULL,
    imap_tls      TEXT NOT NULL,        -- implicit | starttls | none
    smtp_host     TEXT NOT NULL,
    smtp_port     INTEGER NOT NULL,
    smtp_tls      TEXT NOT NULL,
    auth_user     TEXT NOT NULL,
    auth_method   TEXT NOT NULL DEFAULT 'password',  -- password | app_password | oauth2
    oauth_provider TEXT,                -- google | microsoft
    oauth_subject  TEXT,                -- 服务商稳定用户标识（可选）
    token_expires_at INTEGER,           -- unix 秒；仅展示/诊断，不参与令牌有效性判断
    needs_reauth   INTEGER NOT NULL DEFAULT 0,
    idle_enabled   INTEGER NOT NULL DEFAULT 1,
    poll_interval_secs INTEGER,         -- NULL = 跟随全局默认；非 NULL 时 60～3600
    created_at    INTEGER NOT NULL
);

CREATE TABLE folders (
    id           INTEGER PRIMARY KEY,
    account_id   INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    name         TEXT NOT NULL,         -- 服务器原名（modified UTF-7 解码后）
    delimiter    TEXT,
    role         TEXT NOT NULL DEFAULT 'other'
                 CHECK (role IN ('inbox','sent','drafts','trash','junk','archive','other')),
    uid_validity INTEGER NOT NULL DEFAULT 0,
    last_uid     INTEGER NOT NULL DEFAULT 0,
    deleted_on_server INTEGER NOT NULL DEFAULT 0,  -- 服务器已删除、本地待确认
    UNIQUE(account_id, name)
);
CREATE UNIQUE INDEX idx_folders_trash ON folders(account_id) WHERE role = 'trash';

CREATE TABLE messages (
    id             INTEGER PRIMARY KEY,
    account_id     INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    folder_id      INTEGER NOT NULL REFERENCES folders(id) ON DELETE CASCADE,
    uid            INTEGER,             -- NULL = 本地已移动、服务器身份待确认（见 §4.3）
    message_id     TEXT,
    subject        TEXT,
    from_addr      TEXT,
    from_name      TEXT,
    to_addrs       TEXT,                -- JSON 数组
    cc_addrs       TEXT,                -- JSON 数组
    date           INTEGER,             -- unix 秒
    date_source    TEXT NOT NULL DEFAULT 'header',
    size           INTEGER,
    flags          INTEGER NOT NULL DEFAULT 0,
    snippet        TEXT,
    has_attachment INTEGER NOT NULL DEFAULT 0,
    body_path      TEXT,                -- NULL = 正文未缓存；非 NULL = 已写入 FTS
    UNIQUE(folder_id, uid)
);
CREATE INDEX idx_messages_folder_date ON messages(folder_id, date DESC, id DESC);
CREATE INDEX idx_messages_account ON messages(account_id);
CREATE INDEX idx_messages_body_pending ON messages(account_id, folder_id, date DESC, id DESC) WHERE body_path IS NULL;
CREATE INDEX idx_messages_unread ON messages(folder_id, (flags & 1));   -- 未读计数：\Seen 位是表达式，普通索引用不上
CREATE INDEX idx_messages_indexed ON messages(account_id) WHERE body_path IS NOT NULL;   -- 正文索引覆盖率
CREATE INDEX idx_messages_message_id ON messages(folder_id, message_id);   -- 本地占位行与服务器行去重

CREATE TABLE attachments (
    id         INTEGER PRIMARY KEY,
    message_id INTEGER NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
    part_index INTEGER NOT NULL,
    filename   TEXT,
    mime_type  TEXT,
    size       INTEGER,
    local_path TEXT,
    is_inline  INTEGER NOT NULL DEFAULT 0,
    content_id TEXT,
    UNIQUE(message_id, part_index)
);

CREATE TABLE drafts (
    id           INTEGER PRIMARY KEY,
    account_id   INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    raw_path     TEXT NOT NULL,
    message_id   TEXT NOT NULL,
    subject      TEXT,
    to_addrs     TEXT,                  -- JSON 数组，草稿列表直接读取
    bcc_addrs    TEXT,                  -- JSON 数组；只存本地，不写入 RFC 5322
    status       TEXT NOT NULL CHECK (status IN ('draft','sent')),
    server_uid   INTEGER,
    server_uid_validity INTEGER,
    server_hash  TEXT,                  -- 上次同步的服务器规范化哈希
    local_hash   TEXT,                  -- 上次同步的本地规范化哈希
    sync_state   TEXT NOT NULL DEFAULT 'local_only',
    conflict_of  INTEGER,               -- 冲突副本指向原草稿（逻辑外键）
    last_synced_at INTEGER,
    sync_attempts INTEGER NOT NULL DEFAULT 0,
    deleted_at   INTEGER,               -- 本地删除墓碑
    last_error   TEXT,
    updated_at   INTEGER NOT NULL
);
CREATE INDEX idx_drafts_account_state ON drafts(account_id, sync_state);
CREATE UNIQUE INDEX idx_drafts_server_identity
    ON drafts(account_id, COALESCE(server_uid_validity, 0), server_uid)
    WHERE server_uid IS NOT NULL AND deleted_at IS NULL;
CREATE INDEX idx_drafts_message_id ON drafts(account_id, message_id);
CREATE INDEX idx_drafts_updated ON drafts(account_id, updated_at DESC, id DESC);   -- 草稿列表排序

CREATE VIRTUAL TABLE messages_fts USING fts5(
    subject, body, from_addr, to_addrs,
    tokenize='trigram'
);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);
```

> v0.2 起，新库直接按上表创建并写入 `schema_version = 2`；v1 库的纯加列迁移见 §9。
> v2 迁移**只加列/索引**，新增列不加 `CHECK`/外键：`sync_state` 的合法值由 `me-store` 写入前校验，`conflict_of` 为逻辑外键。
>
> **禁止依赖物理列序。** v1 库经 `ALTER TABLE ADD COLUMN` 迁移后，新列只能追加到表尾，因此迁移库的列序与本节的逻辑列序不同：`accounts.created_at`、`drafts.last_error` / `updated_at` 会被新列挤到前面。两边的字段名、类型、`NOT NULL`、`DEFAULT`、`CHECK`、外键与索引**完全等价**，由 `me-store/tests/migration_v1_v2.rs::migrated_v2_matches_fresh_v2_schema` 守护。因此任何 `SELECT *` 或不带列名的 `INSERT ... VALUES` 都可能因列序差异错位，一律禁止（当前仓库已无此类写法）。

### 4.3 待同步队列表（v0.4 已并入大纲 §5.1）

```sql
-- 待同步标志：同一邮件的多次变更合并为最终态
CREATE TABLE pending_flags (
    message_id   INTEGER PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
    target_flags INTEGER NOT NULL,      -- 目标态，非增量
    attempts     INTEGER NOT NULL DEFAULT 0,
    last_error   TEXT,
    updated_at   INTEGER NOT NULL
);

-- 待同步操作：本地已生效、服务器尚未确认的移动 / 永久删除
CREATE TABLE pending_ops (
    id               INTEGER PRIMARY KEY,
    account_id       INTEGER NOT NULL REFERENCES accounts(id) ON DELETE CASCADE,
    kind             TEXT NOT NULL,     -- move_to_trash | delete_permanent | empty_folder
    message_id       INTEGER REFERENCES messages(id) ON DELETE SET NULL,
    source_folder_id INTEGER REFERENCES folders(id) ON DELETE SET NULL,
    source_folder_name TEXT,            -- 文件夹被删后仍可读
    source_uid       INTEGER,           -- 移动前所在文件夹的 UID
    target_folder_id INTEGER REFERENCES folders(id) ON DELETE SET NULL,
    attempts         INTEGER NOT NULL DEFAULT 0,
    last_error       TEXT,
    created_at       INTEGER NOT NULL
);
CREATE INDEX idx_pending_ops_account ON pending_ops(account_id, attempts);
```

**`pending_flags` 存目标态而非增量**：用户连续切三次星标，只会留下最后一行最终状态，服务器同步一次即可；若存增量则需要保序且可能互相抵消。

**`uid` 可空的理由**：本地「移入废件箱」后，邮件行改指向 Trash 文件夹，但它的 `uid` 仍属于源文件夹，与 Trash 的 UID 空间冲突。改为允许 `uid` 为 NULL（本地已移动、服务器身份待确认），原位置记录在 `pending_ops.source_folder_id / source_uid`。SQLite 的 `UNIQUE` 视 NULL 互不相等，因此多行 `uid IS NULL` 不会冲突；去重补 UID 的规则见 §6.4。

**待同步操作必须独立于本地行**：永久删除/清空废件箱会删除 `messages` 行，若 `message_id` 使用 `CASCADE`，队列里的 `delete_permanent` 会一起消失，服务器端删除永远发不出去。因此 `message_id` 与 `source_folder_id` 都用 `ON DELETE SET NULL`，执行时以 `source_folder_id + source_uid` 为准；`source_folder_name` 保留可读名称。源文件夹本身被删（`UIDVALIDITY` 重建或服务器删除）时，该操作已无意义，由清理任务删除并记录日志。

**移动确认**：`MOVE` 成功后本地行仍为 `uid=NULL`。支持 `UIDPLUS` 时直接用 `COPYUID` 回填；不支持时对目标文件夹执行 `UID SEARCH HEADER Message-ID <id>` 定向补齐；确认后才删除 `pending_ops`。目标文件夹暂不可同步时保持 `uid=NULL`，操作继续等待。

**约束与版本**：v1 发布时，`drafts.status` 的 `CHECK` 与 `attachments(message_id, part_index)` 的唯一键直接进建表语句，`schema_version = 1`。v2（0.2.0）只做纯加列 + 新索引，不新增 `CHECK`/外键；`drafts.bcc_addrs`、同步基线与墓碑字段见 §5.3。v2 冻结后改列必须走 v3 迁移。

### 4.4 v3 增量 DDL（v0.3：日历 / 天气 / AI）

> v3 **只新增表与索引**，不修改 v1/v2 的既有表。因此不需要 `ALTER TABLE`，也不存在「给已有表补约束」的风险。
> 新建库与 v2→v3 迁移**共用同一份 SQL**（`migrations.rs` 的 `SCHEMA_V3_DDL`），两条路径的物理结构必然一致——这一点由 `crates/me-store/tests/migration_v1_v2.rs::v2_database_upgrades_to_v3_in_place` 与 `calendar_store.rs` 守护。
>
> **v4 / v5 / v8 是这份 DDL 之上的三次纯加列**：`ai_conversations.model_id`、`ai_messages.plan`、
> `ai_messages.thinking`。**v6 是纯索引调整**：见 §6 的四条索引（列序必须与 `ORDER BY` 前缀对齐）。
> 这三列**已包含在本节的 `SCHEMA_V3_DDL` 里**（新建库直接带上，`thinking` 追加在表尾），因此：
> - 新建库与 v8 库的结构完全一致，不需要迁移；
> - 从 v3 / v4 / v7 等更早的库升级时，由 `migrate_v3_to_v4` / `migrate_v4_to_v5` / `migrate_v7_to_v8`
>   幂等补列（判据是 `pragma_table_info` 查列是否存在，见 §9）。

```sql
CREATE TABLE calendars (
    id         INTEGER PRIMARY KEY,
    name       TEXT NOT NULL,
    color      TEXT NOT NULL DEFAULT '#3B82F6',
    visible    INTEGER NOT NULL DEFAULT 1 CHECK (visible IN (0,1)),
    is_default INTEGER NOT NULL DEFAULT 0 CHECK (is_default IN (0,1)),
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX ux_calendars_default
    ON calendars(is_default) WHERE is_default = 1;

CREATE TABLE calendar_events (
    id          INTEGER PRIMARY KEY,
    calendar_id INTEGER NOT NULL REFERENCES calendars(id) ON DELETE CASCADE,
    uid         TEXT NOT NULL,
    summary     TEXT NOT NULL DEFAULT '',
    description TEXT,
    location    TEXT,
    start_utc   INTEGER NOT NULL,
    end_utc     INTEGER NOT NULL,
    all_day     INTEGER NOT NULL DEFAULT 0 CHECK (all_day IN (0,1)),
    timezone    TEXT,
    rrule       TEXT,
    recurrence_until INTEGER,
    exdates     TEXT NOT NULL DEFAULT '[]',
    reminders   TEXT NOT NULL DEFAULT '[]',
    status      TEXT NOT NULL DEFAULT 'confirmed'
                CHECK (status IN ('confirmed','tentative','cancelled')),
    source      TEXT NOT NULL DEFAULT 'local'
                CHECK (source IN ('local','ics','ai')),
    sequence    INTEGER NOT NULL DEFAULT 0,
    created_at  INTEGER NOT NULL,
    updated_at  INTEGER NOT NULL,
    deleted_at  INTEGER,
    CHECK (end_utc >= start_utc),
    CHECK (recurrence_until IS NULL OR recurrence_until >= start_utc)
);
CREATE UNIQUE INDEX ux_calendar_events_uid
    ON calendar_events(calendar_id, uid) WHERE deleted_at IS NULL;
CREATE INDEX ix_calendar_events_range
    ON calendar_events(calendar_id, start_utc, end_utc);
CREATE INDEX ix_calendar_events_recurring
    ON calendar_events(calendar_id, start_utc) WHERE rrule IS NOT NULL AND deleted_at IS NULL;
CREATE INDEX ix_calendar_events_updated
    ON calendar_events(updated_at);
CREATE INDEX ix_calendar_events_reminder
    ON calendar_events(start_utc) WHERE reminders <> '[]' AND deleted_at IS NULL;

CREATE TABLE calendar_event_exceptions (
    id            INTEGER PRIMARY KEY,
    event_id      INTEGER NOT NULL REFERENCES calendar_events(id) ON DELETE CASCADE,
    recurrence_at INTEGER NOT NULL,
    cancelled     INTEGER NOT NULL DEFAULT 0 CHECK (cancelled IN (0,1)),
    summary       TEXT,
    description   TEXT,
    location      TEXT,
    start_utc     INTEGER,
    end_utc       INTEGER,
    all_day       INTEGER,
    updated_at    INTEGER NOT NULL,
    UNIQUE(event_id, recurrence_at)
);

CREATE TABLE calendar_reminder_fires (
    event_id       INTEGER NOT NULL REFERENCES calendar_events(id) ON DELETE CASCADE,
    occurrence_at  INTEGER NOT NULL,
    minutes_before INTEGER NOT NULL,
    fired_at       INTEGER NOT NULL,
    PRIMARY KEY (event_id, occurrence_at, minutes_before)
);
CREATE INDEX ix_calendar_reminder_fires_time
    ON calendar_reminder_fires(fired_at);

-- v0.3 尚未接入天气 / AI，表结构先建全，避免二次 schema 迁移。

    latitude             REAL NOT NULL CHECK (latitude BETWEEN -90 AND 90),

CREATE TABLE weather_snapshots (
    location_id INTEGER PRIMARY KEY REFERENCES weather_locations(id) ON DELETE CASCADE,
    provider    TEXT NOT NULL,

-- payload 是版本化 JSON：{"v": 2, "snapshot": {...}}。

-- 表结构本身不变，故不需要 v4 迁移。

CREATE TABLE ai_conversations (
    id         INTEGER PRIMARY KEY,
    title      TEXT NOT NULL,
```

### 4.5 v7 增量 DDL（v0.4：联系人 / 保存的搜索 / 会话线程）

v0.4 的唯一 DDL 级变更，三项合并做一次迁移。

```sql
-- 联系人：**本地派生数据**，由正文补全落库 / 发信归档时累积。
-- 永不出网、不参与 AI 请求；ClearCache 不清理它（与 D30 一致）。
CREATE TABLE IF NOT EXISTS contacts (

    -- 但显示时保留原样更友好。

CREATE UNIQUE INDEX IF NOT EXISTS ux_contacts_normalized ON contacts(normalized);

-- 保存的搜索：只存**条件**，不做自动动作（D42）。
-- `query_json` 存 `SearchQuery` 的**持久化子集**——不含 `cursor` / `limit`
-- 这类分页态。
CREATE TABLE IF NOT EXISTS saved_searches (
    id            INTEGER PRIMARY KEY,
    name          TEXT NOT NULL,
    query_json    TEXT NOT NULL,
    created_at    INTEGER NOT NULL,
    last_used_at  INTEGER NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_saved_searches_name ON saved_searches(name);
```

**`messages` 补两列**（会话线程）：

```sql
-- 会话线程（v7 加列）：`In-Reply-To` / `References` 头。
-- **必须可空**：NOT NULL DEFAULT '' 会让历史行全是空串，
-- 与「有但为空」混淆；用 NULL 表示「未知」。
-- 注：`references` 是 SQLite 的**保留关键字**，列名必须加引号。
ALTER TABLE messages ADD COLUMN in_reply_to TEXT;
ALTER TABLE messages ADD COLUMN "references" TEXT;   -- JSON 数组
```

> ⚠️ **`references` 是 SQLite 保留关键字**：DDL 与所有 SQL 里列名必须写 `"references"`。
> `pragma_table_info` 返回的列名**不带**引号，比对时按裸名 `references` 匹配。

**`NULL` 与 `"[]"` 不是一回事**（v0.4 C5 的回填队列依赖这个区分）：

| 值 | 含义 | 谁写 |
| --- | --- | --- |
| `NULL` | **还没回填过**（历史邮件，或入库时本来就没有回复头） | 同步入库 |
| `"[]"` | **回填过，确实没有引用链** | 离线回填任务 |
| `["a@x","b@x"]` | 祖先链，根在前 | 入库 / 回填 |

队列判据是 `in_reply_to IS NULL AND "references" IS NULL`；把空链写成 `NULL`
会让没有回复头的邮件永远留在队列里、每次启动重解析一遍。

**`contacts` 的去重规则**：`normalized`（小写）唯一——邮箱大小写不敏感，
但 `addr` 保留原样用于显示。重复出现只更新 `last_seen` 与 `seen_count`，不新增行。

**`saved_searches` 只存条件**：D42 拍板「保存的搜索只存条件、不做自动动作」，
自动规则推迟到用户真的用了一阵子之后再说。

### 4.6 v8 增量 DDL（思考块落库）

v0.4 之后唯一的 DDL 级变更：给 `ai_messages` 补一列，存本轮的思考块（纯展示，**不回灌上下文**）。

```sql
-- 思考内容（v8 加列）：JSON `{segments: [{index, text, followed_by_tool}], truncated}`。
-- 必须可空：NULL = 这家服务商不返回思考（老行 / 非推理模型）；
-- 空块（segments 为空或全空串）= 返回过但被过滤/截断——UI 据此区分「没有」与「有但丢了」。
-- 不复用 `content`：思考是**纯展示**的，不进下一轮请求——混进正文既会被
-- 回灌，也会让「复制这段回答」带上推理过程。
ALTER TABLE ai_messages ADD COLUMN thinking TEXT;
```

- **幂等判据是列存在性**（`pragma_table_info`），不是版本号：新建库的 DDL 已带这一列，
  无条件 `ALTER` 会报 duplicate column。
- **目标版本写死 `8`**，不能写 `SCHEMA_VERSION`——否则 v7 库会被一步盖上「已是最新」。
- 思考块**不参与**任何检索与索引，也不进 FTS。落库前已按 `MAX_THINKING_CHARS` / `MAX_THINKING_SEGMENTS`
  截断并置 `truncated`，DB 侧只做整体存储。
- **列必须追加在表尾**：`map_message` 按位置索引读列，插在中间会让所有下游列错位。

## 5. 字段语义

### 5.1 messages

| 列 | 语义 | 取值 / 约束 |
| --- | --- | --- |
| `id` | 本地主键 | 自增；**不对应任何服务器标识** |
| `uid` | 该邮件在**当前文件夹**的 IMAP UID | 可为 NULL（待确认，见 §4.3） |
| `message_id` | RFC 5322 `Message-ID` | 可空、可重复；仅用于去重与展示 |
| `to_addrs` / `cc_addrs` | `[Address]` 的 JSON | 不用逗号分隔，避免 `Doe, John` 被拆开 |
| `date` | unix 秒 | `Date` 头失败时取 `INTERNALDATE` |
| `date_source` | `header` / `internal` | 供排错与导出使用 |
| `flags` | 位掩码 | 见 §7 |
| `snippet` | 列表预览文本 | 补全完成时由正文前 200 字符生成；同步阶段必为 NULL（已定，见 §11） |
| `has_attachment` | 来自 `BODYSTRUCTURE` | 0/1；不要靠正文解析补，避免全量下载 |
| `body_path` | 正文文件相对路径 | NULL ⇔ 未缓存且未进 FTS |

**不变量**：`(folder_id, uid)` 唯一；`body_path IS NOT NULL` ⇔ `messages_fts` 中该 rowid 的 `body` 列已写入。

### 5.2 folders

- `name` 存**解码后**的 UTF-8 名称；与服务器通信时再编码为 modified UTF-7。`UNIQUE(account_id, name)` 因此作用在解码后的字符串上。
- `role` 非空，取值由 `CHECK` 限制；由 `SPECIAL-USE` 优先判定，否则按名称启发式，最终可由用户手动改写。`role='trash'` 是删除语义的锚点，同一账户下必须唯一（部分唯一索引保证）；多个候选时以用户选择为准。
- **没有 trash 角色时**：UI 禁用删除并提示先创建废件箱或手动指定角色；不退化为永久删除。
- **改名**：同步发现同名文件夹消失、新名出现时，按 `UIDVALIDITY` + delimiter + 角色匹配；命中则只 `UPDATE name`，不删建、不重建 `messages` 与 FTS。
- **服务器删除文件夹**：置 `deleted_on_server=1`，在树中标记“服务器已删除”；用户确认后才删除本地文件夹及其邮件与 FTS 行。未确认时保留只读缓存。同名文件夹重新出现时清除该标记，不插入重复行。
- `last_uid` 只在**一批数据完整写入**后才推进，取消与崩溃不会跳过邮件。

### 5.3 drafts

- `raw_path` 指向 `drafts/<id>/message.eml`，是**唯一不可重建**的数据。
- `message_id` 在首次保存时生成并固定，重发复用。
- 草稿列表直接读 `subject` / `to_addrs` / `updated_at`，不解析 `raw_path`；普通列表过滤 `deleted_at IS NOT NULL` 与 `conflict_of IS NOT NULL`。
- 草稿行删除时一并删除 `drafts/<id>/`；发送成功后目录保留，直到用户删除草稿；启动时清理无对应行的孤儿目录。
- `status` 只有 `draft` / `sent`；发送成功但归档失败仍为 `sent`，失败原因记 `last_error`。`status = 'sent'` 不参与草稿双向同步。
- `bcc_addrs` 为 `[Address]` JSON，**只存本地**；`build_rfc822` 不输出 `Bcc`，重新打开草稿时从该列恢复。
- `sync_state` 只允许 `local_only` / `synced` / `local_dirty` / `conflict` / `deleted_local` / `deleted_server`；状态迁移由 `me-sync` 决定，`me-store` 写入前校验。
- `local_hash` / `server_hash` 是两侧各自的同步基线；**不直接比较两者相等**，只判断各自是否变化（Bcc/头部差异会造成假冲突）。
- `server_uid_validity` 为 NULL 表示服务器身份尚未建立基线（v1 迁移行或 UIDVALIDITY 重置后）；重新绑定成功后写入真实值。
- `(account_id, COALESCE(server_uid_validity, 0), server_uid)` 在 `server_uid` 非空且未删除时唯一。冲突副本不得复用同一服务器身份。
- `conflict_of` 指向原草稿；冲突副本不进普通列表，按 Message-ID 与原草稿一起取出。
- `deleted_at` 是本地删除墓碑；非空行不参与普通列表与自动推送，只进入服务器删除确认候选；确认后才物理删除。目录保留到确认完成。
- `sync_attempts` 是连续失败次数；成功或用户手动重试时清零；达到 3 后停止自动重试并提示人工处理。

### 5.4 attachments

- `part_index` 是 MIME 部件序号，由本应用在解析时编号，`UNIQUE(message_id, part_index)` 保证唯一。
- `local_path` 为 NULL 表示未下载；下载后写入附件根目录（默认 `attach/`，可由 `meta.attachment_dir` 重定位）下的 `<messages.id>/`，保存绝对路径。

### 5.5 accounts（v0.2 新增列）

- `auth_method = 'oauth2'` ⇔ `oauth_provider IS NOT NULL`；密码/授权码账户的 `oauth_provider` 为空。
- `oauth_provider`：`google` / `microsoft`；OAuth2 账户的 IMAP/SMTP 必须为 `implicit` 或 `starttls`，禁止明文。
- `oauth_subject`：服务商稳定用户标识（可选），由 userinfo/id_token 得到，仅用于展示与去重。
- `token_expires_at`：访问令牌绝对过期时间（unix 秒），**仅展示/诊断**，不参与令牌有效性判断。
- `needs_reauth`：刷新令牌失效或缺失时置 1；成功刷新后清零。UI 显示「需要重新授权」。
- `idle_enabled`：单账户是否尝试 IDLE；默认 1。全局 `realtime_sync=false` 时整体关闭。
- `poll_interval_secs`：NULL = 跟随 `meta.poll_interval_secs`；非 NULL 时覆盖全局，范围 60～3600。
- 令牌不落库：表中只有非敏感元数据；刷新令牌在系统密钥库（或会话内存），访问令牌只在进程内存。

## 6. 索引与查询模式

### 6.1 邮件列表（键集分页）

```sql
-- 首页
SELECT * FROM messages
 WHERE folder_id = ?1
 ORDER BY date DESC, id DESC
 LIMIT ?2;
-- 下一页（传入上一页最后一行的 date/id）
SELECT * FROM messages
 WHERE folder_id = ?1 AND (date < ?2 OR (date = ?3 AND id < ?4))
 ORDER BY date DESC, id DESC
 LIMIT ?5;
```

用键集而非 `OFFSET`：10 万行下 `OFFSET 50000` 仍需扫描前 5 万行；键集分页恒定代价。索引 `idx_messages_folder_date(folder_id, date DESC, id DESC)` 直接支撑。

> **索引列序必须与 `ORDER BY` 的前缀严格对齐**（不只是「补一个 id」）。
> 若索引只到 `(folder_id, date DESC)`，SQLite 会用
> `USE TEMP B-TREE FOR LAST TERM OF ORDER BY` 临时排序补齐 `id DESC` 那一段。
> 同理，`(account_id, date DESC, folder_id, id DESC)` 也**不能**满足
> `ORDER BY folder_id, date DESC, id DESC` —— 首列必须是 `folder_id`。

### 6.2 未读计数

```sql
SELECT COUNT(*) FROM messages WHERE folder_id = ?1 AND (flags & 1) = 0;
```

文件夹树上的计数按需刷新，不做实时聚合（避免每次标志变化触发全量扫描）。

> `(flags & 1) = 0` 是**表达式**，普通索引帮不上忙 —— SQLite 只能命中
> `folder_id` 前缀，然后逐行回表求值。索引 `idx_messages_unread(folder_id, (flags & 1))`
> 是**表达式索引**，命中后走覆盖扫描，不必回表。
>
> 代价随**账户总邮件数**增长，与待补全/未读的数量无关。
> 实测（5 万行、13 个文件夹）：无此索引 60.18 ms → 有此索引 1.28 ms（47×）。

### 6.3 正文补全队列

```sql
-- 按文件夹分组；文件夹内部按时间倒序，保证最近的邮件先被全文索引
SELECT id, folder_id, uid FROM messages
 WHERE account_id = ?1 AND body_path IS NULL AND uid IS NOT NULL
 ORDER BY folder_id, date DESC, id DESC
 LIMIT ?2;
```

依赖部分索引 `idx_messages_body_pending`。`uid IS NOT NULL` 排除尚未确认服务器身份的本地行。执行侧先按 `folder_id` 分组，对每个文件夹 `SELECT` 后批量 `FETCH`；逐封使用 `BODY.PEEK[]`（禁止 `BODY[]`，否则会把邮件标为已读）。

> **`folder_id` 必须排在最前。** 执行侧（`me-sync/src/indexer.rs`）是**游程式**消费：`jobs[index].folder` 之后只消费「连续同 `folder_id`」的那一段，对每段做一次 `SELECT` 再批量 `FETCH`。若把 `date` 放到 `folder_id` 前面，不同文件夹的邮件会交错，同一文件夹被反复 `SELECT`，IMAP 往返成倍增加。
>
> **排序语义**：文件夹之间按 `folder_id` 升序（INBOX 等主文件夹 id 小、先补），**文件夹内部按 `date DESC`**。这是「最近优先」的主要落点——绝大多数待补全邮件都在 INBOX。`date` 可为 NULL（缺 Date 头），SQLite 在 `DESC` 下把 NULL 排末位；`id DESC` 作 tiebreaker，保证同一天内次序稳定不抖动。
>
> **索引列序必须与 `ORDER BY` 前缀对齐**（schema v6 起）：
> `idx_messages_body_pending(account_id, folder_id, date DESC, id DESC) WHERE body_path IS NULL`。
> 首列 `account_id` 对应 `WHERE`，次列 `folder_id` 对应 `ORDER BY` 的首列。
>
> 此前索引是 `(account_id, folder_id, uid)`，末尾的 `uid` **满足不了**新的 `ORDER BY`，
> 于是 SQLite **整个弃用这条部分索引**，转而扫账户全部邮件再排序
> （`USE TEMP B-TREE FOR ORDER BY`）。代价随**账户总邮件数**增长，
> **与待补全数量几乎无关** —— 待补全占比越低，退化越严重：
>
> | 总行数 | 待补全占比 | 旧索引 | 新索引 | 倍数 |
> | ---: | ---: | ---: | ---: | ---: |
> | 50,000 | 5% | 6.72 ms | 0.22 ms | 31× |
> | 50,000 | 50% | 9.82 ms | 0.21 ms | 46× |
> | 200,000 | 5% | 28.62 ms | 0.22 ms | 130× |
> | 200,000 | 50% | 46.05 ms | 0.32 ms | 144× |
>
> 补全全程（每批 200 封查一次队列，`body_jobs` 持**全局写锁**）：
> 20 万行 / 50% 待补全 = 500 批，旧索引累计 **25.57 s** → 新索引 **0.19 s**。
>
> ⚠️ 注意**不要**用 `ON messages(account_id, date DESC) WHERE body_path IS NULL` ——
> 实测仍是 6.85 ms（与旧索引持平），因为 `ORDER BY` 的首列是 `folder_id`，
> 索引首列不匹配就消不掉排序。

### 6.4 服务器插入前的去重

本地移动过的邮件在服务器上会以新 UID 出现，若直接 INSERT 会产生重复行。规则：

```
插入 (folder_id, uid, message_id) 前：
  1. 若存在同 folder_id + 同 message_id 且 uid IS NULL 的行
     → UPDATE 该行 set uid = 新 UID，删除对应 pending_ops，不插入
  2. 否则正常 INSERT
  3. message_id 为 NULL 时不走去重（无法判定同一性）
     → 后果：无 UIDPLUS 时，移动无法经 UID SEARCH HEADER Message-ID 确认，
       该行保持 uid=NULL、pending_ops 持续等待；该行不进入正文补全队列（见 §11）

移动确认：
  1. 有 UIDPLUS → 从 COPYUID 取得目标 UID，UPDATE 本地行，删除 pending_ops
  2. 无 UIDPLUS → 对目标文件夹执行 UID SEARCH HEADER Message-ID <id>，命中后回填，删除 pending_ops
  3. 目标文件夹暂不可同步 → 保持 uid=NULL，pending_ops 继续等待
```

依赖 `idx_messages_message_id(folder_id, message_id)`。

### 6.5 搜索

```sql
-- 词长 ≥ 3：FTS + 过滤
SELECT m.* FROM messages m
  JOIN messages_fts f ON f.rowid = m.id
 WHERE f MATCH ?1
   AND m.folder_id IN (SELECT value FROM json_each(?2))
   AND m.date >= ?3
   AND (?4 = 0 OR m.has_attachment = 1)
 ORDER BY m.date DESC LIMIT ?5;

-- 词长 1～2：仅头部 LIKE
SELECT * FROM messages
 WHERE (subject LIKE ?1 OR from_addr LIKE ?1 OR to_addrs LIKE ?1)
 ORDER BY date DESC LIMIT ?2;
```

`folder_ids` 以 JSON 数组绑定到 `?2`，用 `json_each` 展开；也可按数组长度生成占位符。`MATCH` 的查询串需转义双引号并整体加引号，避免 `:`、`OR`、`NEAR` 等被当作 FTS 语法。

**一次搜索发几条 SQL**：词长 ≥ 3 时是 3 条 —— FTS 总数、FTS 分页、正文索引覆盖率。
覆盖率那两条**刻意保持分开**，不要合并成 `COUNT(*), COUNT(body_path)`：
合并后 SQLite 只能整表扫一次（两个聚合都要全量行），5 万行实测 **7.3 ms**；
分开则各自走覆盖索引，各 **0.5 ms**（合计 1.1 ms）—— 合并反而慢 6.7 倍。
其中「已索引」那条靠 `idx_messages_indexed(account_id) WHERE body_path IS NOT NULL`
部分索引（6.68 ms → 0.56 ms，12×）。

**词长 1～2 的 LIKE 回退无法走索引**（`%xx%` 前缀通配），只能全表扫描，
成本随**账户总邮件数**线性增长（5 万行 11.96 ms）。已实测并**否决**了几个方案：

| 方案 | 实测 | 结论 |
| --- | ---: | --- |
| 改用 FTS 的 `LIKE`（trigram 索引原生支持） | 42.7 ms | **更慢** —— trigram 索引要扫三个列的 trigram 词条 |
| 加 `(date DESC, id DESC)` 索引让分页提前退出 | 常见词 0.17 ms，但**罕见词 173 ms** | **否决** —— 罕见词要扫完整棵索引，比原扫描慢 17 倍 |
| 给头部三列加覆盖索引 | 5.9 ms（原 6.1 ms） | 收益太小，不值一条索引 |

结论：1～2 字的查询保持现状（全表扫描），UI 已提示
「查询词 1～2 字时仅匹配头部，正文不参与」。

## 8. FTS5 维护

`messages_fts` 是**普通 FTS5 表**（非 external / contentless），`rowid` 与 `messages.id` 一一对应。

| 时机 | 操作 |
| --- | --- |
| 摘要入库 | `INSERT INTO messages_fts(rowid, subject, from_addr, to_addrs) VALUES (?,?,?,?)`，`body` 留空 |
| 正文补全完成 | `UPDATE messages_fts SET body = ? WHERE rowid = ?`（必须先 `INSERT` 或 `INSERT OR IGNORE` 保证行存在） |
| 删除邮件 / 清空文件夹 | `DELETE FROM messages_fts WHERE rowid IN (...)` |
| `UIDVALIDITY` 重建 | 先按 folder 查出所有 id，批量删除 FTS 行，再删 `messages` |
| 兜底 | `settings → 重建索引`（`RebuildIndex`）：清空 `messages_fts`，按 `body_path` 重新导入，完成后发 `IndexRebuilt` |

**一致性保证**：FTS 写入与 `messages.body_path` 更新放在**同一事务**；任何一步失败整体回滚，不产生「能搜到但打不开」的状态。

**已知限制**：trigram 要求查询 ≥3 字符；1～2 字查询只走头部 `LIKE`。

## 9. 迁移

- 版本号存 `meta.schema_version`（整数），当前为 `8`（v0.4 + 未定版增量）。v1 是 v0.1 的完整初始形态，v2 是 0.2.0，v3 引入日历/天气/AI 表，v4/v5 是 v0.3 期间的两次纯加列，v6 是 v0.4 的**纯索引调整**，v7 是 v0.4 的**唯一 DDL 级变更**，v8 给 `ai_messages` 补 `thinking`（思考块落库）。迁移链为 **v1→v2→v3→v4→v5→v6→v7→v8**，逐级执行，每步单独事务。
- **新库**：在同一事务里依次执行 §4.2 的 v2 DDL、§4.4 的 v3 增量与 §4.5 的 v7 DDL，写 `schema_version = 8`，不经过迁移。新建库的 DDL 已包含 v4/v5 两列、v6 的索引定义、v7 的两表两列与 v8 的 `thinking` 列，因此后续迁移对它是幂等的。
- **v1 → v2（纯加列）**：`Store::open` 读到版本 1 时：
  1. `PRAGMA wal_checkpoint(TRUNCATE)`，关闭连接；
  2. 复制 `myemail.db` 为 `myemail.db.bak-v1`（已存在则保留旧备份）；
  3. 重新打开，**保持** `PRAGMA foreign_keys = ON`；
  4. 单事务执行：`accounts`/`drafts` 加列、建 `idx_drafts_*`、初始化旧草稿 `sync_state`（有 `server_uid` → `local_dirty`，无 → `local_only`；`status='sent'` → `local_only`）、存在未上传草稿时写 `meta.draft_bulk_upload_pending=true`、删除 Drafts 文件夹下的历史 `messages` 与 FTS 行、写 `schema_version=2`；
  5. `PRAGMA foreign_key_check` 无结果后提交。
- **Drafts 历史行清理**：v0.1 把服务器草稿当普通邮件写入 `messages`；迁移只删除这些摘要行（`attachments`/`pending_flags` 随外键级联，`pending_ops.message_id` 置 NULL），本地 `drafts` 表与 `drafts/` 目录不受影响。不得在这段删除里关闭外键。
- **失败处理**：任一步失败回滚、不写版本号、启动中止并提示「数据库升级失败」，不自动重试、不自动降级；备份保留。
- **v2 → v3（纯新增表）**：`Store::open` 读到版本 2 时，单事务执行 §4.4 的 SQL 并写 `schema_version=3`。因为不改既有表，**不需要备份文件**，失败即回滚、版本留在 2，下次启动可重试。
- **v3 → v4（纯加列）**：给 `ai_conversations` 补 `model_id TEXT`（会话绑定的模型档案 id，可空——兼容 v0.3 早期无绑定的会话）。
- **v4 → v5（纯加列）**：给 `ai_messages` 补 `plan TEXT`（本轮任务清单的 JSON）。
- **v5 → v6（纯索引调整）**：不改列类型/`CHECK`/`NOT NULL`，只调整六条索引：
  - 重建 `idx_messages_folder_date` → `(folder_id, date DESC, id DESC)`（§6.1 邮件列表）；
  - 重建 `idx_messages_body_pending` → `(account_id, folder_id, date DESC, id DESC) WHERE body_path IS NULL`（§6.3 补全队列）；
  - 重建 `ix_ai_conversations_updated` → `(updated_at DESC, id DESC)`；
  - 重建 `ix_ai_entities_last_seen` → `(last_seen_at DESC, id DESC)`；
  - 新增 `idx_messages_unread(folder_id, (flags & 1))`（§6.2 未读计数）；
  - 新增 `idx_messages_indexed(account_id) WHERE body_path IS NOT NULL`（§6.5 正文索引覆盖率）；
  - 新增 `idx_drafts_updated(account_id, updated_at DESC, id DESC)`（草稿列表）。
- **v6 → v7（新增表 + 加列）**：v0.4 的唯一 DDL 级变更，三项合并做一次迁移——
  拆分意味着三次迁移、三次备份、三次签名比对测试，收益为零：
  - 新增 `contacts` 表（联系人，本地派生数据）；
  - 新增 `saved_searches` 表（保存的搜索，只存条件）；
  - 给 `messages` 补 `in_reply_to TEXT` 与 `"references" TEXT` 两列（会话线程）。
- ⚠️ **`references` 是 SQLite 的保留关键字**：DDL 与所有 SQL 里列名**必须加双引号**
  （`"references"`），否则报 `near "references": syntax error`。
  `pragma_table_info` 返回的列名**不带**引号，比对时按裸名 `references` 匹配。
- **v7 的两列必须可空**：`NOT NULL DEFAULT ''` 会让历史行全是空串，
  与「有但为空」混淆；用 `NULL` 表示「未知」。
- **v7 的幂等判据按变更类型分开**：建表用 `CREATE TABLE IF NOT EXISTS`（`SCHEMA_V7_DDL` 内）；
  加列用 `pragma_table_info` 判存在性（新建库的 `SCHEMA_V3_DDL` 已带这两列，
  无条件 `ALTER` 会报 duplicate column）。**目标版本写死 `7`**，不能写 `SCHEMA_VERSION`。
- **v7 不重复 v6 的索引定义**：`SCHEMA_V7_DDL` 只含本次的两表两列；
  那 6 条索引已在 `SCHEMA_V3_DDL` 里，改索引列序属于 v6 的职责。
- **v7 → v8（纯加列）**：给 `ai_messages` 补 `thinking TEXT`（思考块 JSON，可空）。幂等判据是
  `pragma_table_info` 查列存在性——新建库的 `SCHEMA_V3_DDL` 已带这一列，无条件 `ALTER` 会报
  duplicate column；**目标版本写死 `8`**。思考是纯展示数据，不进上下文、不进 FTS、不参与检索。
- **v6 的幂等判据是「先 DROP 再 CREATE」，不是版本号**：SQLite 没有 `ALTER INDEX`，
  改索引列序只能重建；而 `DROP INDEX IF EXISTS` + `CREATE INDEX` 对已存在的同名索引是幂等的，
  且列序**必然**与 DDL 一致。判据不能是版本号 —— 新建库走 `create_schema`，
  它的 DDL 已经建好了这些索引，迁移测试里也有「把新库回退成 v5 再升级」的路径。
- **索引列序必须与 `ORDER BY` 的前缀严格对齐**：这是 v6 存在的全部理由。  只补一个 `id` 是不够的 —— 首列不对，`ORDER BY` 仍要临时排序。
  详见 §6.1 / §6.3 的实测表。
- **v4 / v5 的幂等判据是列存在性，不是版本号**：用 `pragma_table_info` 查该列是否存在，缺了才 `ALTER TABLE ADD COLUMN`。原因：新建库走 `create_schema`，其 DDL 已带这两列；而 v2 库刚跑完 v3 时同样带列——两条路径到达这里时列的情况不同，靠版本号判断不可行。
- **中间步骤的版本号必须写死**（v2→v3 写 `3`、v3→v4 写 `4`、v4→v5 写 `5`、v5→v6 写 `6`、v6→v7 写 `7`、v7→v8 写 `8`），**不能写 `SCHEMA_VERSION`**。写 `SCHEMA_VERSION` 会给旧库盖上「已是最新」的章，把后续迁移步骤整段跳过。
- **v3 / v4 / v5 都不改既有约束**：`ai_messages` 上有 `role`/`status` 的 CHECK，改它们就得重建表，风险远大于收益，因此一律走纯加列。v6 连列都不动，只动索引。
- **v1 → v6**：先备份 `myemail.db.bak-v1`（沿用 v1→v2 的备份），再依次执行 `migrate_v1_to_v2` → `migrate_v2_to_v3` → `migrate_v3_to_v4` → `migrate_v4_to_v5` → `migrate_v5_to_v6`，每步各自独立事务。
- 升到更高版本：沿用同一模式，每个迁移函数独立事务（DDL 在 SQLite 中可回滚）。
- 破坏性变更（改列类型、加/改 `CHECK`、改 `NOT NULL`、加 `UNIQUE`）在 SQLite 中需「建新表 → 拷数据 → 删旧表 → 改名」，务必在同一事务内完成，并先复制 `myemail.db` 到 `myemail.db.bak-{version}`。**纯加列（`ALTER TABLE ADD COLUMN`）与纯索引调整都不算破坏性**，v1→v2、v3→v4、v4→v5、v5→v6、v7→v8 均属此类。
- 迁移前检查：破坏性重建才使用 `PRAGMA foreign_keys=OFF`，结束后恢复并执行 `PRAGMA foreign_key_check`；v1→v2 不需要关闭外键。
- v2 冻结后，任何列/索引变更必须走后续迁移，不得改写 `migrate_v1_to_v2`。

## 10. 事务与并发

| 操作 | 事务范围 |
| --- | --- |
| 一批邮件入库 | 单事务：`messages` 批量 INSERT + FTS 头部列 + `folders.last_uid` 更新；不触碰 `pending_flags` |
| 正文落盘 + 索引 | 文件写入成功后再开事务：`messages.body_path` + FTS `body` |
| 标志变更（本地） | 单事务：`messages.flags` + `pending_flags` UPSERT |
| 本地移动 | 单事务：`messages.folder_id/uid` + `pending_ops` INSERT |
| 服务器标志回拉 | 单事务：仅更新 `messages.flags`；有 `pending_flags` 的行跳过 |
| 永久删除 | 单事务：先 INSERT `pending_ops`，再 DELETE `messages`（SET NULL 保留操作） |
| 清理缓存 | 单事务：`messages.body_path` 置 NULL + 清空 FTS `body`；文件删除在事务外分批执行 |
| 发送 | 多步：草稿状态更新与服务器操作分离，避免长事务跨网络 |

**铁律**：事务内不做网络 IO。所有协议调用在事务外完成，结果再进事务写入。

## 11. 不一致与边界

| 场景 | 处理 |
| --- | --- |
| 正文文件被用户删除，`body_path` 仍非空 | 打开时文件缺失 → 置 `body_path=NULL`、删 FTS `body` 列、重新下载 |
| 服务器 `UIDVALIDITY` 变化 | 清空该文件夹 `messages` 与 FTS 行，`last_uid=0`，全量重同步 |
| 服务器邮件被其他客户端删除 | 已 `EXPUNGE` 的邮件不会出现在 FETCH 结果中，本地不主动删除；由用户或后续版本「校验」处理 |
| 服务器端标志变化 | 每轮分页 `UID FETCH 1:* (FLAGS)` 回拉；本地有 `pending_flags` 时以本地为准 |
| 服务器无 UIDPLUS | 禁用永久删除与清空废件箱；移入废件箱仍可用 MOVE/COPY 回退 |
| 本地移动的邮件 `message_id` 为空 | 无 `UIDPLUS` 时无法确认移动：行保持 `uid=NULL`（§6.4），`pending_ops` 仅在源文件夹被清理时结束（§4.3）；该行不进入正文补全队列（`uid IS NOT NULL`），也不参与去重 |
| 草稿原文目录丢失 | 无法恢复，`drafts` 行标记异常并在 UI 提示 |
| `snippet` 一直为空 | 正常现象：同步不拉正文，摘要来自正文补全。已在 v0.4 定为产品口径，列表在补全前只显示主题 / 发件人 / 时间 / 附件标记 |

## 12. 容量与清理

- 估算与依据见 `doc/可行性分析.md` §3.4：10 万封不含附件约 3～6 GB。
- 「清理缓存」：删 `bodies/`、`raw/`、`attach/`，保留 `messages`、`flags`、`folders`；同时把 `body_path` 置 NULL 并清空 FTS `body` 列（保持不变量）。清理后「从 `raw/` 重解析」的兜底不再成立。
