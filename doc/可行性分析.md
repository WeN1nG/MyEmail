# MyEmail 可行性分析

> 依据：`doc/项目大纲.md` v0.4（2026-11-01）
> 分析日期：2026-11-01　|　结论：**技术可行，以 3 个技术验证（Spike）作为 M2/M4/M5 的分阶段门禁**

---

## 1. 结论摘要

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 技术可行性 | **可行** | Rust 生态可覆盖 IMAP/SMTP/MIME/GUI/SQLite 全部需求，无必须自研的底层组件 |
| 进度可行性 | **基本可行，偏紧** | 单人全职约 3.5～5 个月（含 3 个 Spike）；主要不确定性在 IMAP 服务商兼容与 MOVE/EXPUNGE 细节 |
| 依赖风险 | **中等** | `async-imap` 活跃度存疑，是唯一可能触发协议层重写的依赖，已通过 `me-proto` 抽象层隔离；`html2text` 成熟度同为中等，但有明确替换路径 |
| 范围风险 | **低** | v0.1 已明确排除 OAuth2、HTML 渲染、IDLE、双向草稿同步 |
| 数据与隐私 | **需明确告知** | 本地正文与附件为明文缓存，凭证明文不落盘；不满足企业级合规存储要求 |
| 结论 | **Go（有条件）** | 按 §7 的门禁点执行 Spike A/B/C（A 在 M2 前，B/C 分别在 M4、M5 前），任一不达标则调整范围或替换依赖 |

**决定可行性的三个硬条件**

1. `async-imap` 在 QQ / 163 / Dovecot 上能完成登录、`LIST`、`FETCH`、`STORE`、`APPEND`；`BODYSTRUCTURE` 可用或可在 `me-proto` 内补命令；删除语义可由 `MOVE` **或** `COPY + \Deleted`（有 `UIDPLUS` 时才追加 `UID EXPUNGE`）回退路径正确实现（至少一条可用，且不误删未选中邮件）。
2. egui 在 10 万行邮件列表下可保持可用帧率（虚拟滚动 + 分页查询）。
3. SQLite FTS5 `trigram` 在 1 万封中文邮件上查询 P95 < 200 ms，索引体积 1 万封 ≤ 正文文本 3 倍、10 万封 ≤ 4 倍。上述查询与体积指标已写入大纲 §7 的 M5 验收标准（v0.4）；Spike C 实测不达标时需同步修订大纲指标与交付预期。

## 2. 分析范围与假设

**范围内**：大纲 §2.1 的 v0.1 功能；§3 的技术选型；§4 的架构与线程模型；§5 的数据模型；§7 的里程碑。

**范围外**：OAuth2、完整 HTML 渲染、IDLE、服务器草稿双向同步、PGP、移动端。

**估算假设**（若实际不符，工作量需重算）：

- 1 名全职 Rust 开发者，具备异步与 GUI 经验，无历史代码可复用
- 开发机与验收机为 Windows 11（8 核 / 16 GB / NVMe）
- 可用真实测试账号：QQ 邮箱、163 邮箱各 1 个（均开启 IMAP/SMTP 与授权码）
- 本地可用 Docker Desktop（WSL2）跑 GreenMail / Dovecot 做端到端测试
- 不包含代码签名采购、应用商店上架与多语言本地化

## 3. 技术可行性

### 3.1 依赖生态成熟度

| 依赖 | 成熟度 | 本项目用法 | 主要风险 | 备选 / 兜底 |
| --- | --- | --- | --- | --- |
| `egui` / `eframe` | 高 | 全部界面、表格、文本编辑 | 大列表需手写虚拟滚动；原生文件对话框需 `rfd` | `iced`（重写 UI 成本高） |
| `lettre` | 高 | SMTP 投递、MIME 构建、附件 | 各服务商对 EHLO/大小/限流策略不同 | 自写 SMTP 客户端（不建议） |
| `async-imap` | **中** | IMAP 登录、文件夹、增量同步、标志、APPEND | 维护活跃度、扩展命令覆盖不全 | 换 `imap` crate，或在 `me-proto` 内直接发原始命令 |
| `mail-parser` | 高 | 头部与 MIME 解析、附件提取 | 恶意/畸形 MIME 的健壮性需模糊测试 | 改用 `mailparse` |
| `rusqlite`（bundled） | 高 | 本地缓存、FTS5、迁移 | FTS5 trigram 体积；并发写需单写连接 | 改用 `sqlx` + 同版本 SQLite |
| `rustls` | 高 | 全部 TLS 连接 | 少数老旧服务器证书链异常 | 允许用户关闭证书校验需谨慎（不建议） |
| `keyring` | 中高 | Windows 凭据管理器 | 便携模式/策略限制下不可用；平台差异 | 已定义“仅本次会话记忆”降级 |
| `html2text` | 中 | HTML 正文转纯文本 | 复杂表格被压平，可读性下降 | 保留原文，v0.2 换完整渲染 |
| `egui_extras`（v0.3 已回写） | 高 | 虚拟滚动表格 | 与 egui 版本强绑定，须同版本升级 | 手写 `ScrollArea` + 只渲染可见行 |
| `rfd`（v0.3 已回写） | 高 | 原生文件选择、另存为、拖拽 | Windows 依赖 COM，须在 UI 线程调用 | `native-dialog` 或直接调 Windows API |
| `jieba-rs`（备选） | 中 | 中文预分词，仅在 Spike C 选该方案时引入 | 词典与分词一致性维护；换分词器需整体重建索引 | 保留 trigram，即当前默认方案 |

**结论**：处于中等成熟度及以下的是 `async-imap`、`html2text`、`keyring`（中高）与条件引入的 `jieba-rs`。真正可能触发返工的是 `async-imap`，其风险被架构中的 `me-proto` 层吸收，替换成本可控（预计 5～10 人日，含可能 fork 的维护成本）；`html2text` 的兜底是保留原文、v0.2 换完整渲染（预计 2～3 人日）；`keyring` 与 `jieba-rs` 都已有明确降级或替换路径，不影响 v0.1 交付。

上表中 `egui_extras`、`rfd` 原未列入大纲 §3.1，已在 v0.3 中回写；`jieba-rs` 仍为条件引入，不作默认依赖。

v0.4 新增的 `flate2`、`dirs`、`uuid`、`tokio-util`、`fs2`、`r2d2_sqlite`，以及既有的 `tokio`、`chrono`、`tracing`，均为成熟基础设施 crate，无协议级风险，不单列成熟度行。

### 3.2 协议层可行性

**IMAP 是本项目技术复杂度的主要来源**，以下问题必须在真实服务器上验证（全部归入 Spike A，M2 前完成）：

| 问题 | 影响 | 大纲中的处理 | 验证方式 |
| --- | --- | --- | --- |
| 网易/QQ 要求 `ID` 命令 | 不发送 `ID` 时部分服务器拒绝或行为异常 | `me-proto` 登录后按 `CAPABILITY` 发送 `ID`；失败不阻断登录 | Spike A：登录 163/QQ 实测 |
| `SPECIAL-USE` 未通告 | 无法自动识别 Sent/Drafts/Trash | 名称启发式 + 手动指定角色 | Spike A：`LIST` 能力检查 |
| 文件夹名使用 modified UTF-7 | 中文文件夹名乱码 | `me-proto` 自实现 modified UTF-7 编解码（`utf7.rs`） | Spike A：创建中文文件夹并往返 |
| `MOVE` 未实现 | 删除只能走 COPY + `\Deleted`（不 `EXPUNGE`） | 已定义回退路径；无 `UIDPLUS` 时不执行 `EXPUNGE` | Spike A：能力探测 + 回退实测 |
| `EXPUNGE` 的全邮箱副作用 | 可能顺带清除其他客户端标记的删除邮件 | v0.4 规定：仅 `UIDPLUS` 下使用 `UID EXPUNGE`；无 `UIDPLUS` 时禁用整文件夹 `EXPUNGE` | Spike A：多客户端同时标记删除后观察 |
| 无 `UIDPLUS` | 无法只清除指定 UID，`EXPUNGE` 只能整文件夹执行 | v0.4 规定：无 `UIDPLUS` 时禁用永久删除与清空废件箱；移入废件箱仍可用 `MOVE`/COPY 回退 | Spike A：检查 `UIDPLUS` |
| 服务商连接数限制 | 同步触发 `BYE` | 已定义串行 + 2 连接 + 退避 | Spike A + 压测 |
| 增量同步与 `UIDNEXT` | 重复拉取最后一封 | 已定义判空与 UID 过滤 | 单元 + mock 测试 |

**SMTP 侧**：`lettre` 覆盖 STARTTLS/隐式 TLS/认证/附件，主要风险是服务商限制（单封大小、发送频率、发件人验证），属于配置与提示问题，不构成技术阻塞。

### 3.3 客户端与性能可行性

- **10 万封列表**：egui 的表格需使用 `egui_extras::TableBuilder` 的按行渲染（只构建可见行），数据侧用键集分页（`LIMIT/OFFSET` 在 10 万行下代价高，不作为默认），不把 10 万行全部载入内存。
- **内存**：设计目标是分页加载——列表常驻仅当前页与导航元数据，常驻量在数十 MB 量级。150～300 MB 是“退化为全量常驻”时的上限估算（10 万封摘要 150～250 MB + egui 纹理与正文渲染），不是目标值；Spike B 需实测分页方案的实际常驻值。
- **中文字体**：egui 默认字体不含 CJK，需内嵌子集或加载系统字体；内嵌思源黑体子集约 3～6 MB，会增大二进制体积。
- **正文渲染**：纯文本 + 等宽/比例字体即可；10 万字符级正文需分段布局，egui 大段落性能需在 Spike B 中验证。
- **文件对话框 / 拖拽**：依赖 `rfd`，Windows 原生支持良好。

### 3.4 存储与搜索可行性（粗估）

假设：10 万封邮件，摘要 1.5 KB/封，正文纯文本平均 8 KB/封，不含附件。

| 项目 | 估算 | 说明 |
| --- | --- | --- |
| 摘要 + 索引 | 200～300 MB | `messages` 表、文件夹、标志、分页索引 |
| 正文缓存文件 | 0.8～1.2 GB | `bodies/*.txt`，文件系统块开销另计 |
| FTS5 trigram 索引 | 1.6～3.6 GB | 约为正文文本的 2～3 倍；这是最大不确定项 |
| 原始邮件 `raw/*.eml.gz` | 0.4～1.0 GB | 大纲 v0.3 定为「下载正文即留存」，覆盖率与正文缓存相同；gzip 后按纯文本 3～5 KB、HTML 10～15 KB 加权估算 |
| 附件 | 取决于用户 | 按需下载，可清理 |
| 合计（不含附件） | **约 3～6 GB** | 若关闭后台补全且停存 `raw/` 则降至百 MB 级 |

**风险**：trigram 索引体积可能超预期。兜底方案：
1. 关闭后台补全，仅索引打开过的正文；
2. 换 `jieba-rs` 预分词 + 普通 FTS5（索引更小，但需要中文词典依赖与分词一致性维护）；
3. 只对正文建索引、不保留正文文件（从 `raw/*.eml.gz` 重解析），牺牲打开速度。该方案的前提——`raw/` 覆盖全部已索引正文——已由大纲 v0.3 §5.3 的「下载正文即留存」保证。

**1～2 字查询**：trigram 无法命中，大纲已限定为仅搜头部并用 `LIKE`，方案成立；`LIKE '%x%'` 在 10 万行摘要上可接受（需实测）。该限制随分词方案变化：若 Spike C 改用 jieba 预分词，能命中几字取决于词典切分，需重新评估——本节结论只适用于 trigram 方案。

### 3.5 安全与隐私可行性

| 项 | 现状 | 评价 |
| --- | --- | --- |
| 凭证存储 | `keyring`，不落盘明文 | 满足个人使用；便携模式降级为内存 |
| 本地邮件缓存 | 明文文件 + 明文 SQLite | **不满足**企业合规/全盘加密要求，已写入大纲 §2.1（首次启动与设置页告知）与 M6 验收 |
| 日志 | 声明脱敏、不记录正文与凭证 | 需在实现中用类型约束（不传正文进日志宏）保证 |
| 恶意邮件 | 仅 `html2text`，不渲染 HTML、不加载远程图片 | 攻击面小；仍需对畸形 MIME 做 fuzz |
| 附件 | 按需下载，不自动打开 | 大纲 §2.1 已要求打开前提示风险；不自动执行 |
| 依赖供应链 | 主流 crate | 建议引入 `cargo-deny` 做许可证与漏洞检查 |
| 网络 | TLS 连接统一走 rustls | 需明确不支持“忽略证书错误” |
| 明文 TLS 模式 | 大纲 §2.1 与 `imap_tls` / `smtp_tls = none` 允许该配置 | **高风险**：SASL PLAIN 凭据与邮件全文明文过网，仅自建内网/测试环境可接受。大纲 v0.3 已定为默认禁止，仅「高级」+ 风险确认后可启用，账户列表常驻风险标记 |

### 3.6 服务商兼容性

| 服务商 | v0.1 支持 | 依据 | 备注 |
| --- | --- | --- | --- |
| QQ 邮箱 / 163 | 预期支持 | 密码改用授权码，IMAP/SMTP 开放 | 需 Spike A 实测 `ID`、限流、附件上限 |
| 自建 Dovecot / Postfix | 支持 | 标准 IMAP/SMTP | 端到端测试的主要环境 |
| Gmail / Outlook | **不支持** | 已禁用基础认证 | v0.2 做 OAuth2 后才能接入 |
| 企业 Exchange（IMAP 模式） | 视配置 | 取决于是否开放 IMAP 基础认证 | 不承诺 |

### 3.7 架构与线程模型

| 检查点 | 判断 | 说明 |
| --- | --- | --- |
| 立即模式 GUI + 独立 tokio 运行时 | 可行 | egui 每帧重建 UI，主线程不做阻塞；DB 与网络调用一律经 `spawn_blocking` / tokio 任务，与大纲 §4.2 的分工一致 |
| `Command` / `Event` 单向契约 | 可行 | UI 只发命令、只读事件，`me-core` 不依赖 tokio/rusqlite，领域逻辑可脱离运行时单测——这是本项目最稳的一层 |
| `Event` 通道无背压 | 原设计需改，**v0.3 已修正** | 大纲原用 `UnboundedSender<Event>`，后台补全 10 万封时若 UI 帧率低，`IndexProgress` 会持续堆积；v0.3 改为有界通道（1024）+ 进度事件按 ≥200 ms 或每 50 封合并，关键事件不丢弃 |
| 标志回拉 | 可行 | 每轮分页 `UID FETCH 1:* (FLAGS)`；本地 `pending_flags` 优先，服务器变更不回写队列（大纲 §2.2/§4.3） |
| 单写连接 + 读连接池 | 可行 | 与 SQLite 单写者模型匹配；需配合 `busy_timeout` 与 WAL，相关故障见风险 R11 |

## 4. 进度与工作量

### 4.1 分阶段估算（单人，全职，单位：人日）

| 阶段 | 内容 | 乐观 | 保守 | 主要不确定性 |
| --- | --- | --- | --- | --- |
| M0 骨架 | workspace、日志、schema 初始化、空窗口 | 3 | 5 | 无 |
| M1 账户 | 账户 CRUD、keyring、连接测试、TLS 组合 | 5 | 8 | 各服务商 TLS/认证差异 |
| M2 收信 | 文件夹、增量同步、列表、标志、BODYSTRUCTURE | 10 | 15 | `ID`、UTF-7、MOVE、限流 |
| M3 读信 | 按需正文、已读回写、html2text、附件、索引 | 7 | 10 | 大正文渲染性能 |
| M4 发信 | 纯文本撰写、附件、SMTP、Sent 归档、草稿 | 10 | 15 | 部分成功与重发边界 |
| M5 搜索 | 头部索引、后台补全、FTS、过滤 | 8 | 12 | trigram 体积与查询性能 |
| M6 打磨 | 界面状态、缓存清理、日志、快捷键、打包 | 8 | 12 | MSI 打包与字体 |
| Spike A/B/C | 三个技术验证（见 §7） | 6 | 8 | 协议能力覆盖度 |
| **合计（含 Spike）** | | **57** | **85** | |

估算方法：以大纲 §7 的里程碑交付物做 WBS 分解后逐项估值（如 M2 拆为文件夹树、增量同步、标志位同步、BODYSTRUCTURE 解析、删除与移动、限流退避 6 个子项），基准为「熟悉 Rust、做过一次同类协议客户端」的开发者；乐观值对应不返工，保守值含一次中等规模返工。未使用类比项目系数，也未计入调研与选型时间。

按 20% 缓冲计，**单人全职约 68～102 人日，即 3.5～5 个月**。若 2 人并行（1 人协议/存储，1 人 UI/发信），理论可压到 8～11 周，计入 15%～20% 的接口联调与代码评审开销后为 **9～13 周（约 2～3 个月）**；Spike 可由两人分摊，不额外增加墙钟时间。

### 4.2 关键路径

```
M0 骨架 ─► M1 账户 ─► M2 收信 ─┬─► M3 读信 ─► M5 搜索
                                └─► M4 发信 ─► M6 打磨   ← 关键路径

Spike A（协议）：须在 M2 前完成
Spike B（UI）：  与 M0/M1 并行，须在 M4 前完成
Spike C（FTS）： 与 M0/M1 并行，须在 M5 前完成
```

- **关键路径为 M0 → M1 → M2 → M4 → M6**：按 §4.1 数字为乐观 36 人日 / 保守 55 人日，比 M3 分支（33 / 50）长 3～5 人日；含 Spike A 后为 39～58 人日。
- **M2 是风险最集中的节点**：协议兼容问题一旦返工，会同时推迟 M3/M4/M5 三条下游。
- M4 与 M5 可并行开发（前者依赖 SMTP，后者依赖存储），但都依赖 M2 的数据结构稳定；M5 的正文检索还依赖 M3 的正文拉取完成。

### 4.3 进度风险

| 风险 | 预估影响 | 触发信号 | 应对 |
| --- | --- | --- | --- |
| 服务商 IMAP 行为异常 | +5～10 人日 | Spike A 中出现 3 个以上未覆盖能力 | `me-proto` 内加原始命令；必要时缩小支持列表 |
| trigram 索引超预期 | +3～5 人日 | 1 万封索引 > 1.5 GB 或查询 > 400 ms | 切 jieba 预分词或关闭后台补全 |
| egui 大列表卡顿 | +3～5 人日 | 10 万行滚动低于 30 fps | 分页 + 只渲染可见行 + 减少每行布局元素 |
| MSI 打包与签名 | +2～4 人日 | 打包失败或 SmartScreen 拦截 | 先出便携版，签名后置 |

## 5. 资源需求

| 类别 | 需求 | 说明 |
| --- | --- | --- |
| 人力 | 1 名全职 Rust 开发（最少） | 2 人可缩短至约 2～3 个月（已含联调与评审开销） |
| 测试账号 | QQ、163 各 1 个，Dovecot 1 套 | 真实账号不可替代 |
| 开发环境 | Windows 11 + Rust 工具链 + MSVC Build Tools | 本机已具备 |
| 测试环境 | Docker Desktop（WSL2）跑 GreenMail/Dovecot | 端到端测试前提 |

## 7. 技术验证（Spike）与门禁点

每个 Spike 不超过 3 人日，结论写入 `doc/spike-*.md`。门禁点为：**Spike A 须在 M2 前通过，Spike B 在 M4 前、Spike C 在 M5 前通过**；B/C 可与 M0/M1 并行，不阻塞开工。任一 Spike 未通过时先调整范围或依赖，不越过对应门禁。

### Spike A · IMAP 兼容性（2～3 人日）

**验证内容**
- 用 `async-imap` 登录 QQ、163、Dovecot 三套环境
- 检查能力：`ID`、`SPECIAL-USE`、`MOVE`、`UIDPLUS`、`IDLE`（仅记录）
- 首次全量同步 100 封：`SELECT` → `UIDNEXT` → `FETCH (HEADER BODYSTRUCTURE FLAGS INTERNALDATE)` → 解析中文主题与附件；随后连续 10 次增量同步
- 标志回写：`STORE \Seen`、星标
- 删除：`MOVE` 与 `COPY + \Deleted`（有 `UIDPLUS` 时才 `UID EXPUNGE`）两条路径
- 中文文件夹名往返（modified UTF-7）

**通过标准**
- 三套环境均能完成 100 封首次同步 + 10 次增量同步，中文主题/发件人/文件夹名无乱码
- BODYSTRUCTURE 的附件标记与部件数逐封人工核对，100 封样本 100% 一致
- 删除路径至少一条（`MOVE` 或 COPY 回退）可用，且不会误删未选中邮件
- 连续同步 10 次不触发限流；触发时可按大纲退避恢复

### Spike B · UI 与渲染（2 人日）

**验证内容**
- egui 表格渲染 10 万行（分页数据 + 只渲染可见行）的滚动帧率
- 中文字体内嵌后的显示效果与二进制体积
- 10 万字符正文的滚动与选中性能
- 文件选择对话框与拖拽上传

**通过标准**
- 10 万行滚动 ≥ 30 fps（目标 60 fps）
- 中文无缺字、无排版错位
- 单封长正文打开 < 1 s

### Spike C · SQLite FTS5 中文检索（2～3 人日）

**验证内容**
- 构造 1 万 / 10 万封中文邮件正文，写入 `trigram` FTS5
- 测量：索引体积、3 字以上查询 P50/P95、1～2 字 `LIKE` 头查询耗时
- 对比 `jieba-rs` 预分词方案

**通过标准**
- 1 万封：正文查询 P95 < 200 ms，索引 ≤ 正文文本 3 倍
- 10 万封：查询 P95 < 500 ms（放宽目标），索引 ≤ 4 倍
- 删除与重建后无残留命中

上述查询延迟与索引体积指标均已写入 `doc/项目大纲.md` §7 的 M5 验收标准（v0.4）；实测不达标时先修订大纲指标，再进入 M5。

## 8. 替代方案与取舍

| 方案 | 优点 | 缺点 | 是否采纳 |
| --- | --- | --- | --- |
| egui 原生 GUI | 纯 Rust、单二进制、构建简单 | 原生控件少、大列表需手写 | **采纳** |
| Tauri + Web 前端 | 界面表现力强 | 前后端工具链、包体大、IPC 成本 | 否 |
| TUI（ratatui） | 轻量 | 不符合桌面邮件客户端预期 | 否 |
| 纯在线代理（不缓存） | 实现最简单 | 无离线、无本地搜索 | 否 |
| 自研 IMAP/SMTP | 完全可控 | 工作量大、边界多 | 否 |
| 正文存 SQLite BLOB | 单一存储、事务一致 | 大库膨胀、备份慢 | 否（正文走文件） |
| jieba 预分词 | 索引小、中文查询质量高 | 额外词典与一致性维护 | 备选（Spike C 决定） |

## 9. 可行性结论与 Go/No-Go 条件

**结论：可行。** v0.1 的功能边界、范围决策、架构分层与数据模型已基本闭环；协议路径仍有 §3.2 所列 8 项待 Spike A 证实，回退方案已在 §3.2 逐项写明（其中无 `UIDPLUS` 时的策略是禁用而非降级）。剩余风险集中在外部依赖与协议实现细节，跨文档未决事项统一见大纲 §9。

**Go（进入 M0）的前提**

1. Spike A 在 M2 前通过，Spike B、C 分别在 M4、M5 前通过（或失败项已有经确认的替代方案）。进入 M0 本身不等待 Spike 结果。
2. 用于验收的真实邮箱账号（QQ/163）已就绪。
3. 确认 v0.1 不支持 Gmail/Outlook 的定位可被接受。
4. 确认本地缓存为明文，并在界面与文档中如实告知用户。
5. 接受单人全职 3.5～5 个月的交付预期，或补齐第二名开发者（约 2～3 个月）。

**若条件不满足**

- Spike A 失败 → 缩小支持服务商范围，先做 Dovecot/自建服务器版本，v0.2 再扩。
- Spike B 失败 → 降低列表目标（按文件夹分页加载、放弃单视图 10 万行），大邮箱体验打折但仍可在 M4 前交付。
- Spike C 失败 → 关闭后台补全，v0.1 仅索引已打开正文，搜索范围在 UI 明示。
- 人力不足 → 砍掉 M6 的 MSI 与快捷键，只出便携版。
