# MyEmail 技术栈选用

> 依据：`doc/项目大纲.md` v0.4 §3、`doc/可行性分析.md` §3.1 / §3.7（2026-11-01）
> 本文说明**为什么选它、为什么淘汰别的、出问题换成什么**。与大纲冲突时以大纲为准。
> 关联文档：[项目架构.md](项目架构.md)｜[数据结构.md](数据结构.md)

---

## 1. 选型原则

1. **能用生态库解决的，绝不自己写协议**。IMAP/SMTP 的边角情况远多于文档描述，自研是进度黑洞。
2. **每个关键依赖必须写出替换成本**。写不出替换路径的依赖不进依赖表。
3. **纯 Rust、静态链接优先**。Windows 上避免 OpenSSL 这类需要额外分发的运行库。
4. **依赖尽量收在 `me-proto` / `me-store` 两个 crate 内**，不让上游类型扩散（`me-core` 只依赖纯类型库）。
5. **不为将来可能用到的能力引入依赖**，例如不因「以后可能做富文本」提前引入编辑器框架。

## 2. 总览

| 领域 | 选用 | 成熟度 | 位置 | 备选 / 兜底 |
| --- | --- | --- | --- | --- |
| 语言 | Rust（2024 edition） | — | 全部 | — |
| 异步运行时 | `tokio`（rt-multi-thread, macros, fs, time） | 高 | `me-sync`、`me-proto` | `async-std`（生态与 IMAP 库兼容性差，不建议） |
| GUI | `eframe` / `egui` | 高 | `me-app` | `iced`（等价重写 UI，不视为可行退路） |
| 表格 / 虚拟滚动 | `egui_extras` | 高 | `me-app` | 手写 `ScrollArea` + 只渲染可见行 |
| 原生文件对话框 | `rfd` | 高 | `me-app` | `native-dialog`、直接调 Win32 |
| SMTP | `lettre` | 高 | `me-proto` | 自写 SMTP 客户端（不建议） |
| IMAP | `async-imap` | **中** | `me-proto` | `imap` crate；或在 `me-proto` 内发原始命令（需先验证接口可注入） |
| MIME 解析 / 构建 | `mail-parser` | 高 | `me-proto` | `mailparse`（仅解析） |
| HTML→纯文本 | `html2text` | 中 | `me-proto` | 保留原文，v0.2 换完整渲染 |
| 数据库 | `rusqlite`（bundled，≥ SQLite 3.54.1）+ `r2d2`（连接工厂自己实现，见 `me-store/src/db.rs`） | 高 | `me-store` | `sqlx`（同版本 SQLite） |
| 全文检索 | SQLite FTS5（`tokenize='trigram'`） | 高 | `me-store` | `jieba-rs` 预分词 + 普通 FTS5；不选 tantivy |
| TLS | `rustls` + `webpki-roots` / `rustls-native-certs` | 高 | `me-proto` | 不建议回退 `native-tls` |
| 凭证 | `keyring` | 中高 | `me-sync` | 仅本次会话记忆（已定义） |
| 序列化 | `serde` + `serde_json` | 高 | 全部 | — |
| 时间 | `chrono` | 高 | `me-core` | `time`（时区能力弱于 chrono） |
| 日志 | `tracing` + `tracing-appender` | 高 | 全部 | `log` + `env_logger`（缺少结构化字段） |
| 错误 | `thiserror`（库）/ `anyhow`（应用层） | 高 | 分层 | — |
| 压缩 | `flate2`（`raw/*.eml.gz` 需要） | 高 | `me-store` | `async-compression`（异步场景更重） |
| 目录定位 | `dirs` | 高 | `me-store` | 手写 `%APPDATA%` 解析（跨平台差） |
| Message-ID 生成 | `uuid`（v4）或随机数 + 域名 | 高 | `me-core` | 自写随机串（不推荐） |
| 取消 | `tokio-util`（`CancellationToken`） | 高 | `me-sync` | 自建 `Arc<AtomicBool>`（无法 `select!`） |
| 单实例锁 | `fs2` 文件锁 或 命名互斥量 | 高 | `me-app` | 不做（多实例可能损坏库，见 R12） |
| 时区（v0.3） | `chrono-tz`（IANA 时区库） | 高 | `me-core`、`me-app` | `chrono` 的偏移量（无 DST 规则） |
| 音频解码（v0.3） | `rodio` + `symphonia`（mp3/flac/wav/ogg） | 中高 | `me-app` | `cpal` + 自写解码（成本高）；不引入 mp4/aac |
| 标签与封面（v0.3） | `symphonia`（随 rodio 一起编译） | 中高 | `me-app` | 第三方标签库（多一个依赖） |
| 目录扫描（v0.3） | `walkdir` | 高 | `me-app` | `std::fs` 递归（不跟随符号链接需自己处理） |
| 图片栅格化（v0.2） | `image` + `resvg` | 高 | `me-app` | 不栅格化（直接跳过 SVG） |

> 标注「成熟度」沿用可行性分析的判断口径：高 = 主流稳定；中 = 有明确缺口但有替换路径。

## 3. 逐项说明

### 3.1 语言与运行时：Rust + tokio

- **tokio 的理由**：`lettre`、`async-imap` 都基于 tokio；统一运行时避免两套 reactor。
- **多线程运行时**（`rt-multi-thread`）：同步与补全需要并发，且 `spawn_blocking` 供 SQLite 使用。
- **edition 2024**：`async fn` in trait（RPITIT）已稳定，`me-core` 的端口 trait 不需要 `async-trait` 依赖。
- **代价**：编译时间较长；workspace 拆分反而有助于增量编译——UI 改动不重编协议层。

### 3.2 GUI：egui / eframe

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **egui / eframe** | 采纳 | 纯 Rust、零 JS 工具链、单二进制；立即模式适合高频刷新的邮件列表 |
| Tauri + Web 前端 | 否 | 表现力强，但引入 Node 工具链、包体大、IPC 复制成本，且与「单二进制」目标冲突 |
| iced | 否 | 保留式框架更省心，但生态与示例少于 egui，且本项目以列表 + 文本为主，不需要强布局能力 |
| ratatui（TUI） | 否 | 不符合桌面邮件客户端的用户预期 |

**已知代价**：默认字体无 CJK，需内嵌子集（约 3～6 MB）或加载系统字体；立即模式意味着每帧重建 UI，10 万行列表必须走虚拟滚动（Spike B 验证）。

### 3.3 IMAP：async-imap

**唯一中等风险的核心依赖**，风险点：

1. 维护活跃度有限，扩展命令（`ID`、`MOVE` 之外的服务商私有行为）覆盖不全；
2. 网易/QQ 要求 `ID` 命令这类行为，库不提供时需要补原始命令；
3. 文件夹名 modified UTF-7 编解码的完整性需实测。

**缓解**：`me-proto` 是唯一 `use async_imap` 的地方，替换成本估计 5～10 人日（含可能 fork 的维护成本）。退路有两条：先验证能否在 `me-proto` 内注入原始命令并复用连接；若该库不暴露底层接口，则换 `imap` crate，或在上游不响应时临时 fork 并记录补丁原因与回收计划。

**与 `imap` crate 的取舍**：`imap`（同步接口）更成熟，但需要自己套 tokio 阻塞线程，且 TLS 与超时语义要重做——净收益不明显，列为备选而非首选。

### 3.4 SMTP：lettre

- 覆盖 STARTTLS / 隐式 TLS / SASL PLAIN / LOGIN / MIME 构建 / 附件，正好对应 v0.1 需求。
- 与 `async-imap` 同属 tokio 生态，无需第二套运行时。
- 风险不在库而在服务商：单封大小、发送频率、发件人验证属于配置与提示问题，不构成技术阻塞。
- **不引入** lettre 的地址簿/模板等高级特性，v0.1 用不到。

### 3.5 MIME：mail-parser

- 同时提供**解析**与**构建**能力，发信侧不必再引入 `mime` + `email` 组合。
- 对畸形输入需模糊测试，见 §6。
- 备选 `mailparse`：API 更底层，构建能力弱，替换会牵动发信路径。

### 3.6 存储：rusqlite（bundled）

- **bundled 的意义**：静态链接 SQLite，不受用户机器上旧版本影响；`trigram` 分词器自 SQLite 3.34.0 起可用。
  当前随 `rusqlite 0.41.1` 打包的是 **SQLite 3.54.1**。下限不再写「≥3.43」这种泛泛之词，而是钉在
  **≥3.54.0**——这是 RUSTSEC-2026-0459 / CVE-2026-119375 的修复线（旧版在打开「页大小与库不一致的
  `-wal`」时可能把进程内存里的旧字节当查询结果返回）。`crates/me-store/src/db.rs` 有一条运行时断言
  `SELECT sqlite_version() ≥ 3.54.0`：`cargo deny` 只看 crate 版本号，关掉 `bundled` 或改链系统库时它看不出来。
- **连接模型**：`r2d2` 提供读连接池（4 条），写连接单独持有（SQLite 单写者）。PRAGMA 在每次取连接时设置。
  连接工厂是**自实现**的 `SqliteConnectionManager`（`me-store/src/db.rs`，实现 `r2d2::ManageConnection`）：
  `r2d2_sqlite` 最新版把 rusqlite 钉在 `^0.40`，挡住了上面那次安全升级，而它的全部职责只有建连接 + 校验
  存活，30 行就能等价实现。
- **为什么不选 sqlx**：sqlx 的编译期 SQL 校验需要 `DATABASE_URL` 与离线缓存文件，对「本地单库 + 复杂 FTS 查询 + 动态条件拼接」收益不大；rusqlite 的 API 更直接，且能精确控制 FTS 与 PRAGMA。
- **为什么不用 ORM**：21 张普通表 + 1 张 FTS5 虚表，ORM 会掩盖 FTS 与显式 rowid 维护这类必须精确控制的细节。

### 3.7 全文检索：FTS5 + trigram

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **FTS5 `trigram`** | 采纳（默认） | 内建、无额外依赖；无需中文分词；支持任意 3 字以上子串匹配 |
| `jieba-rs` 预分词 + 普通 FTS5 | 备选 | 索引更小、中文召回更好；代价是词典依赖与「换分词器必须整体重建索引」 |
| tantivy | 否 | 独立索引库，需要双写与一致性维护，与 SQLite 事务脱节 |
| `LIKE '%x%'` 全表扫 | 否 | 10 万封正文不可接受，仅用于 1～2 字头部查询 |

**已知限制**：trigram 要求查询词 ≥3 个字符；1～2 字查询只走头部字段，界面必须提示。该限制随分词方案变化（见可行性分析 §3.4）。

### 3.8 TLS：rustls

- 全部连接走 rustls，避免 OpenSSL 的运行库分发与交叉编译问题。
- 证书根：`webpki-roots`（可预测）与 `rustls-native-certs`（尊重企业根证书）二选一或组合，倾向**优先系统根证书、失败回退内置根**。
- **明确不支持「忽略证书错误」开关**——这是产品决策而非技术限制。

### 3.9 凭证：keyring

- Windows 凭据管理器；macOS Keychain；Linux 视后端可用性。只在 `me-sync` 的 tokio 线程读取，避免 UI 线程被系统调用阻塞。
- 不可用时的降级已在大纲 §2.1 定义：仅本次会话记忆（进程内存），**不提供明文持久化**。

### 3.10 正文降级：html2text

- 只做「HTML → 可读纯文本」，索引与展示共用同一份文本（保证搜索结果能定位到看到的文字）。
- 复杂表格会被压平，这是明确接受的取舍；原始 HTML 随 `raw/` 保留，v0.2 再做完整渲染。
- 备选：自己写 HTML 抽取器（不值得）、引入 Web 引擎（包体与攻击面都不可接受）。

### 3.11 基础设施

| crate | 用途 | 备注 |
| --- | --- | --- |
| `serde` / `serde_json` | 头部结构化存储、`to_addrs` 等 JSON 数组列、事件载荷 | 不用来序列化正文 |
| `chrono` | 邮件 `Date` 头解析、时区换算、列表排序 | 需要 `clock` 特性 |
| `tracing` / `tracing-appender` | 结构化日志、按天滚动 | 保留 7 天 |
| `thiserror` / `anyhow` | 分层错误 | `anyhow` 只在 `me-app` 顶层 |
| `flate2` | `raw/*.eml.gz` 压缩 | 若改存未压缩 `.eml` 可去掉 |
| `dirs` | `%APPDATA%/MyEmail` 定位 | 跨平台路径 |
| `uuid` | 固定 `Message-ID` 生成 | 采用 `<uuid-v4>@<发信域名>`；首次保存草稿时生成并固定，重发复用，见大纲 §4.3 |
| `tokio-util` | `CancellationToken` | 同步可取消 |
| `fs2` | 单实例锁 | 防多实例打开同一库（风险 R12） |

### 3.12 构建与发布

| 项 | 选择 | 说明 |
| --- | --- | --- |
| 构建 | Cargo workspace，`resolver = "2"` | 统一 `Cargo.lock` |
| 工具链 | `rust-toolchain.toml` 固定版本 | 避免本机与 CI 漂移 |
| 发布配置 | `lto = "thin"`、`codegen-units = 1` | 二进制更小、运行更快，构建稍慢 |
| 打包 | MSI（WiX）+ 便携 zip | 大纲待确认项；建议两者都出 |
| 签名 | 可选 | 无签名会有 SmartScreen 提示 |

## 4. 明确不引入的技术

| 技术 | 不引入的理由 |
| --- | --- |
| Web 引擎（WebView2 / wry） | 包体、内存、攻击面；v0.1 不做完整 HTML 渲染 |
| ORM（diesel / sea-orm） | 表少，且 FTS5 与显式 rowid 维护需要精确 SQL |
| tantivy / 外部检索引擎 | 双写一致性与部署复杂度不划算 |
| OpenSSL | 交叉编译与运行库分发麻烦，rustls 已足够 |
| 插件 / 脚本引擎（Lua、WASM） | 非目标，架构上不预留 |
| SSE 客户端库 | `me-proto/sse.rs` 自行按行解析即可（约 270 行）；引入库只为一个协议不划算 |
| 通用 HTTP 客户端 | v0.1 无 HTTP 接口；v0.2 起 OAuth、v0.3 起天气与 AI 都用 `reqwest`（仅 `me-proto` 内部使用，对外不暴露类型） |
| 富文本编辑器 | v0.1 纯文本撰写（大纲 §1.2） |
| 系统通知库（`notify-rust` 等） | v0.3 未交付系统通知；引入平台相关依赖的收益尚不明确，留到 v0.4 决策 |

## 5. 版本与依赖治理

1. **不写死版本号**：初始化时用 `cargo add` 取当前稳定版，结果锁进 `Cargo.lock`。
2. **MSRV 策略**：取所依赖 crate 的实际下限，并在 `rust-toolchain.toml` 固定；不追求「最新编译器」。
3. **`cargo-deny`**：许可证白名单（MIT / Apache-2.0 / BSD / ISC / MPL-2.0）+ 漏洞公告 + 重复版本检查。
4. **升级节奏**：安全更新立刻跟；次要版本在里程碑间隙批量升，升级后跑全量测试与 Spike 回归用例。
5. **默认不引入 git 依赖或 fork**：若 `async-imap` 缺必需命令且上游不响应，允许临时 fork，必须记录补丁原因、回收计划与升级方式（见 §3.3）。

## 6. 依赖风险与替换成本

| 依赖 | 风险 | 触发信号 | 替换成本 |
| --- | --- | --- | --- |
| `async-imap` | 维护活跃度、命令覆盖 | Spike A 出现 3 个以上未覆盖能力 | 5～10 人日（含 fork 维护） |
| `html2text` | 复杂 HTML 可读性 | 用户反馈正文不可读 | 2～3 人日（v0.2 完整渲染）或换库 |
| `egui` / `eframe` | 大列表性能、CJK 字体 | Spike B 帧率不达标 | 替换等价于重写 UI（`iced`），不作为可行退路；只能优化（虚拟滚动 + 分页） |
| `rusqlite` | FTS5 trigram 体积 | 索引 > 正文 4 倍 | 换分词方案，不换库 |
| `keyring` | 便携模式不可用 | 用户无凭据管理器 | 已定义会话内存降级 |
| `mail-parser` | 畸形 MIME 崩溃 | fuzz 发现 panic | 单封隔离解析 + 解析超时；必要时换 `mailparse` |
| `reqwest`（v0.2，OAuth） | 代理/TLS 行为、包体增长 | OAuth 在代理环境不可用 | 换 hyper + rustls 直连；仅 `me-proto` 使用，影响面集中 |
| `rand`（v0.2） | 随机源质量 | PKCE/state 熵不足 | 可直接换 `getrandom` |
| `sha2`（v0.2） | 包体 | 哈希实现替换 | 可换 `ring` / `aws-lc-rs` 的 SHA-256 |
| `scraper`（v0.2，HTML） | html5ever/selectors 版本耦合 | 上游 API 破坏 | 直接使用 `html5ever` + `selectors`，约 3～5 人日 |
| `cssparser`（v0.2） | MPL-2.0 依赖 | 许可证白名单变化 | 已允许 MPL-2.0；可换自写声明解析 |
| `url`（v0.2） | 与 reqwest 共用版本 | 版本冲突 | 与 `reqwest` 的 `url` 对齐即可 |

**v0.2 依赖约束**：`reqwest` 只在 `me-proto` 的 OAuth 路径使用，沿用 `default-features = false` + rustls，不自动跟随系统代理；令牌端点禁止重定向、响应体 ≤64 KB。`rand` 只用于 PKCE verifier、`state` 与轮询抖动；`sha2` 只用于 PKCE S256 与草稿规范化哈希。

**模糊测试**：对 `mail-parser` 入口接 `cargo-fuzz`，语料取自真实 `.eml` 夹具的变异体；任何 panic 必须修复或降级为「解析失败」而非崩溃。
